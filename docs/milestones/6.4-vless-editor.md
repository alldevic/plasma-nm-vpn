# 6.4 VLESS XHTTP Reality editor

**Stage:** 6 · **Duration:** 2 d · **Depends on:** 6.3, 4.1, 4.2 · **Needed for:** 6.7

## Goal
A VLESS XHTTP Reality profile is created in plasma-nm and connected from the applet. The editor follows the 6.3 pattern; the main work here is its own “Reality” and “XHTTP transport” blocks, the protocol fields and their validation, with value lists taken from the xray package data so they do not drift from the core.

## Inputs
- Shared blocks and message code rendering from 6.1, the kill switch banner from 6.2. The Hysteria2 editor from 6.3 as the pattern: secrets, `askUser()`, `vpn.persistent` on every save, the kill switch hint, empty `supportedFileExtensions()` and `suggestedFileName()`.
- From 4.1: the data file with the value lists (TLS fingerprints, XHTTP modes) and the `extra` and `xhttp-extra` allowlists, shipped in `plasma-nm-vpn-xray`. The xray daemon and integration tests (4.2); the integration bench from 1.4 with the bench DNS 203.0.113.1.
- [design.md](../design.md), section “Profile data schema”: VLESS XHTTP Reality keys, the `uuid` secret, item “Secrets”.
- [design.md](../design.md), section “plasma-nm user interface”: the table of blocks (“Reality” and “XHTTP transport” live in the VLESS editor), value lists as core package data, form validation through the 2.2 library with allowlists; the `encryption` field (default `none`) and `uuid` masked with `setPasswordModeEnabled(true)`.
- [design.md](../design.md), section “Leak protection”, item “Kill switch”: a permanent hint next to the checkbox, since the editor cannot see never-default.
- [design.md](../design.md), section “Architecture”, item “Service names follow the protocol, not the core”: `org.freedesktop.NetworkManager.pnv.vless`.

## Tasks
- [ ] A `VpnUiPlugin` subclass in the `plasma-nm-vpn-xray` package.
  - `X-NetworkManager-Services` = `org.freedesktop.NetworkManager.pnv.vless`.
  - A constructor without side effects (the data file is read when the form is created); `supportedFileExtensions()` returns an empty list, `suggestedFileName()` an empty string.
- [ ] A form from the 6.1 blocks “Server”, “Authentication”, “Protection”, “Advanced” (`mtu`, `extra` with the xray `extra` allowlist), plus this editor's own blocks below. The shared “TLS” block is not used: SNI and fingerprint are part of “Reality”.
- [ ] An `encryption` field next to “Authentication”: default `none`, or a VLESS Encryption ML-KEM value, kept exactly as entered or loaded, so that an imported ML-KEM value survives save and export.
- [ ] Own block “Reality”: `tls-sni`, `reality-pbk`, `reality-sid`, `reality-spx`, `tls-fingerprint` (a choice from the 4.1 fingerprint list).
- [ ] Own block “XHTTP transport”: `xhttp-mode` (a choice from the 4.1 mode list), `xhttp-path`, `xhttp-host`, `xhttp-extra` (JSON).
- [ ] No value list is duplicated in the code; a missing or unreadable data file makes the form show an error instead of guessing values.
- [ ] Validation through the 2.2 library: `encryption` (`none` or a VLESS Encryption ML-KEM key), `reality-pbk`, `reality-sid`, the UUID format, and `xhttp-extra` and `extra` including their allowlists; messages are codes rendered by 6.1.
- [ ] The `uuid` secret via `PasswordField` with `setPasswordModeEnabled(true)`, as for every secret field in 6.3.
  - `uuid-flags` flags: StoreForUser → `AgentOwned`, StoreForAllUsers → `None`, AlwaysAsk → `NotSaved`. The default storage is the `PasswordField` default (StoreForUser when a keychain is available), as in 6.3.
  - `askUser()` for `uuid` (kded6 shows it, as in 6.3).
- [ ] The kill switch hint from 6.1 is shown next to the checkbox, as in 6.3.
- [ ] `setting()` writes `schema` and calls `VpnSetting::setPersistent(true)` on every save.
- [ ] Plug in the kill switch banner from 6.2, as in 6.3.
- [ ] Strings via ki18n, source strings in English; `Name[ru]`/`Description[ru]` via the 6.1 CMake function. Fingerprint and mode values are shown as is, not translated.

## Deliverables
- The VLESS XHTTP Reality `VpnUiPlugin` plugin in the `plasma-nm-vpn-xray` package with its “Reality” and “XHTTP transport” blocks, its metadata and the `uuid` prompt widget.

## Done when
- [ ] The “Add VPN” list in the VM → a VLESS XHTTP Reality entry is present, the form opens.
- [ ] A profile created in the form against the bench from 1.4, DNS 203.0.113.1 set in the “Protection” block before connecting → connects and disconnects from the applet; a DNS query goes through the tunnel.
- [ ] The fingerprint and XHTTP mode choices → exactly the values in the 4.1 data file; a test value added to the file in the VM appears without rebuilding the editor.
- [ ] An `xhttp-extra` key outside the allowlist, a path in `extra` or a malformed `reality-pbk` → the form is invalid with a readable message.
- [ ] `nmcli -s -g vpn.data,vpn.secrets connection show <id>` → `uuid` is present only in `vpn.secrets`, `uuid-flags` in `vpn.data`; the field shows the UUID masked.
- [ ] Each of the three `uuid` storage modes → the connection succeeds.
- [ ] A new profile → `encryption=none` in `vpn.data`. A profile whose `encryption` holds an ML-KEM value (written with `nmcli connection modify`) → the field shows the value, and re-saving in the editor keeps it byte for byte; a malformed value → the form is invalid with a readable message. The chain “imported `vless://` with ML-KEM `encryption` → save → export → re-import” is checked in 6.8.
- [ ] `nmcli -g vpn.persistent connection show <id>` for a new profile → `yes`; re-saving an existing profile keeps `vpn.persistent=yes`.
- [ ] The “Protection” block → the hint “The kill switch applies only when all traffic goes through the VPN” is shown next to the kill switch checkbox.
- [ ] A kill switch block produced by `kill -9` of the daemon after success, or by stopping the bench server and waiting for the cycle timeout → the banner is visible in the VLESS form.

## Risks and notes
- A UUID is not a password, but it is the credential of a VLESS account and is stored as a secret; it is masked like one (design.md, “plasma-nm user interface”); this does not affect storage.
- The set of `xhttp-mode` and fingerprint values depends on the xray version; taking them from the package data keeps the editor in step with the core on update.
- `kill -9` of the core after success does not leave a block: the reconnect cycle restores the connection.
- The routing loop, UDP through TUN and `sockopt.interface` were verified in 0.6 and 4.2 and are not rechecked in this milestone.
