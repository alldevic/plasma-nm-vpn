# 5.5 Reconnection

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.4, 0.7 · **Needed for:** 5.6, 5.8, 6.2

## Goal
The daemon restores a successful session by itself after a change of the parent device, after sleep, after a core crash and after three failed liveness checks, without letting go of the connection in NM and without traffic leaving directly while the core is recreated. For can-persist plugins NM does not retry the connection either after `STOPPED` or after a daemon crash, so reconnection is entirely up to the daemon. This milestone builds the cycle itself; updating the earlier suites and the CI tests are 5.6–5.8.

## Inputs
- The `STARTING` → re-sending the configuration cycle, verified in 0.7; network parameters, the persistent TUN and binding to the parent device from 2.4; whether each core attaches to an existing persistent TUN (0.4, 0.6); the per-core post-start step from 3.1; the liveness check and its periodic schedule from 5.4; the session server IP that 2.4 writes to the run directory; the give-up flag, the success marker, the versioned run-directory format and the kill switch rules from 5.1; the inherited-block and takeover rules from 5.2; `guard-status` from 5.3.
- [design.md](../design.md), sections “Network changes and sleep” (the TUN belongs to the daemon, the fallback block chain, the cycle steps), “Core supervision and cleanup” (item “Core unit failure”), “Leak protection”, “Route to the server”, “Testing” (Wi-Fi emulation, real suspend woken by `rtcwake`, test hooks only in the test build).
- The behavior of NM 1.58.1 (`src/core/vpn/nm-vpn-connection.c`) and libnm is already analyzed in design.md and does not need to be re-verified.

## Tasks
- [x] Track the parent device of our connection through libnm (`NMClient`), the same way 2.4 determines the device for binding.
- [x] Sleep tracking: the `PrepareForSleep` signal on `org.freedesktop.login1.Manager`, accepted only from logind; after waking up (`false`), a reconnect cycle.
- [x] Session server IP: the file that 2.4 already writes to the run directory (the IP of this session: resolved, cached or a literal) moves into the versioned run-directory format of 5.1. The cycle reads it from there; it never resolves the name and does not depend on the cache.
- [x] The reconnect cycle in the shared library, started only from `STARTED` (NM handles `STARTING` only on a transition from `STARTED`):
  1. `g_object_set(plugin, NM_VPN_SERVICE_PLUGIN_STATE, NM_VPN_SERVICE_STATE_STARTING, NULL)`; libnm has no public `set_state`. NM moves the connection to ACTIVATING and does not remove the routes. If there is no parent device (after resume NM often brings devices back only later), the cycle waits for one; the wait counts against the cycle timeout, and step 2 starts only once a device exists.
  2. Recreate the core unit: `StopUnit` on `plasma-nm-vpn-core-<uuid>.service`, then `StartTransientUnit` with a regenerated config (a garbage-collected unit cannot simply be restarted) carrying the session server IP and, for the proxy cores, the new binding (`bind_interface` / `sockopt.interface`). The core attaches to the same persistent TUN, so NM's routes stay. Then the per-core post-start step: for AmneziaWG, remove the stale UAPI socket before the start, wait until amneziawg-go has attached to the TUN and its UAPI socket has appeared, then run `awg setconf` again (it has no interface binding to update). While the core is down, traffic routed into the TUN is dropped there rather than leaving directly. The guard unit is bound to the daemon's scope, not to the core, so the DNS and IPv6 guard and the kill switch chains stay as they are.
  3. Wait until the core has attached to the TUN (netlink), then Config (`TUNDEV`, external gateway, `CAN_PERSIST`) and `Ip4Config` back to back. NM returns the connection to ACTIVATED and the plugin is `STARTED` again.
  4. The liveness check (5.4). The cycle succeeds only when it passes; otherwise it is retried with an increasing backoff (e.g. 1, 2, 4 … s, with an upper bound): from step 1 if the plugin is `STARTED` again (only a new `STARTING` makes NM reread DNS), from step 2 if it is still `STARTING` (step 2 or 3 failed; setting `STARTING` again would be a no-op).
- [x] Fallback, only for a core that 0.4 or 0.6 found unable to attach to a persistent TUN: for default-route tunnels, a temporary per-UUID block chain (the kill switch rules) is installed before `StopUnit` and removed only after NM reports ACTIVATED again at the end of step 3 (the routes are back), even with `kill-switch=no`; `--daemon-gone` and orphan cleanup always remove it, like the DNS and IPv6 guard chains.
- [x] Triggers: a parent device change, a wake-up, a core unit failure after success, three failed periodic liveness checks in a row (this replaces the interim give-up of 5.1 and 5.4). A core unit failure before success still means give-up. The periodic check is paused during the cycle.
- [x] Events arriving during the cycle (several device changes in a row) are coalesced: the cycle continues with the latest device, without an extra transition to `STARTING`.
- [x] Cycle timeout: NM has no timeout in this state, so the daemon keeps its own, covering device waits and retries. Choose the value from measurements in the VM and record it in design.md, section “Network changes and sleep”. When it expires the daemon gives up: sets the give-up flag and calls `nm_vpn_service_plugin_failure`, the connection goes to `STOPPED`; the session has the success marker, so the kill switch chains remain and `guard-status` gets the entry.
- [x] An explicit disconnect during the cycle stops it and is handled by the 5.1 and 5.2 rules.
- [x] Log every step of the cycle with its trigger, the device and the attempt number.
- [x] Test build only (`-DPNV_TEST_HOOKS=ON`, never packaged, design.md “Testing”): a switch that skips step 1 and a switch that sends a different DNS list in the cycle's `Ip4Config`, for the 5.8 check that the test does not pass vacuously. Nothing else for tests is added in this milestone.
- [x] Manual check in the VM (KVM): Wi-Fi via `mac80211_hwsim` and `hostapd`, Ethernet (veth) as a second interface managed by NM; a real `systemctl suspend` (S3) woken by `rtcwake`, as set up in 0.2 and 1.4. The VM is driven over `AF_VSOCK`; its management NIC is never disconnected.

## Deliverables
- Device and sleep tracking, the session server IP in the versioned run-directory format, the reconnect cycle with the liveness check, the timeout and the core recreation in `plasma-nm-vpn-common`; the daemons supply only their post-start step; the fallback block chain if 0.4/0.6 require it; the two switches in the test build.
- The cycle timeout in design.md.

## Done when
- [x] In the VM with the tunnel up, the parent device is switched from emulated Wi-Fi to Ethernet and back → ACTIVATING → ACTIVATED, the liveness check passes, the route to the gateway is on the new device, the tunnel's DNS is in place, traffic flows. For all three protocols.
- [x] `rtcwake -m no -s 20 && systemctl suspend` (S3) with the tunnel up → after resume, with the device returning only some seconds later, the tunnel is restored without user involvement.
- [x] With `kill-switch=no` on a default-route tunnel, a parent device change and a `kill -9` of the core → a capture on the physical interfaces shows no IPv4 leaving directly (other than to the server, DHCP and local networks) during the cycle; `ip link show pnv-…` shows the same interface index before and after (or the fallback block chain existed during the restart).
- [x] After success, `kill -9` of the core process → the core unit is recreated, the connection is ACTIVATED again and passes the liveness check; with the kill switch there is no `guard-status` entry afterwards.
- [x] The bench server is stopped while connected, or the parent device is removed and none comes back → the cycle gives up after the timeout; NM does not reconnect on its own; with the kill switch the chains are in place and `guard-status` shows the block.

## Risks and notes
- Without step 1, NM updates the routes and the gateway but not DNS: DNS is applied only on the transition to ACTIVATED. This is established in design.md.
- The core binds to the VPN's parent device in NM, not to the system's “best” device: if the old device stays up, NM keeps the VPN on it, and there is no need to reconnect.
- The VM sleeps in S3, not s2idle, because QEMU does not wake an s2idle guest on the RTC alarm (0.2); s2idle is checked on the hardware test machine in 7.2. The daemon gets no emulated sleep path.
- The core-kill cases of the 2.7, 3.2 and 4.2 suites expect a give-up after success and stop matching here; this milestone only marks those cases as expected failures with a reference to 5.6, which rewrites them, so CI stays green in between.
- Results:
  - Code, in `core.c`:
    - The reconnect cycle: STARTING; wait for a parent device; the core unit stopped and recreated through the protocol's own `connect` (its post-start step included, so AmneziaWG removes its socket and runs `awg setconf` again); Config and `Ip4Config`; the liveness check.
    - Retries back off 1, 2, 4, 8 and 16 s, from step 1 if the plugin is `STARTED` again, else from step 2; the cycle gives up after 120 s.
    - Events during a cycle join it: one more step 2 with the latest device, without a new STARTING.
    - Triggers: `notify::devices` of the VPN's active connection; logind's `PrepareForSleep(false)`, subscribed by its bus name; a core unit failure after success (before success it is still a give-up); three failed liveness checks.
    - The periodic check pauses during a cycle. Cleanup steps are registered once per name, so recreating the core does not stack them. The session server IP is `server-ip` in the 5.1 state file.
  - Findings, recorded in design.md (“Network changes and sleep”):
    - NM 1.58.1 does not give a default-route VPN a new parent device, so the daemon makes the VPN step aside under a temporary block chain.
    - NM leaves the VPN ACTIVATING after an identical `Ip4Config`, so the config varies from cycle to cycle.
  - Test hooks: `skip-starting` (no step 1) and `cycle-dns` (an extra DNS server, 203.0.113.53, in the cycle's `Ip4Config`).
  - Manual check in the VM (a detached script). The second parent is a second veth to the bench, `stand-cli2` (192.0.3.2) under NM with a worse metric. Wi-Fi via `mac80211_hwsim` is left to 5.8.
    - For Hysteria2, VLESS XHTTP Reality and AmneziaWG: after `nmcli device disconnect stand-cli` the connection was ACTIVATED again in 3–4 s on `stand-cli2`, NM's route to the server on `stand-cli2`, DNS 203.0.113.1, traffic flowing; back to `stand-cli` likewise.
    - After `kill -9` of the core: reconnected in 0–2 s, the same TUN ifindex, ACTIVATED, traffic, no direct IPv4 during the cycle, no `guard-status` entry; three kills in a row all ended ACTIVATED.
    - With `kill-switch=no` during a parent change: no direct IPv4 on `stand-cli2` apart from an mDNS announcement to 224.0.0.251, which stays on the link; no temporary chain left afterwards.
    - Server stopped: the cycle started after 196 s (three failed checks) and gave up after another 136 s; the chains and the `guard-status` entry remained; NM did not reconnect.
  - Suspend: `tests/integration/cases/test_91_resume.py` (kvm and test build), a real S3 suspend woken by `rtcwake`; the tunnel must come back with “reconnected (trigger: resume”. The local VM cannot sleep, so this runs in CI.
  - The full local suite: 69 cases, green.
  - CI: `test_91_resume` passed in both DNS modes. After a real S3 suspend woken by `rtcwake`, the Hysteria2 tunnel was ACTIVATED again with “reconnected (trigger: resume …)” and traffic flowed, with no give-up.
  - The first CI run also showed that `test_80_packages` reinstalled only common and sb, while removing common also removes the other core packages. It now reinstalls all four.
