# 2.6 DNS and IPv6 guard

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 2.4 · **Needed for:** 2.7, 5.1

## Goal
Meet the requirement “with a default-route tunnel, DNS and IPv6 never bypass the tunnel” with our own nftables chains. This milestone also creates the per-UUID chain mechanism in the `inet plasma_nm_vpn` table that the kill switch will build on in 5.1, and the chain removal in `plasma-nm-vpn-guard --daemon-gone`.

## Inputs
- The network parameters from 2.4 (TUN name, resolved server IP), the core launch module from 2.3 (guard unit, `plasma-nm-vpn-guard --daemon-gone`, synchronous `disconnect`).
- [design.md](../design.md), section “Leak protection”: the `inet plasma_nm_vpn` table, chains with the UUID in the name on the `output` and `forward` hooks, “the tunnel” = any of our `pnv-*` interfaces; item “DNS and IPv6 guard” (reject of IPv6 and of DNS on 53 and 853 via non-tunnel interfaces; link-local and multicast destinations and ICMPv6 neighbour discovery to any address allowed; loopback untouched; the `meta skuid plasma-nm-vpn` exception); item “When the chains are installed”.
- [design.md](../design.md), section “Core supervision and cleanup”: items “On `Connect`, in this order”, “Disconnect”, “Daemon crash”, “`--daemon-gone <uuid>`”.
- [design.md](../design.md), section “Architecture”, item “Paths”: nftables templates in `/usr/share/plasma-nm-vpn/`.

## Tasks
- [x] The indicator “the tunnel carries the default route”: the profile's `ipv4.never-default` from `Connect`. Check whether there are other cases where NM does or does not set a default route via the VPN.
- [x] A template in `/usr/share/plasma-nm-vpn/`. A sketch, to be refined during implementation:
  - the `inet plasma_nm_vpn` table and the connection's chains with the UUID in the name, one each for the `output` and `forward` hooks (`type filter`, priority `filter`);
  - in `output`, the first rule `meta skuid "plasma-nm-vpn"` → `return`;
  - `oifname "lo"` → `return`;
  - IPv6: `icmpv6 type { nd-router-solicit, nd-neighbor-solicit, nd-neighbor-advert }` → `return` for any destination (the kernel also sends neighbour probes to global addresses); destinations `fe80::/10` and `ff00::/8` → `return`; otherwise `oifname != "pnv-*"` → `reject` (for TCP, `reject with tcp reset`);
  - DNS: `oifname != "pnv-*"`, `udp`/`tcp dport { 53, 853 }` → `reject`;
  - a counter on each reject rule (used by the tests).

  “Tunnel” is any of our `pnv-*` interfaces, not only this connection's TUN. Each connection has its own base chains, and a `reject` in any base chain is final (an `accept` in one does not cancel it), so a narrower match would make one connection's chains reject traffic and DNS correctly routed into another connection's tunnel.
- [x] Applying: `nft -f` with a filled-in template, or libnftables — choose one. Only values the daemon itself generates (the UUID) are substituted into the rule text; values from the profile, never.
- [x] Ordering on `Connect` (design.md, step 3): the chains are installed after the guard unit is running, the server name is resolved and the persistent TUN is created (2.4), and before the core starts and `Ip4Config` is sent (so a crash at any later moment is cleaned up and there is no unprotected window). A never-default profile → the chains are not installed.
- [x] Removal in the synchronous `disconnect` (2.3), after the core stops and the TUN is deleted, and before the run directory is deleted and the guard unit stopped. Orphan cleanup on `Connect`: delete leftover DNS/IPv6 chains of our UUID (kill switch chains are the concern of 5.1).
- [x] Removal if the daemon crashes: extend `plasma-nm-vpn-guard --daemon-gone <uuid>` from 2.3, which the guard unit runs as root. It acts only if `/run/plasma-nm-vpn/<uuid>/` still exists and then deletes the DNS/IPv6 chains of this UUID before the run directory. Kill switch chains and the success marker are added in 5.1, the “inherited block” and takeover markers in 5.2, `guard-status` in 5.3. The guard unit mechanism itself was verified in 0.5 and built in 2.3; do not investigate it again.
- [x] Verification in the VM with scripts suitable for moving into 2.7.

## Deliverables
- An nftables module in `plasma-nm-vpn-common`, the DNS and IPv6 guard rule template, chain removal in `plasma-nm-vpn-guard --daemon-gone`.

## Done when
- [x] A default-route tunnel is up, `tcpdump` on `stand-cli` → no packets to 53/853 and no IPv6 other than link-local/multicast and neighbour discovery; the core's traffic to the server flows.
- [x] `dig @192.0.2.1 srv.stand.test` (the “ISP” DNS) → an immediate error (reject), not a timeout. A name query through the system resolver gets an answer through the tunnel in both DNS modes: in the default `resolv.conf` mode via the VPN's DNS server listed first in `/etc/resolv.conf`, in the systemd-resolved variant via 127.0.0.53.
- [x] `ping -6 -c1 2001:db8:1::1` → immediate error from the reject, not a timeout. With a profile using `server=srv6.stand.test` (the core talks to 2001:db8:100::1 over IPv6): `ip -6 neigh change 2001:db8:1::1 dev stand-cli nud stale`, then traffic through the tunnel → the kernel's unicast neighbour probes to the global address pass (seen in `tcpdump`), the entry returns to `REACHABLE`.
- [x] `forward` hook: a test netns `tst-fwd` with a veth `tst-fwd0` to the root namespace (the `tst-` prefix, never `pnv-`, which the rules treat as a tunnel), `net.ipv4.ip_forward=1` and masquerade out of `stand-cli`; with the tunnel up, `ip netns exec tst-fwd dig @192.0.2.1 srv.stand.test` (an address routed via the parent device) → rejected immediately, and the counter of the DNS reject rule in this UUID's `forward` chain grows.
- [x] `nmcli connection down` → once the daemon has exited, `nft list table inet plasma_nm_vpn` has no chains for this UUID.
- [x] `kill -9` of the daemon → there are no DNS/IPv6 chains for this UUID and no `/run/plasma-nm-vpn/<uuid>/`; the journal shows `--daemon-gone` acting.
- [x] Two simultaneous connections (a default-route tunnel and a second one with a route to 203.0.113.1 and that server as its DNS) → HTTP traffic and DNS queries routed into the second tunnel are not rejected by the first one's chains.
- [x] A never-default profile → no chains, DNS works as without the VPN.

## Risks and notes
- The IPv6 checks need IPv6 on the parent device; the bench (0.3, 1.4) provides it on `stand-cli`, plus the server's IPv6 address.
- The `skuid` exception relies on the core running as `plasma-nm-vpn`. If sing-box has to be run as root (a risk in design.md), the exception is reworked to match on the unit's cgroup.
- Kill switch and fail closed are milestone 5.1, `guard-status` and `plasma-nm-vpn-guard --clear` are 5.3, not here. The kill switch's own DNS rule (53 and 853 rejected towards every non-tunnel destination, local networks included, even with `allow-lan`) and its MLD exemption belong to 5.1; the guard here is unchanged by them: it already rejects 53/853 on every non-tunnel interface whatever the destination, and its link-local/multicast exemption covers MLD.
- Test namespaces and interfaces use the `tst-` prefix, never `pnv-`.
- Results:
  - Code: `common/daemon/nft.c` applies the template `common/data/guard.nft` (installed as `/usr/share/plasma-nm-vpn/guard.nft`) through `nft -f -`, substituting only the checked UUID. The chains are `guard-out-<uuid>` and `guard-fwd-<uuid>` in `inet plasma_nm_vpn`. They are removed with `destroy chain`, which is idempotent, on disconnect after the TUN, in the orphan cleanup and in `--daemon-gone`. In the test build `--daemon-gone` also removes the dummy `test-<8>` chain of 2.3.
  - Indicator: NM 1.58.1 routes the default via a VPN unless the profile has `ipv4.never-default`, or the plugin sends `never-default` in `Ip4Config`, which only AmneziaWG will do (3.x) and which then has to count as never-default too. Not covered: a never-default profile whose own `ipv4.routes` contain `0.0.0.0/0` gets a default route without the guard. That is the user's explicit choice and is noted for 5.1.
  - Cases: `tests/integration/cases/test_33_guard.py`, 7 cases on the bench:
    - no 53/853 and no non-link-local IPv6 on `stand-cli`;
    - `dig @192.0.2.1` refused at once, `ping -6` failing at once;
    - names resolved through the tunnel;
    - the neighbour probe to the global gateway address passing with `srv6.stand.test`;
    - forwarded DNS from netns `tst-fwd` rejected, with the counter of the `forward` chain growing;
    - chains gone after `down` and after `kill -9`;
    - a second never-default tunnel with `dns=203.0.113.1` not blocked;
    - no chains for never-default.
  - Found in the full run: a connect right after another VPN went down could fail with “has no address”. While NM rewrote `resolv.conf`, the lookups failed fast with a temporary error. Resolution now retries every 250 ms within the 5 s budget, unless both A and AAAA answer “no such name”. The full suite (2.1–2.6) is 38 cases, green in the VM.
