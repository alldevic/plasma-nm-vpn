# 3.2 Routes and tests

**Stage:** 3 · **Duration:** 2 d · **Depends on:** 3.1 · **Needed for:** 4.1, 6.5

## Goal
Bring AmneziaWG up to the level of Hysteria2: NM sets the address, routes, DNS and MTU from the profile fields, and the integration suite in CI confirms traffic, the absence of leaks and cleanup. After this milestone AmneziaWG works through `.nmconnection` and `nmcli`.

## Inputs
- AmneziaWG daemon from 3.1 (minimal `Ip4Config`); test suite and shared check helpers from 2.7; integration test bench from 1.4.
- [design.md](../design.md), section “Profile data schema”, “AmneziaWG rules in the MVP”: first IPv4 from `address`, dropping IPv6, detecting a default-route tunnel, `NM_VPN_PLUGIN_IP4_CONFIG_NEVER_DEFAULT=true` for split tunnels, default DNS.
- [design.md](../design.md), section “Routing, DNS and IPv6”: NM is the sole owner of addresses, routes and DNS; `AllowedIPs` are passed to NM as routes; “Route to the server”; “DNS” (no defaults with never-default, /32 routes via the TUN for explicit DNS servers); “Leak protection”.
- For reference: the `Ip4Config` keys in `nm-vpn-dbus-interface.h` and their handling in `src/core/vpn/nm-vpn-connection.c` (NM 1.58.1).

## Tasks
- [x] `address` → `NM_VPN_PLUGIN_IP4_CONFIG_ADDRESS` and `_PREFIX`: the first IPv4 address; the daemon skips the remaining IPv4 and all IPv6 addresses with a warning in the journal (the profile may have been created other than through import).
- [x] The “default-route tunnel” flag follows the design.md rule: `allowed-ips` contains `0.0.0.0/0` and `ipv4.never-default` is not enabled in the settings from `Connect`. The 2.6 guard (and later the 5.1 kill switch) depend on it. The split `0.0.0.0/1` + `128.0.0.0/1` is normalized to `0.0.0.0/0` by one function of the shared 2.2 validator library, which the daemon calls on `allowed-ips` here before the flag is computed; the editor (6.5) and the importer (6.6) call the same function, so all three treat such a profile alike. If 2.2 did not provide the function, it is added to the library here, with unit tests.
- [x] `allowed-ips` → `NM_VPN_PLUGIN_IP4_CONFIG_ROUTES`, IPv6 entries are skipped, `0.0.0.0/0` is never passed as a route. A default-route tunnel → `NEVER_DEFAULT` is not set; otherwise (narrow `allowed-ips`, or `0.0.0.0/0` with `ipv4.never-default`) the daemon passes `NM_VPN_PLUGIN_IP4_CONFIG_NEVER_DEFAULT=true` and only the narrower entries as routes, because NM would otherwise put a default route through the VPN. NM applies the user's `ipv4.ignore-auto-routes` on top by itself.
- [x] `dns` → `NM_VPN_PLUGIN_IP4_CONFIG_DNS`, through the same 2.4 code as for the proxy cores: empty `dns` and a default-route tunnel → `1.1.1.1` and `9.9.9.9`; with never-default no defaults are passed, and DNS servers set explicitly get /32 routes via the TUN, so that queries to them go into the tunnel.
- [x] `mtu` → `NM_VPN_PLUGIN_CONFIG_MTU` in Config (without the field, amneziawg-go's value stays).
- [x] Route to the server: the external gateway from 2.4 (the endpoint IP); verify that when `allowed-ips` include the server's address, the /32 via the parent device wins and there is no loop.
- [x] Unit tests for the field mapping: several addresses, IPv6 in `address` and `allowed-ips`, `0.0.0.0/0` and the split `0.0.0.0/1` + `128.0.0.0/1` with and without never-default, narrow `allowed-ips` with and without `dns`, empty `dns`.
- [x] Test profiles following 2.7: a default-route tunnel without `dns`, and never-default with narrow `allowed-ips`; the AWG 3.1 parameters match the test bench server. The default-route profile without `dns` is checked for the defaults only at the NM level; profiles that resolve names set `dns=203.0.113.1` (the bench DNS), as in 2.7.
- [x] Integration tests on the shared 2.7 helpers: connection and traffic; DNS and IPv6 leaks (`tcpdump` on the physical interface); never-default: only the routes from `allowed-ips` (plus the /32 to an explicit DNS server) exist, no guard chains; cleanup after `Disconnect` and `kill -9` of the daemon (the guard unit's `--daemon-gone` removes the persistent TUN, the socket in `/run/amneziawg` and the run directory); the core runs as `plasma-nm-vpn`; reconnecting after the crash scenarios.
- [x] Test “`kill -9` of the core”: as in 2.7, the daemon gives up and “no traces left” holds, including the socket in `/run/amneziawg`. From 5.5 the behaviour after success is recovery through the reconnect cycle; 5.5 marks the after-success case as an expected failure and 5.6 updates this test to recovery after success and give-up before success.
- [x] Rejection tests through `nmcli`: newline in an `awg-*` value, key outside the allowlist, a wg-quick hook key in `vpn.data` (e.g. `awg-postup`) → `Connect` is rejected, the core was not started.
- [x] Enable the suite in CI on every pull request alongside the Hysteria2 suite.

## Risks and notes
- Parsing `.conf` (a single `[Peer]`, dropping wg-quick hooks) is milestone 6.6; here the profile is defined by `.nmconnection` fields. The `/1`+`/1` normalization is not a parser feature: it lives in the 2.2 library, so a profile written by hand with the split pair behaves like one with `0.0.0.0/0`.
- The liveness check (handshake, 5.4), reconnection, network changes and the kill switch are stage 5.
- The mapping rules for the MVP are already decided in design.md; IPv6 in the tunnel is phase 2, and skipping IPv6 entries will be revisited then.
- Results:
  - The mapping is one pure function, `pnv_ip4_plan()` (`common/daemon/ip4plan.c`). It takes the tunnel's own routes (a protocol hook: AmneziaWG `allowed-ips`, none for the proxy cores), the profile's never-default and `dns`, and returns:
    - the default-route flag, which the 2.6 guard now also reads;
    - `NEVER_DEFAULT`, for a narrow AmneziaWG tunnel or one with never-default;
    - the routes, never `0.0.0.0/0`, plus /32 routes to explicit DNS servers when the tunnel is not a default-route one;
    - the DNS list.
  - The split `0.0.0.0/1` + `128.0.0.0/1` is normalized by the 2.2 validator before the flag is computed. `mtu` goes to Config only when the profile sets it.
  - IPv6 entries in `address` and `allowed-ips` are skipped and counted (`pnv_parse_cidr_list_v4`); the daemon logs them, and also the IPv4 addresses after the first. A list left empty is “missing”.
  - Unit tests: `tests/unit/test_ip4plan.c` (11 mapping cases: proxy and AmneziaWG, `0.0.0.0/0` and the split with and without never-default, narrow lists with and without `dns`, an extra route next to `0.0.0.0/0`) and the IPv6 cases in `test_awg_profile.c`.
  - Integration: `tests/integration/cases/test_41_awg_routes.py`, 9 cases on the bench:
    - the default-route tunnel for both `0.0.0.0/0` and the split: default via `pnv-…`, the /32 to the server via `stand-cli` (it wins over `allowed-ips` that include the server), DNS 1.1.1.1 and 9.9.9.9, guard chains, traffic;
    - leaks;
    - never-default and narrow `allowed-ips`, with and without `dns=203.0.113.1`;
    - `kill -9` of the core before success, with no socket left;
    - up again after `kill -9` of the daemon;
    - rejections through `nmcli` (a newline in `awg-jc`, `awg-foo`, `awg-postup`).
  - Deliberate breakage: no routes in `Ip4Config` → the narrow case fails.
  - The suite runs in the same CI job as Hysteria2 (all of `tests/integration/cases`).
  - CI stability. Four test-side races showed up only in CI and were fixed in the shared helpers, after which three runs of one commit were green in both DNS modes (64 passed each):
    - a late inbound packet from an earlier session's server counted as a leak; leak captures are now outbound only (`tcpdump -Q out`);
    - NM listing the tunnel device a moment after the activation; `ip4_dns()` waits for it;
    - background queries from apt in the no-DNS-query case; only bench names count;
    - systemd-resolved applying a new link's DNS a moment later; `fetch()` retries HTTP for up to 15 s.
