# 5.2 Inherited block and takeover

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.1, 0.7 · **Needed for:** 5.3, 5.4

## Goal
Kill switch chains left over from an earlier successful session survive a new attempt that fails or is disconnected, and go away only with a successful connect, `--clear` (5.3) or a reboot. Re-activating a profile that is up never opens a window without its chains and shows no banner. Apart from the short-lived “handing over” entry written here, `guard-status` entries for these cases are written in 5.3.

## Inputs
- The kill switch chains, the versioned run-directory format with the success and takeover markers, explicit-disconnect detection, the give-up flag, the disconnect rules and the shared marker function from 5.1; orphan cleanup that places the takeover marker and waits for a still-active previous instance from 2.3; the cache read function (ignores a file stored for another `server` value) from 2.4; the test-build hook that holds the daemon before `Ip4Config` from 2.7.
- The 0.7 finding on re-activation, recorded in design.md: the order of the old instance's `Disconnect` and the new instance's `Connect`, the deactivation reason the old instance sees, and which re-activation signal arrives in time (the libnm check of the old instance, the takeover marker of the new one, or both). At least one must; if 0.7 recorded neither, the design is changed before this milestone starts (go/no-go).
- [design.md](../design.md), section “Leak protection”: items “Kill switch lifecycle”, “Re-activation”, “Inherited block”; sections “Route to the server” (the cached server IP while this profile's chains remain), “Core supervision and cleanup” (items “On `Connect`, in this order”, “`--daemon-gone <uuid>`”).

## Tasks
- [ ] The inherited-block and “handed over” markers, in the 5.1 run-directory format.
- [ ] Inherited path on `Connect`: after orphan cleanup, the daemon looks for this profile's kill switch chains. If they exist, the attempt installs no kill switch chains of its own (the DNS and IPv6 guard chains as usual), places the inherited marker and works under the inherited chains.
- [ ] Cache rules for an inherited attempt: the server name is not resolved (DNS is blocked and would bypass the tunnel); the cached server IP is used right away, an IP literal in `server` directly. No usable cache (missing, aged out, or stored for a different `server` value) → `Connect` fails with the reason in the journal, and the inherited chains stay. As for any session, the cache is written only on success.
- [ ] On success: the inherited chains are replaced by this session's chains in one nftables transaction (same names), or removed if the profile no longer qualifies (`kill-switch=no` or never-default); the inherited marker is dropped.
- [ ] Re-activation detection by the old instance, in the disconnect handler before it decides on its chains: it asks libnm (`NMClient`) whether another active connection of the same profile UUID exists besides its own (activating or activated), and checks for the takeover marker that the new instance places in the run directory (2.3). Either signal means a re-activation; the journal names which one fired. Both are implemented; the 0.7 finding says which one the tests can rely on.
- [ ] Disconnect rules in front of those of 5.1, first match wins:
  1. inherited marker present → the chains remain, whatever the reason, explicit disconnect included;
  2. re-activation and the success marker → the chains remain, whatever the reason;
  3. otherwise the 5.1 rules; a re-activation of a session that never succeeded removes its chains, and the new instance starts fresh.
- [ ] Hand-over: when the old instance keeps its chains for a re-activation (rule 2, or rule 1 with a re-activation), it still stops the core, deletes the TUN, removes the guard chains and stops the guard unit, and deletes the core config with its secrets from the run directory, but instead of deleting the directory leaves it holding only the markers, the “handed over” marker added, and writes a `guard-status` entry for the UUID in the `handing-over` state with a timestamp.
- [ ] A first `guard-status` writer in the shared library for that entry: under a lock, atomic replace (temporary file, then rename), other entries kept as they are; 5.3 fixes the full format and adds the other entries.
- [ ] The new instance's orphan cleanup finds the handed-over run directory (or its own takeover marker) and takes the inherited path as a takeover, even if it never saw the old instance active. When it adopts the chains it removes the `handing-over` entry and writes none of its own; a regular entry appears only if the new attempt ends without success (5.3).
- [ ] The shared marker function (`--daemon-gone`, orphan cleanup) keeps the kill switch chains if the success or the inherited marker is present; a takeover marker alone keeps nothing, and together with a kept block it means that no `blocked` entry is written (5.3), because the new instance owns the chains: `--daemon-gone` (a crash during a re-activation) writes a `handing-over` entry with a timestamp instead, so that the block becomes visible after 30 s if the new instance does not adopt it, and orphan cleanup writes none. A “handed over” marker: `--daemon-gone` (run by the old guard unit as it stops) leaves the chains, the run directory and the `handing-over` entry for the new instance and writes no entry of its own; orphan cleanup treats the directory as a takeover, then deletes it.
- [ ] Two test-build hooks for the new instance's `Connect`: an exit hook that makes it exit right after it has placed its takeover marker, without the 2.3 marker removal, so that the hand-over happens whichever signal 0.7 found reliable but no new instance follows; and a delay hook that holds it before orphan cleanup until the old instance's scope is gone, so that it really never sees the old instance and places no takeover marker.
- [ ] Manual check in the VM for Hysteria2, AmneziaWG and VLESS XHTTP Reality (CI tests are 5.7).

## Deliverables
- The inherited-block and “handed over” markers, the inherited path with its cache rules, the atomic swap, re-activation detection with the hand-over and its `handing-over` entry, and the extended marker function in `plasma-nm-vpn-common`.

## Done when
In these checks, “fails before ACTIVATED” means the core unit drop-in from 5.1 or, in the test build, the 2.7 hold hook followed by `kill -9` of the core; a stopped bench server is detected only from 5.4 on.
- [ ] Leftover chains from a successful session (`kill -9` of the daemon after success), then `nmcli connection up` → a loop of `nft list chain` sees no second set of kill switch chains, the capture has no DNS query bypassing the tunnel, it connects via the cached server IP, `nft monitor` shows the swap as one transaction, no inherited marker remains.
- [ ] The same with the cache file deleted, or with `server` changed in the profile → `nmcli connection up` fails right away, the chains stay, the reason is in the journal. With the profile switched to `kill-switch=no` → a successful connect removes the chains.
- [ ] Leftover chains, then an attempt that fails before ACTIVATED, an attempt held by the hook and ended with `nmcli connection down`, and one ended with `kill -9` of its daemon → the chains are still in place after each.
- [ ] After success, `nmcli connection up` of the same profile while it is up → a loop of `nft list chain` during the switch sees the kill switch chains every time; afterwards the new session owns them, no inherited or handed-over marker remains, and no sample shows a visible entry: any `handing-over` entry is younger than 30 s and disappears within the adoption; the old instance's journal names the re-activation signal, one of the signals 0.7 lists.
- [ ] Hand-over without the new instance seeing the old one, only if 0.7 found the libnm check reliable (otherwise this check is skipped and the skip is recorded next to the 0.7 finding in design.md): after success, `nmcli connection up` of the same profile with the delay hook → no takeover marker is placed, the old instance's journal names libnm as the signal, the old run directory holds only markers (no core config) and remains with the “handed over” marker until the new instance's orphan cleanup, which adopts the chains as a takeover and removes the `handing-over` entry.
- [ ] Hand-over whose new instance never starts (the exit hook above: it exits after placing its takeover marker) → the chains, the handed-over run directory and the `handing-over` entry remain; 30 s after its timestamp the entry counts as a block (the 6.2 banner rule, checked here by the timestamp).
- [ ] A session held by the 2.7 hook before `Ip4Config` (not succeeded; the hook waits without blocking the daemon's main loop, so the held instance still handles `Disconnect`) re-activated with `nmcli connection up` → the old instance removes its chains, the new attempt installs its own and places no inherited marker; if that attempt fails before ACTIVATED too, no chains remain.

## Risks and notes
- A handed-over run directory whose new instance never reaches `Connect` keeps the chains; its `handing-over` entry is shown by the banner (6.2) as a block once it is 30 s old, so the user is not left without a hint. The next `Connect` of the profile adopts it as a takeover (a regular entry appears only if that attempt fails), `--clear` (5.3) removes it, and so does a reboot.
- An inherited block kept after an explicit disconnect goes away only with a successful connect, `--clear` (5.3) or a reboot. Example: the server changed its IP while the cached IP is used; this case is tested in 5.7, once the liveness check exists.
