# 0.6 xray TUN

**Stage:** 0 · **Duration:** 1 d · **Depends on:** 0.3 · **Needed for:** 4.1, 4.2

## Goal
Make sure that the built-in TUN inbound of the pinned xray version is fit for the product: with the default route through the TUN there is no loop, TCP and UDP (DNS) pass through VLESS XHTTP Reality, and xray attaches to an existing persistent TUN, so that a core restart keeps NM's routes. Otherwise VLESS would need a different scheme (for example, xray as a SOCKS bridge behind a sing-box TUN), and we need to know this before stage 4.

## Inputs
- The bench from 0.3 (VLESS XHTTP Reality server at 198.51.100.1:443, the “internet” 203.0.113.1 with HTTP and DNS).
- [design.md](../design.md), section “Research findings”, row “Xray TUN inbound on Linux?”: TUN since January 2026, its own stack since v26.10.10, issue 6412 fixed in v26.10.21.
- [design.md](../design.md), section “Routing, DNS and IPv6”, subsection “Route to the server”: NM sets the /32 to the server; the second line of defense is an explicit `sockopt.interface`. Subsection “Network changes and sleep”, item “The TUN belongs to the daemon, not to the core”.
- The findings of 0.4 on attaching to a persistent TUN (flags, readiness signal), if 0.4 is already done.

## Tasks
- [ ] Take the xray version that is planned to be pinned (in design.md the package is `0.1.0+xray26.11.9`; v26.10.21 or later), verify the sha256 against `.dgst`; record the version.
- [ ] Client config: a TUN inbound named `pnv-1a2b3c4d` with no routes (keys per the README of the TUN module in this version), a VLESS XHTTP Reality outbound to the bench with `sockopt.interface: stand-cli`, routing: everything from the TUN to this outbound.
- [ ] Create `pnv-1a2b3c4d` beforehand as a persistent TUN owned by `plasma-nm-vpn` (as in 0.4; as root if 0.4 is not done yet). Run xray as the unit `plasma-nm-vpn-core-<uuid>` from 0.4 (if 0.4 is not done yet, as root) and manually repeat what NM will do: address 198.18.0.1/30 on the TUN; `ip route add 198.51.100.1/32 via 192.0.2.1 dev stand-cli`; a default route through `pnv-1a2b3c4d` with a lower metric than `stand-cli`.
- [ ] Traffic: `curl http://203.0.113.1/` (TCP), `dig @203.0.113.1 stand.test` (UDP), `dig +tcp @203.0.113.1 stand.test`; download a file of a few MB.
- [ ] Loop: during the checks, `tcpdump -ni stand-cli` sees only TCP to 198.51.100.1:443, and `tcpdump -ni pnv-1a2b3c4d` sees no packets to 198.51.100.1. xray's CPU usage drops back to zero after the checks.
- [ ] Experiment without the /32: delete the route to 198.51.100.1 and reconnect. Record whether `sockopt.interface` keeps the core's connection on `stand-cli` or a loop appears. Restore the route.
- [ ] Core restart with the default route through the TUN: stop the xray unit, wait a few seconds, start it again → the TUN, its address and the default route stay (`ip monitor route` shows no removal), during the gap `tcpdump -ni stand-cli` sees no traffic to 203.0.113.1 (a `curl` loop runs throughout), and after the start traffic flows again with no further setup.
- [ ] Record how UDP over VLESS XHTTP is configured (which parameters were needed) and how xray behaves when the TUN address is set not by xray itself but by external code (as NM will do).
- [ ] Save the working config in `proto/0.6/` as a reference for 4.1.
- [ ] Update design.md: close the second “Verify on a prototype (stage 0)” item in “Open questions and risks”; in “Research findings”, in the row about Xray TUN, add the tested version and the outcome of the experiment without the /32. Close the xray part of the fourth item (persistent TUN) and record the outcome in “Network changes and sleep”; if xray cannot attach, record that the temporary block chain fallback applies to it.

## Deliverables

## Done when
- [ ] With the default route through the TUN, `curl http://203.0.113.1/` → the bench page; there is no direct traffic to 203.0.113.1 on `stand-cli`.
- [ ] `dig @203.0.113.1 stand.test` → answer 203.0.113.1; the query is visible on `pnv-1a2b3c4d` and not visible on `stand-cli`.
- [ ] No signs of a loop (see the tcpdump check and the CPU usage).
- [ ] Restarting the xray unit on the persistent TUN keeps the address and the default route, nothing goes to 203.0.113.1 via `stand-cli` during the gap, and traffic resumes; or the failure to attach is recorded in design.md.

## Risks and notes
- According to its README, the xray TUN module is still meant for advanced users and is changing. If UDP does not pass or there is a loop, first try the next stable version; if that does not help, record it in design.md and bring the decision (for example, a SOCKS bridge behind a sing-box TUN, as other clients do) up for discussion before stage 4.
- Interface auto-detection is not used at all (design.md): `sockopt.interface` is always set explicitly. The issue 6412 fix does not need to be rechecked.
- IPv6 inside the tunnel is not needed (phase 2).
