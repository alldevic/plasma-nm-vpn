# 0.7 Minimal NM plugin

**Stage:** 0 · **Duration:** 2 d · **Depends on:** 0.3, 0.4, 0.5 · **Needed for:** 1.4, 2.1, 2.4, 5.2, 5.5

## Goal
Test on a live NetworkManager the whole chain the daemon design rests on: NM starts a daemon based on `NMVpnServicePlugin`, the daemon brings up sing-box and hands over Config and `Ip4Config`, and NM itself sets the address, routes, the route to the gateway and DNS. Separately, test the reconnect cycle via `STARTING`, without which DNS is not updated after a network change, moving the real plugin out of the NetworkManager cgroup into its own scope, and what the plugin sees when NM deactivates the VPN: an explicit disconnect versus an NM restart or a re-activation of the same profile.

## Inputs
- The bench from 0.3 (hysteria2 at 198.51.100.1:443, `stand-cli` under NM, tunnel DNS 203.0.113.1), running sing-box as `plasma-nm-vpn` from 0.4, the persistent TUN and the readiness signal from 0.4, the scope, the guard unit and the core unit (`BindsTo=`, `LoadCredential=`, plain `ExecStop` as root, core `After=` the guard unit) from 0.5.
- [design.md](../design.md), section “Architecture”: the daemon language, “Core lifetime is bound to the daemon”, “The daemon reports the TUN name to NM”, “Names must match”, “Service names follow the protocol, not the core”.
- [design.md](../design.md), section “Routing, DNS and IPv6”: subsections “Route to the server”, “TUN addressing”, “Network changes and sleep” (NM 1.58.1 behavior, from the sources); in “Leak protection”, item “Kill switch lifecycle” (an explicit disconnect is `NM_ACTIVE_CONNECTION_STATE_REASON_USER_DISCONNECTED` or a deleted profile, `CONNECTION_REMOVED`; NM's behavior on `systemctl restart NetworkManager` is verified here) and item “Re-activation” (two signals: the old instance asks libnm whether another activation of the same profile exists, and the new instance places a takeover marker; either one means a re-activation, this milestone records which arrives in time, and at least one must).
- [design.md](../design.md), section “Core supervision and cleanup”: items “On `Connect`, in this order” and “Disconnect” (synchronous, finished before the `disconnect` handler returns).
- Reference: NetworkManager-openvpn — `nm-openvpn-service.name.in`, `nm-openvpn-service.conf` (D-Bus policy), `src/nm-openvpn-service.c` (parsing `--bus-name`).

## Risks and notes
- Without `gateway`, NM aborts activation — this is already known from design.md; always pass it.
- According to the NM 1.58.1 sources (`src/core/vpn/nm-vpn-connection.c`), the `STARTED` → `STARTING` transition puts the connection into the connecting state, and DNS is applied only on entering ACTIVATED. The prototype confirms this on the NM version from the VM; the sources are not studied again.
- If the plugin cannot tell an NM restart from an explicit disconnect (for example, the same reason or no reason at all), the kill switch would drop its block on every NM restart: record it and raise a design change before 5.1; 5.6 tests “NM restart keeps the block”.
- The re-activation result is a hard gate: 5.2 (inherited block and takeover) builds on whichever signal is recorded here. Go needs at least one signal in every run; if each signal shows up only in some runs but together they cover all of them, 5.2 checks both, and a run with neither is a no-go.
- Resolving the name, choosing a subnet from the pool and binding to the parent device from NM are tasks for 2.4; here everything is hard-coded.
- The prototype is the temporary payload for the first CI test in 1.4 (it moves to `tests/integration/smoke/`) and is removed in 2.7; it does not go into the product. Keep it buildable until 1.4.
- Results (`proto/0.7/*.log`; design.md “Kill switch lifecycle”, “Re-activation”, “Network changes and sleep”, “Disconnect”, “Decide before 5.2”): the whole chain works on NM 1.58.1 — `--bus-name …Connection_<N>`, the daemon in its own scope, NM sets the address, the /32 via `stand-cli`, the default route and DNS; the `STARTING` cycle keeps the routes and the TUN (same ifindex) and applies a new DNS list, but so does resending without `STARTING`. Explicit reasons arrive before `Disconnect` (15 of 15), an NM restart gives `Disconnect` without a reason (3 of 3). Re-activation of an active VPN profile does not exist in NM 1.58.1; the down/up overlap had no signal in 1 of 26 runs, so the 5.2 go/no-go is no-go and a design change is proposed in design.md.
