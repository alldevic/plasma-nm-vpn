# 4.2 xray daemon and tests

**Stage:** 4 · **Duration:** 2 d · **Depends on:** 4.1 · **Needed for:** 5.1, 6.4

## Goal
The `plasma-nm-vpn-xray` daemon on the shared library brings up VLESS XHTTP Reality through `nmcli`, and integration tests in CI confirm this, including UDP (DNS) through the tunnel. After this milestone all three MVP protocols work through `.nmconnection` and `nmcli`.

## Inputs
- The config generator, allowlists and value lists (TLS fingerprints, XHTTP modes) from 4.1; shared library 2.1–2.6 (D-Bus, `need_secrets`, launching the core in a unit, network parameters, DNS and IPv6 guard); test suites 2.7 and 3.2 as a reference.
- The VLESS XHTTP Reality server on xray in the 0.3 test bench and the integration test bench in CI from 1.4.
- [design.md](../design.md), sections “Architecture”, “Profile data schema”, “Route to the server”, “Core supervision and cleanup”, “Testing”.

## Tasks
- [ ] The daemon binary `/usr/lib/plasma-nm-vpn/plasma-nm-vpn-service-xray` on `plasma-nm-vpn-common`; `.name` with `service=org.freedesktop.NetworkManager.pnv.vless`, `program` set to that path, `supports-multiple-connections=true` and the D-Bus policy (`own_prefix` on this name), following 2.1. The service-type, the D-Bus name and (later, in 6.4) `X-NetworkManager-Services` match.
- [ ] Validation of the protocol fields with the 2.2 validators: `encryption` (`none` or an ML-KEM key; check the format against the xray documentation), `reality-pbk`, `reality-sid`, `reality-spx`, `tls-sni`, `tls-fingerprint` and `xhttp-mode` (against the 4.1 value lists, not lists in code), `xhttp-path`, `xhttp-host`, `xhttp-extra`.
- [ ] `need_secrets`: the only secret is `uuid`; without it the daemon requests it from NM.
- [ ] Launch through the shared `Connect` sequence of 2.3, 2.4 and 2.6 (orphan cleanup, run directory, daemon scope, guard unit `plasma-nm-vpn-guard-<uuid>.service` with `/usr/bin/plasma-nm-vpn-guard --daemon-gone <uuid>`, server name resolution with a 5 s timeout, the persistent TUN, guard chains), then the unit `plasma-nm-vpn-core-<uuid>.service` with the binary `/usr/lib/plasma-nm-vpn/bin/xray`, user `plasma-nm-vpn`, `CAP_NET_ADMIN CAP_NET_RAW`, sandboxing, config from `/run/plasma-nm-vpn/<uuid>/` via `LoadCredential=`, `BindsTo=` on the daemon's scope and `After=` the guard unit; the server IP chosen by 2.4 and the parent device are passed to the generator.
- [ ] Readiness: xray has attached to the persistent TUN `pnv-…` (netlink) within the allotted time, 15 s by default; then Config (`TUNDEV`, external gateway, `CAN_PERSIST`) and `Ip4Config` from 2.4. NM brings the interface up after `Ip4Config`.
- [ ] The `plasma-nm-vpn-xray` package (version `0.1.0+xray<version>`): core, daemon, `.name`, template and allowlists from 4.1.
- [ ] Integration tests following 2.7, with profile parameters from the test bench:
  - connecting with `nmcli connection up` and TCP traffic passing;
  - UDP: a DNS query (e.g. `dig`) to the DNS server from the profile goes through the tunnel and gets a response; the DNS in the test profile is the bench DNS 203.0.113.1, as in 2.7 (later the liveness check target, 5.4); in both DNS modes;
  - no DNS and IPv6 leaks (capture on the physical interface);
  - cleanup after `nmcli connection down` and `kill -9` of the daemon: no unit, processes, TUN, routes, nftables chains of the connection or `/run/plasma-nm-vpn/<uuid>/` remain (after `kill -9` of the daemon the persistent TUN and the run directory are removed by `--daemon-gone` from the guard unit);
  - `kill -9` of the core: as in 2.7, the daemon gives up and no traces remain; from 5.5 the behaviour after success is recovery, and 5.5 marks the after-success case as an expected failure and 5.6 updates this test to recovery after success and give-up before success;
  - the core runs as `plasma-nm-vpn`, not as root;
  - attack vectors: paths in `extra` and `xhttp-extra`, newlines in fields: the profile is rejected, the core is not started.

## Deliverables
- The `plasma-nm-vpn-xray` daemon, `.name` and D-Bus policy in the `plasma-nm-vpn-xray` package.
- A VLESS XHTTP Reality integration test suite in CI.

## Done when
- [ ] `nmcli connection up` of a VLESS XHTTP Reality profile from the test bench → ACTIVATED, `pnv-…` has an address from 198.18.0.0/15, traffic goes through the test bench server.
- [ ] DNS query through the tunnel → a response is received, there are no packets to ports 53 and 853 on the physical interface.
- [ ] Profile without `uuid` in `vpn.secrets` → `need_secrets` returns `"vpn"` and NM issues `GetSecrets` (NM journal); with `nmcli connection up … passwd-file` it connects.
- [ ] xray integration test suite in CI → green.

## Risks and notes
- UDP through the xray TUN and VLESS XHTTP was verified in 0.6; if UDP does not pass in the test, first compare the config with the prototype rather than change the architecture.
- A loop is prevented by two lines of defense: NM's /32 route to the external gateway and the explicit `sockopt.interface`; both are already decided in design.md.
- The liveness check (a DNS query through the TUN, 5.4), network change and kill switch tests are not written here; they come in stage 5 (5.4, 5.6–5.8). The UDP test here is a precondition for the liveness check.
