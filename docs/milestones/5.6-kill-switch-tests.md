# 5.6 Kill switch tests

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.3, 5.5 · **Needed for:** 5.7

## Goal
Lock down the kill switch chains and their lifecycle in CI so that core and NM updates do not break them unnoticed, and bring the earlier 2.7, 3.2 and 4.2 suites in line with recovery after a core crash. The inherited block, re-activation, `--clear`, liveness detection and two simultaneous connections are tested in 5.7; network changes and sleep in 5.8.

## Inputs
- The kill switch chains, the success marker and explicit-disconnect detection from 5.1; the inherited path from 5.2 (used here only to end a block with a successful connect); `guard-status` from 5.3; the liveness check from 5.4; the reconnect cycle and the core-kill cases marked as expected failures from 5.5; the deactivation reasons recorded in 0.7; the test-build hook that holds the daemon before `Ip4Config` from 2.7.
- The integration test bench in CI (1.4) with the 0.3 additions: the “ISP” DNS on 192.0.2.1 with `srv.stand.test` (A and AAAA) and `srv6.stand.test` (AAAA only, 2001:db8:100::1), the IPv6 gateway 2001:db8:1::1 on `stand-cli`, the RFC 1918 neighbour 192.168.77.1, the bench DNS 203.0.113.1 behind the server (also answering on 1.1.1.1); the VM driven over `AF_VSOCK`; test suites 2.7, 3.2, 4.2 and their shared helpers; `needs: test-build` cases (1.4, 2.7).
- [design.md](../design.md), section “Leak protection” (items “Kill switch”, “Kill switch lifecycle”), sections “Core supervision and cleanup”, “Testing”.

## Tasks
- [ ] Test setup: profiles with `kill-switch=yes` that set `dns=203.0.113.1` before connecting (the 0.3 rule: 9.9.9.9 is unreachable on the bench, and 1.1.1.1 is kept for the never-default check of 5.7), with `server` as a bench name resolved via the “ISP” DNS; secrets via `nmcli connection up … passwd-file`; `tcpdump` on the parent device for the duration of each test; DNS in both modes (default `resolv.conf` and systemd-resolved). Tests with `allow-lan=no` rely on the vsock control channel; the management NIC is never disconnected.
- [ ] Update the core-kill cases of the 2.7, 3.2 and 4.2 suites and drop their expected-failure marks from 5.5: `kill -9` of the core after success → recovery (ACTIVATED again, the liveness check passes, no block, no teardown); before success → give-up and “no traces left”.
- [ ] “Daemon crash after success”: `kill -9` of the daemon → the kill switch chains are in place, the DNS and IPv6 guard chains, the TUN and `/run/plasma-nm-vpn/<uuid>/` are gone, `guard-status` shows the block, the capture has no direct traffic (except DHCP, DHCPv6, ND, MLD and local networks); the RFC 1918 neighbour is reachable over HTTP with `allow-lan=yes` and not with `allow-lan=no`. Then `nmcli connection up` → it connects, the block and its entry are gone (the details of the inherited path are 5.7).
- [ ] “LAN DNS rejected while blocked”: in that blocked state with `allow-lan=yes`, `dig @192.168.77.1` and a connection to port 853 there → rejected at once; the capture has no packets to ports 53 or 853 on the LAN.
- [ ] “IPv6-only server with the kill switch”: `server=srv6.stand.test`, so the core reaches the server over IPv6 → the tunnel stays up and passes traffic under a continuous `curl` for longer than the neighbour reachable time (at least 2 min), `ip -6 neigh` never shows the gateway 2001:db8:1::1 as `FAILED`, and the capture shows unicast NS and NA between 2001:db8:1::2 and 2001:db8:1::1 (not only to multicast). Then `kill -9` of the daemon → the block holds and no IPv6 other than ND and MLD leaves.
- [ ] “NM restart keeps the block”: after success, `systemctl restart NetworkManager` → the chains remain, `guard-status` shows the block, no direct traffic until a new successful connect.
- [ ] “Profile deleted”: after success, `nmcli connection delete` → counted as explicit: no chains, no entry. “Explicit disconnect”: after success, `nmcli connection down` → the same.
- [ ] “First connection failed” (failures that the liveness check does not decide; wrong secrets and dead servers are 5.7): the core unit failing before ACTIVATED (the 5.1 drop-in), and, in the test build, the 2.7 hold hook followed by `kill -9` of the daemon or of the core → give-up, no kill switch chains, no `guard-status` entry, no cache written, direct traffic flows.
- [ ] “No traces left” after an explicit disconnect after success and after `kill -9` of the daemon before success, including the run directory; kill switch chains and their `guard-status` entry remain only where the rules require them.
- [ ] Tests are parameterized by protocol (Hysteria2, AmneziaWG, VLESS XHTTP Reality) where this does not require separate code.

## Deliverables
- A kill switch integration test suite in CI; the 2.7, 3.2 and 4.2 suites updated for recovery after a core crash.

## Done when
- [ ] The suite and the updated 2.7, 3.2 and 4.2 suites in CI on a pull request → green for all three protocols and both DNS modes, with no expected-failure marks left.
- [ ] A deliberately broken kill switch rule (e.g. a removed reject) → the daemon crash test fails; a LAN exemption that also covers port 53 → the LAN DNS check fails; an ND exemption limited to link-local and multicast destinations → the IPv6-only server test fails.
- [ ] Treating every disconnect as explicit (ignoring the deactivation reason) → the NM restart test fails; treating every disconnect as a give-up → the profile-deleted test fails; keeping the chains of a session without the success marker → the first-connection-failed test fails.

## Risks and notes
- The deliberately broken variants in “Done when” are checked once by hand with a local patch, not with switches in the daemon; the only test hooks live in the never-packaged test build (`-DPNV_TEST_HOOKS=ON`).
- What NM does on `systemctl restart NetworkManager` was recorded in 0.7; if NM's behaviour differs from that record, fix the record before changing the daemon.
- NM's behaviour with `STARTING`, can-persist and a daemon crash has already been checked against the 1.58.1 sources; the tests check our code, not NM.
