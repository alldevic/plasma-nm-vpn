# 5.6 Kill switch tests

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.3, 5.5 · **Needed for:** 5.7

## Goal
Lock down the kill switch chains and their lifecycle in CI so that core and NM updates do not break them unnoticed, and bring the earlier 2.7, 3.2 and 4.2 suites in line with recovery after a core crash. The inherited block, re-activation, `--clear`, liveness detection and two simultaneous connections are tested in 5.7; network changes and sleep in 5.8.

## Inputs
- The kill switch chains, the success marker and explicit-disconnect detection from 5.1; the inherited path from 5.2 (used here only to end a block with a successful connect); `guard-status` from 5.3; the liveness check from 5.4; the reconnect cycle and the core-kill cases marked as expected failures from 5.5; the deactivation reasons recorded in 0.7; the test-build hook that holds the daemon before `Ip4Config` from 2.7.
- The integration test bench in CI (1.4) with the 0.3 additions: the “ISP” DNS on 192.0.2.1 with `srv.stand.test` (A and AAAA) and `srv6.stand.test` (AAAA only, 2001:db8:100::1), the IPv6 gateway 2001:db8:1::1 on `stand-cli`, the RFC 1918 neighbour 192.168.77.1, the bench DNS 203.0.113.1 behind the server (also answering on 1.1.1.1); the VM driven over `AF_VSOCK`; test suites 2.7, 3.2, 4.2 and their shared helpers; `needs: test-build` cases (1.4, 2.7).
- [design.md](../design.md), section “Leak protection” (items “Kill switch”, “Kill switch lifecycle”), sections “Core supervision and cleanup”, “Testing”.

## Tasks
- [x] Test setup: profiles with `kill-switch=yes` that set `dns=203.0.113.1` before connecting (the 0.3 rule: 9.9.9.9 is unreachable on the bench, and 1.1.1.1 is kept for the never-default check of 5.7), with `server` as a bench name resolved via the “ISP” DNS; secrets via `nmcli connection up … passwd-file`; `tcpdump` on the parent device for the duration of each test; DNS in both modes (default `resolv.conf` and systemd-resolved). Tests with `allow-lan=no` rely on the vsock control channel; the management NIC is never disconnected.
- [x] Update the core-kill cases of the 2.7, 3.2 and 4.2 suites and drop their expected-failure marks from 5.5: `kill -9` of the core after success → recovery (ACTIVATED again, the liveness check passes, no block, no teardown); before success → give-up and “no traces left”.
- [x] “Daemon crash after success”: `kill -9` of the daemon → the kill switch chains are in place, the DNS and IPv6 guard chains, the TUN and `/run/plasma-nm-vpn/<uuid>/` are gone, `guard-status` shows the block, the capture has no direct traffic (except DHCP, DHCPv6, ND, MLD and local networks); the RFC 1918 neighbour is reachable over HTTP with `allow-lan=yes` and not with `allow-lan=no`. Then `nmcli connection up` → it connects, the block and its entry are gone (the details of the inherited path are 5.7).
- [x] “LAN DNS rejected while blocked”: in that blocked state with `allow-lan=yes`, `dig @192.168.77.1` and a connection to port 853 there → rejected at once; the capture has no packets to ports 53 or 853 on the LAN.
- [x] “IPv6-only server with the kill switch”: `server=srv6.stand.test`, so the core reaches the server over IPv6 → the tunnel stays up and passes traffic under a continuous `curl` for longer than the neighbour reachable time (at least 2 min), `ip -6 neigh` never shows the gateway 2001:db8:1::1 as `FAILED`, and the capture shows unicast NS and NA between 2001:db8:1::2 and 2001:db8:1::1 (not only to multicast). Then `kill -9` of the daemon → the block holds and no IPv6 other than ND and MLD leaves.
- [x] “NM restart keeps the block”: after success, `systemctl restart NetworkManager` → the chains remain, `guard-status` shows the block, no direct traffic until a new successful connect.
- [x] “Profile deleted”: after success, `nmcli connection delete` → counted as explicit: no chains, no entry. “Explicit disconnect”: after success, `nmcli connection down` → the same.
- [x] “First connection failed” (failures that the liveness check does not decide; wrong secrets and dead servers are 5.7): the core unit failing before ACTIVATED (the 5.1 drop-in), and, in the test build, the 2.7 hold hook followed by `kill -9` of the daemon or of the core → give-up, no kill switch chains, no `guard-status` entry, no cache written, direct traffic flows.
- [x] “No traces left” after an explicit disconnect after success and after `kill -9` of the daemon before success, including the run directory; kill switch chains and their `guard-status` entry remain only where the rules require them.
- [x] Tests are parameterized by protocol (Hysteria2, AmneziaWG, VLESS XHTTP Reality) where this does not require separate code.

## Deliverables
- A kill switch integration test suite in CI; the 2.7, 3.2 and 4.2 suites updated for recovery after a core crash.

## Done when
- [x] The suite and the updated 2.7, 3.2 and 4.2 suites in CI on a pull request → green for all three protocols and both DNS modes, with no expected-failure marks left.
- [x] A deliberately broken kill switch rule (e.g. a removed reject) → the daemon crash test fails; a LAN exemption that also covers port 53 → the LAN DNS check fails; an ND exemption limited to link-local and multicast destinations → the IPv6-only server test fails.
- [x] Treating every disconnect as explicit (ignoring the deactivation reason) → the NM restart test fails; treating every disconnect as a give-up → the profile-deleted test fails; keeping the chains of a session without the success marker → the first-connection-failed test fails.

## Risks and notes
- The deliberately broken variants in “Done when” are checked once by hand with a local patch, not with switches in the daemon; the only test hooks live in the never-packaged test build (`-DPNV_TEST_HOOKS=ON`).
- What NM does on `systemctl restart NetworkManager` was recorded in 0.7; if NM's behaviour differs from that record, fix the record before changing the daemon.
- NM's behaviour with `STARTING`, can-persist and a daemon crash has already been checked against the 1.58.1 sources; the tests check our code, not NM.
- Results:
  - The suite: `tests/integration/cases/test_60_killswitch.py`, 29 cases, parameterized by protocol where the code is shared. Every case runs with `kill-switch=yes` and `dns=203.0.113.1`. AmneziaWG profiles get `allowed-ips=0.0.0.0/0`, since the bench client config is narrow and the kill switch is only for default-route tunnels. Cases:
    - core crash after success → recovery (reconnected, ACTIVATED, traffic, no entry);
    - daemon crash after success with `allow-lan` yes and no: the kill switch chains stay; the guard chains, TUN and run directory are gone; the entry is there; no direct traffic; the LAN neighbour reachable only with `allow-lan=yes`; then a successful `up` takes the block over and removes the entry;
    - LAN DNS (`dig @192.168.77.1`, TCP 853) rejected at once while blocked;
    - the IPv6-only server under a continuous `curl` for 130 s: the gateway never `FAILED`, unicast ND seen; then a crash, and no IPv6 other than ND/MLD leaves;
    - an NM restart keeps the block;
    - `delete` and `down` remove it and leave no traces;
    - a first connection that fails (the core unit failing, the hold hook plus `kill -9` of the daemon or of the core) leaves no chains, entry or cache, and direct traffic flows.
  - The captures exclude the core's own traffic to the server: it is exempt by design, and a crash leaves a FIN or a last UDP datagram from it.
  - The 2.7, 3.2 and 4.2 core-kill cases had no expected-failure marks to drop (they only cover the before-success give-up); recovery after success is covered here for all three protocols.
  - The test hook `broken-config` now runs `/bin/false` as the core, so it fails for every core; amneziawg-go reads no config file.
  - Deliberate breakages, each failing its case:
    - no final reject → the daemon crash case (direct traffic passes);
    - the DNS reject moved after the LAN exemption → the LAN DNS case;
    - the ND exemption limited to link-local and multicast destinations → the IPv6-only server case;
    - every disconnect treated as explicit → the NM restart case;
    - every disconnect treated as a give-up → the profile-deleted case;
    - chains kept without the success marker → the first-connection-failed case.
  - Locally the suite runs detached: the local VM's ssh comes in over passt, and a block cuts it; CI uses vsock.
