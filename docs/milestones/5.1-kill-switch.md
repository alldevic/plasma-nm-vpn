# 5.1 Kill switch chains

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 2.6, 4.2 · **Needed for:** 5.2, 5.3

## Goal
A kill switch from the profile (`kill-switch=yes`), for default-route tunnels only: while the session runs, traffic does not bypass the tunnel, and after a session has succeeded, everything except an explicit disconnect (a give-up, a daemon crash, NM going away) leaves the chains in place (fail closed). A session that never succeeded leaves no chains behind. Leftover chains, the inherited block and re-activation are milestone 5.2; the block status file, `--clear` and polkit are 5.3; the liveness check that completes the definition of success is 5.4; restarting a crashed core after success is 5.5.

## Inputs
- The `inet plasma_nm_vpn` table with per-UUID chains on the `output` and `forward` hooks and the core traffic exemption by user from 2.6; the `Connect` order, the guard unit with `/usr/bin/plasma-nm-vpn-guard --daemon-gone <uuid>`, the run directory `/run/plasma-nm-vpn/<uuid>/`, orphan cleanup and the takeover marker from 2.3; the server IP, the persistent TUN and the cache (server value + IP) from 2.4; the give-up function from 2.1; the deactivation reasons recorded in 0.7 (`down`, `delete`, NM restart); the test-build hook that holds the daemon before `Ip4Config` from 2.7; three daemons on the shared library (2.x, 3.x, 4.2).
- [design.md](../design.md), section “Leak protection”: items “Kill switch”, “When the chains are installed”, “Kill switch lifecycle”.
- [design.md](../design.md), sections “Route to the server”, “Core supervision and cleanup” (items “On `Connect`, in this order”, “Core unit failure”, “Disconnect”, “`--daemon-gone <uuid>`”), “Packages” (versioned marker format), “Testing” (VM driven over `AF_VSOCK`, test hooks only in the test build).

## Tasks
- [ ] Template of the kill switch chains in `/usr/share/plasma-nm-vpn/` (next to the 2.6 templates), with the profile UUID in their names, on the `output` and `forward` hooks. All outgoing traffic is rejected except loopback, all our tunnels (`oifname "pnv-*"`, not only this connection's TUN), DHCP, DHCPv6, ICMPv6 neighbour discovery (RS, NS, NA) to any address as in the 2.6 guard (the kernel also probes global addresses), MLD to multicast destinations, core traffic (`meta skuid plasma-nm-vpn`) and, with `allow-lan=yes`, local networks (RFC 1918, link-local). DNS is not part of the LAN exemption: ports 53 and 853 are rejected towards every non-tunnel destination, local networks included, so a blocked machine does not hand its queries to the LAN router. Defaults: `kill-switch=no`, `allow-lan=yes`.
- [ ] Only for default-route tunnels: with never-default the daemon ignores `kill-switch=yes` and says so in the journal (the editor side is 6.1–6.5).
- [ ] Installation in the `Connect` order of design.md: after the guard unit is running, the server name is resolved and the persistent TUN exists, together with the 2.6 guard chains, before the core unit and `Ip4Config`. The chains stay in place across reconnects.
- [ ] Session state in the run directory, with a versioned format (an upgrade does not touch running connections, so readers accept the previous version): the success marker, and the takeover marker of 2.3 moved into this format; 5.2 adds the inherited-block marker, 5.5 the session server IP. One library call marks success; in this milestone it runs on ACTIVATED for all three cores, and 5.4 moves it behind the liveness check. The same call writes the cache `/var/lib/plasma-nm-vpn/<uuid>` (the `server` value and the IP, refreshing the mtime); nothing writes it earlier.
- [ ] Explicit disconnect: the daemon watches its VPN active connection via libnm and records the deactivation reason. Only `NM_ACTIVE_CONNECTION_STATE_REASON_USER_DISCONNECTED` and `CONNECTION_REMOVED` (the profile was deleted) count as explicit; a vanished NM peer, an NM shutdown or restart, libnm's connect timer or an unknown reason count as a give-up. On a give-up the give-up flag is set before `nm_vpn_service_plugin_failure`, which itself calls the disconnect handler.
- [ ] The disconnect handler runs synchronously (libnm quits the main loop right after `STOPPED`): stops the core unit, deletes the persistent TUN, removes the DNS and IPv6 guard chains, then decides on the kill switch chains: success marker and explicit disconnect → removed; success marker and give-up → remain (fail closed); no success marker → removed, whatever ended the session. 5.2 adds the inherited and takeover rules in front of these. Then it deletes the run directory and stops the guard unit (its command then finds no run directory). `guard-status` is added in 5.3.
- [ ] Core unit failure: before success → give-up, the chains are removed. After success, until 5.5: give-up with the success marker, so the chains remain; 5.5 replaces this with the reconnect cycle.
- [ ] One marker function, shared by `--daemon-gone` and orphan cleanup (2.3), which processes a leftover run directory with it before deleting it. Extend `plasma-nm-vpn-guard --daemon-gone <uuid>` (2.6) with it: it acts only if the run directory still exists; removes the DNS and IPv6 guard chains; removes the kill switch chains unless the success marker is present; removes leftovers (core unit, persistent TUN, AmneziaWG UAPI socket); deletes the run directory. Recording the block in `guard-status` is 5.3; the inherited and takeover markers are added to the function in 5.2.
- [ ] Until 5.2, installing the chains replaces any leftover chains of this profile in one transaction (same names); 5.2 adds the inherited path for that case.
- [ ] Manual check in the VM for Hysteria2, AmneziaWG and VLESS XHTTP Reality (CI tests are 5.6 and 5.7). The VM is driven over `AF_VSOCK` (1.4), so the `allow-lan=no` checks do not cut the control channel; the management NIC is never disconnected.

## Deliverables
- The kill switch chain template; the versioned run-directory format with the success marker; explicit-disconnect detection and give-up handling in the shared library; the shared marker function and the kill switch part of `--daemon-gone` in `plasma-nm-vpn-common`.

## Done when
- [ ] After success, `kill -9` of the daemon → the kill switch chains remain, the DNS and IPv6 guard chains, the TUN and `/run/plasma-nm-vpn/<uuid>/` are gone; a capture on the physical interface shows no traffic bypassing the tunnel (except DHCP, DHCPv6, ND, MLD and local networks). The bench's RFC 1918 neighbour (0.3) is reachable over HTTP with `allow-lan=yes` and not with `allow-lan=no`.
- [ ] In that blocked state with `allow-lan=yes`, `dig @192.168.77.1` (the LAN neighbour as a router) and a DNS-over-TLS attempt on port 853 → rejected at once; the capture has no packets to ports 53 or 853 on the LAN.
- [ ] After success, `kill -9` of the core (until 5.5: give-up) or `systemctl restart NetworkManager` → the chains remain.
- [ ] After success, `nmcli connection down`, and separately `nmcli connection delete` → the profile has no chains.
- [ ] A first attempt that fails before ACTIVATED → no kill switch chains, no cache file, the network works directly. The failure is produced without the liveness check, which does not exist yet: the core unit failing to start (a drop-in, see below), and, in the test build, the 2.7 hook holding the daemon before `Ip4Config` followed by `kill -9` of the core, `kill -9` of the daemon or `nmcli connection down`. A stopped bench server or a wrong password is detected only from 5.4 on.
- [ ] A first-ever connect of a profile (no cache) while another profile's block rejects DNS → `nmcli connection up` fails right away, no core unit was started, no chains of this profile, the reason is in the journal.
- [ ] A default-route profile with the kill switch and a never-default profile with `kill-switch=yes` and a route to a bench address up at the same time → the second has no kill switch chains; traffic and DNS routed into either tunnel pass; one is disconnected → the other keeps working and keeps its chains.

## Risks and notes
- Check in the VM that the deactivation reason reaches the daemon via libnm before NM calls `Disconnect`. If it may arrive later, the handler waits for it briefly, with a bound, and a missing reason counts as a give-up (fail closed).
- Making the core fail before ACTIVATED: a drop-in for `plasma-nm-vpn-core-<uuid>.service` under `/run/systemd/system/<unit>.d/` (e.g. `ExecStartPre=/bin/false`), if drop-ins apply to transient units; otherwise only the 2.7 hold hook. Test hooks exist only in the test build (`-DPNV_TEST_HOOKS=ON`, 2.1), which is never packaged; nothing else for tests is added in this milestone.
- If upstream sing-box switches to running as root (a risk in design.md), the `meta skuid` exemption is replaced with a match on the unit's cgroup; not in this milestone.
