# 6.2 Kill switch banner

**Stage:** 6 · **Duration:** 1 d · **Depends on:** 6.1, 5.3, 5.5 · **Needed for:** 6.3–6.5

## Goal
NM's failure signal carries only a reason code, so the editor is where the user learns that a kill switch block has remained and clears it. This milestone builds the “Kill switch block active” banner as a shared widget, so that the 6.3–6.5 editors simply plug it in.

## Inputs
- The widget library, ki18n setup and QtTest scaffolding from 6.1.
- From 5.3: the `/run/plasma-nm-vpn/guard-status` file and its versioned format (state `blocked` or `handing-over`, timestamp); `plasma-nm-vpn-guard --clear [<uuid>]` with the behaviour fixed there (`--clear <uuid>` always removes that profile's kill switch chains and entry; a bare `--clear` does so for every profile except those whose VPN connection NM reports as activated or activating; refused authentication changes nothing and exits non-zero), which re-executes itself via `pkexec` when run by a regular user, and its polkit action.
- From 5.4: the liveness check timeout and its switch in the never-packaged test build of the daemons (design.md, “Testing”) that raises it, used below to hold an attempt open.
- From 5.5: the reconnect cycle and its timeout (a block produced by a give-up on the cycle timeout).
- [design.md](../design.md), section “Leak protection”: the kill switch lifecycle (inherited block, `--clear <uuid>` always clears that profile, a bare `--clear` skips profiles whose VPN connection NM reports as activated or activating) and the item “How the user learns about a block”.
- [design.md](../design.md), section “Core supervision and cleanup”: a core unit failure after success starts the reconnect cycle, so a block is left by a daemon crash after success or by a give-up on the cycle timeout, not by a core crash.
- [design.md](../design.md), section “Architecture”, item “Paths”: `guard-status` is world-readable.
- plasma-nm 6.7.4: `VpnUiPlugin::widget(const NetworkManager::VpnSetting::Ptr &setting, QWidget *parent)` in `libs/editor/vpnuiplugin.h` gets only the `vpn` setting, without the profile UUID.

## Tasks
- [x] A banner widget in the `plasma-nm-vpn-common` widget library, on `KMessageWidget` (warning type), with no plasma-nm internal API. Source strings in English, via ki18n.
- [x] On creation, read `guard-status` with a parser for the 5.3 format (checking its version); the banner is shown only if there are active blocks. `blocked` entries are blocks; a `handing-over` entry (a re-activation in progress) is hidden while it is younger than 30 s and shown as a block once older. A missing or empty file means no blocks; a malformed line or an unknown format version is skipped and does not crash the editor.
- [x] The editor does not know which profile it is editing, so the banner lists all active blocks with profile names, looked up by UUID via NetworkManagerQt (`NetworkManager::findConnectionByUuid`). A UUID without a profile (the profile was deleted) is shown as the UUID itself.
- [x] Clearing via `QProcess` without a shell; the tool re-executes itself via `pkexec`, so polkit asks for administrator credentials:
  - each entry has its own “Clear”, which runs `plasma-nm-vpn-guard --clear <uuid>` and, per 5.3, always clears that profile;
  - with more than one entry, “Clear all” runs a bare `plasma-nm-vpn-guard --clear`, which, per 5.3, skips profiles whose connection is activated or activating; such an entry stays in the list marked as connecting or connected (state via NetworkManagerQt).
- [x] After the process exits, re-read `guard-status` and refresh the banner. A non-zero exit (authentication refused or failed) leaves the banner as is and shows a short message.
- [x] Tests (QtTest, offscreen): the `guard-status` parser on sample files (empty, one block, several, malformed, unknown version, a `handing-over` entry younger and older than 30 s); the banner's visibility for each; the command lines passed to `QProcess` for an entry's “Clear” and for “Clear all” (with a stub instead of the real tool).

## Deliverables
- The kill switch banner widget and the `guard-status` parser in `plasma-nm-vpn-common`, with tests.

## Done when
- [x] Unit tests in CI → green.
- [x] In the VM, a test form with the banner (the real editors plug it in from 6.3): a profile with `kill-switch=yes` produces a block by `kill -9` of the daemon after success, or by stopping the bench server and waiting for the cycle timeout → the “Kill switch block active” banner shows the profile name.
- [x] “Clear” with the administrator password → the chains are removed, `guard-status` is empty, the banner disappears; with authentication refused → nothing changes, the banner stays.
- [x] Two blocked profiles, one of them activating again under its inherited block → “Clear all” during the attempt clears only the other one, the activating profile stays listed; its own “Clear” removes it. The attempt lasts until its liveness check gives up (5.4 timeout), which may be too short to act by hand, so this check holds it open: the server port of that profile is dropped in netns `stand` (the bench accepts the packets but answers nothing, not even with an ICMP error), and the daemon is the never-packaged test build with the liveness check timeout raised to 120 s through the 5.4 test switch. The test record states both.
- [x] No blocks → no banner. (The `handing-over` state is void: the 5.2 decision dropped it, so the daemons never write it, and the banner skips it like any unknown state.)

## Risks and notes
- The banner reads `guard-status` only when the form opens and after a clear; it does not watch the file. A block that appears while the form is open, or a `handing-over` entry that passes 30 s, is shown the next time it is opened.
- `widget()` cannot get the UUID of the profile being edited, so all blocks are listed; this is a design.md decision, not something to work around.
- `kill -9` of the core after success is not a way to produce a block: the daemon recovers the connection through the reconnect cycle (5.5).
- The editor is loaded by systemsettings, never as root; privileges come only through `pkexec` inside `plasma-nm-vpn-guard`.
- Results:
  - **Parser.** `pnvReadGuardStatus()` (`common/widgets/guardstatus.cpp`) reads the key file line by line, so a malformed line costs only itself. It skips groups that are not a UUID, have a version other than 1 or a missing one, or a state other than `blocked`. A missing, empty or unreadable file means no blocks. The `handing-over` state from 5.3's first plan is void after the 5.2 decision: nothing writes it, and the parser skips it as an unknown state.
  - **Banner.** `PnvKillSwitchBanner`, a warning `KMessageWidget` with no plasma-nm API.
    - It lists the profile names (escaped) or the UUID, the reason in words, the start time, and “(connecting)” or “(connected)” for a profile NM has up.
    - Actions: “Clear “name”” for each entry, and “Clear All” with more than one entry. The tool runs through `QProcess` without a shell. Afterwards the file is read again; a failure (non-zero exit, or the tool missing) keeps the entries and adds a short message.
    - A second constructor takes the file, the tool and the lookups, for tests.
    - The library now links KF6WidgetsAddons.
  - **Unit tests.** `tests/unit/widgets/test_banner.cpp`, 15 QtTest cases offscreen. They cover the parser on the samples, the banner's visibility for each, the names, the states and the escaping. With a stub for the tool they also cover the command lines of Clear and Clear All, the refresh after a clear, a refusal and a missing tool.
  - **VM check.** `tests/integration/cases/test_93_banner.py`, through a test form (`tests/integration/tools/banner-form.cpp`, test build only; `integration.yml` now builds the test build with the editors). The form runs offscreen as a regular user and drives the real banner over stdin.
    - Without blocks there is no banner.
    - A `kill -9` of a Hysteria2 daemon after success gives a banner with the profile name. Clear without a polkit rule (no agent answers) is refused: the chains and the entry stay, and the banner shows the message. With the rule standing in for the administrator's consent, Clear removes the chains and the entry, and the banner goes.
    - Two blocked profiles, Hysteria2 and VLESS; then VLESS connects again under its inherited block. Its attempt is held: TCP 443 is dropped in netns `stand`, and the test build's liveness check timeout is raised to 120 s via `/run/pnv-test-liveness-timeout` (5.4). “Clear All” then clears only the Hysteria2 block, the VLESS one stays listed as connected, and its own Clear removes it.
    - Found: NM shows the held attempt as activated, not activating: the VPN is ACTIVATED once NM has the `Ip4Config`, and the first liveness check, which decides success, comes after it (5.4). The bare `--clear` skips both states, so the result is the same; the check expects “(connected)”.
