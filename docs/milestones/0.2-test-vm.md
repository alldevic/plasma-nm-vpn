# 0.2 Test VM

**Stage:** 0 · **Duration:** 1 d · **Depends on:** — · **Needed for:** 0.3–0.9

## Goal
Get an isolated machine running the target platform (Debian forky, KDE Plasma 6) where we can break networking, install packages and run prototypes without touching the work machine. A snapshot of the clean state lets every experiment start from the same point.

## Inputs
- [design.md](../design.md), section “Goals and requirements”: the platform is Debian forky and KDE Plasma 6, amd64 only.
- [design.md](../design.md), section “Testing”: network experiments only in a test VM, in CI or on a separate hardware test machine, not on the work machine; the test VM is driven over `AF_VSOCK` (ssh via systemd-ssh-generator), not over IP; Wi-Fi in the VM is emulated with `mac80211_hwsim` and `hostapd`; sleep is a real `systemctl suspend` woken by `rtcwake`.
- On the host: libvirt and QEMU/KVM, `virsh`, `virt-install`, `passt`, `cloud-localds`; systemd 256 or later for `systemd-ssh-proxy` (ssh to `vsock/<cid>`).
- Decided for this host: the VM runs under `qemu:///session` with `passt` user networking, so no bridge, tap device or firewall rule appears on the host; ssh goes to `127.0.0.1:2222` (forwarded by passt) until vsock is available. vsock needs access to `/dev/vhost-vsock` (group `kvm`), which the host user does not have yet; adding the user to `kvm` is the user's step and is needed by stage 5 at the latest.

## Tasks
- [x] `proto/vm/create`: download the Debian forky cloud image (`debian-14-generic-amd64-daily.qcow2`, the `generic` flavour with the full kernel, so that `mac80211_hwsim` exists), verify it against `SHA512SUMS`, resize to 40 GiB, and create the VM `pnv-forky` with `virt-install --import`: amd64, 4 vCPUs, 6 GiB RAM (the host has about 8 GiB free), BIOS firmware (see “Risks” about snapshots and UEFI), S3 enabled (`--pm suspend_to_mem.enabled=on`, see the sleep task), a VNC display on 127.0.0.1 (this QEMU build has no SPICE), `passt` networking with the ssh port forward; an existing `pnv-forky` is replaced. A virtio vsock device is added once the host user can open `/dev/vhost-vsock`.
- [x] `proto/vm/user-data` (cloud-init): user `pnv` with `sudo` and the host's ssh key (password `pnv` for the Plasma login; test VM only), `task-kde-desktop` and `openssh-server`, then the tools below; graphical target; networking as on a desktop install (purge netplan, systemd-networkd and systemd-resolved, which the cloud image brings, so that NM manages the uplink and writes `/etc/resolv.conf`); cloud-init disabled after the first boot.
- [x] Between installing `task-kde-desktop` and the tools (cloud-init writes `/root/pkexec-stock.txt`), check whether the stock installation already has `pkexec` (`dpkg -s pkexec`, `command -v pkexec`) and which package pulled it in (`aptitude why pkexec` or `apt-cache rdepends --installed pkexec`). `pkexec` is a dependency of `plasma-nm-vpn-common` (design.md, section “Packages”); the answer tells whether it is a new dependency on users' machines. Record it in `versions.txt`.
- [x] Install the tools for stage 0 (check the package names in forky): `build-essential cmake pkgconf git`, `libnm-dev libglib2.0-dev libjson-glib-dev`, `qt6-base-dev extra-cmake-modules libkf6coreaddons-dev libkf6widgetsaddons-dev libkf6i18n-dev libkf6networkmanagerqt-dev`, `tcpdump bind9-dnsutils dnsmasq-base python3 curl openssl nftables iproute2 hostapd`, `dpkg-dev apt-utils gnupg`.
- [x] Make sure `plasma-nm` and NetworkManager are installed, and record the versions: `dpkg -l network-manager plasma-nm qt6-base-dev systemd apt nftables` → file `proto/vm/versions.txt` (for the prototype directory, see “Risks”).
- [x] Check that Wi-Fi emulation is possible at all in the VM's kernel: `modprobe mac80211_hwsim radios=2` → two `wlan*` interfaces appear; then `modprobe -r mac80211_hwsim`. Setting up an access point is a task for 5.5.
- [x] Sleep (design.md, “Testing”: a real `systemctl suspend` woken by `rtcwake`): check that the VM has an emulated RTC (`/dev/rtc0`); `rtcwake -m no -s 20 && systemctl suspend` → the VM sleeps and wakes by itself, `journalctl -b` shows logind's suspend and resume. Result: in s2idle (libvirt's default, S3 off) the RTC alarm fires but does not wake the guest — under ACPI, rtc_cmos wakes through the fixed RTC event, which QEMU raises only on wake from its own S3; only host input (`virsh send-key`) wakes it. With S3 enabled in libvirt and `MemorySleepMode=deep` in `/etc/systemd/sleep.conf.d/pnv.conf`, `rtcwake` wakes the VM. Recorded in `versions.txt` and design.md, section “Testing”; the CI image in 1.4 uses the same.
- [x] DNS mode: check that the installation is in Debian's default `resolv.conf` mode (systemd-resolved is not installed by default on a desktop; NM writes `/etc/resolv.conf`) and record it in `versions.txt`.
- [x] Shut down the VM and take a snapshot: `virsh snapshot-create-as pnv-forky clean "forky+KDE, stage 0 tools"`.
- [x] A second snapshot for the systemd-resolved variant (design.md, “Testing”: DNS is tested in both modes): from `clean`, `apt install systemd-resolved`, reboot, check that NM uses it (`resolvectl status`), shut down → snapshot `resolved`.
- [x] Script `proto/vm/vm-reset [clean|resolved]`: `virsh snapshot-revert pnv-forky <snapshot>` (default `clean`; with a forced power-off if needed — check the flags) and start the VM.
- [ ] ssh over `AF_VSOCK` (design.md, “Testing”; blocked until the host user is in `kvm`, see “Inputs”; until then experiments that touch the VM's uplink keep `virsh console` as the fallback): in the VM, systemd-ssh-generator binds `sshd` to vsock when a vsock device is present (check that forky's systemd does this by default; otherwise enable it explicitly); on the host, `ssh vsock/<cid>` via `systemd-ssh-proxy` with the key-based login. All later work drives the VM this way, so that disconnecting or firewalling the VM's IP interfaces never cuts the control channel. Transfer prototype code via `git`/`rsync` over this ssh, with no directories shared with the host.
- [x] Update design.md: in “Packages”, replace “whether a stock forky KDE install already has it is checked in milestone 0.2” with the result and the forky date.

## Risks and notes
- Internal qcow2 snapshots in libvirt may not be supported for VMs with UEFI (pflash). Hence BIOS; if UEFI is needed, check snapshot support in the installed libvirt version before installing the system.
- forky is testing and changes every day. The snapshot pins the versions; update the VM deliberately, with a new snapshot and a new `versions.txt`. If NetworkManager in the VM is not 1.58.x, note it: the conclusions in design.md about NM behavior are based on the 1.58.1 sources.
- Stage 0 code lives in the `proto/` directory in `master` and is thrown away. Exceptions (plan.md): the 0.3 bench becomes the product test bench, and the 0.7 prototype temporarily serves as the payload for the CI test in 1.4 and is removed in 2.7.
- After an S3 resume the guest hangs at the final power-off step (filesystems are already synced); `vm-reset` forces the VM off anyway, and a snapshot is taken only after a clean poweroff without a prior suspend.
- There is no real Wi-Fi in the VM: for 5.5 and 5.8 it is emulated with `mac80211_hwsim` and `hostapd` and, if available, checked on a separate hardware test machine (over ssh, 7.2). Here we only check that the module loads.
