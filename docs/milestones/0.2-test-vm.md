# 0.2 Test VM

**Stage:** 0 · **Duration:** 1 d · **Depends on:** — · **Needed for:** 0.3–0.9

## Goal
Get an isolated machine running the target platform (Debian forky, KDE Plasma 6) where we can break networking, install packages and run prototypes without touching the work machine. A snapshot of the clean state lets every experiment start from the same point.

## Inputs
- [design.md](../design.md), section “Goals and requirements”: the platform is Debian forky and KDE Plasma 6, amd64 only.
- [design.md](../design.md), section “Testing”: network experiments only in a test VM, in CI or on a separate hardware test machine, not on the work machine; the test VM is driven over `AF_VSOCK` (ssh via systemd-ssh-generator), not over IP; Wi-Fi in the VM is emulated with `mac80211_hwsim` and `hostapd`; sleep is a real `systemctl suspend` in s2idle mode woken by `rtcwake`.
- On the host: libvirt and QEMU/KVM, `virsh`, `virt-install` (or virt-manager); systemd 256 or later for `systemd-ssh-proxy` (ssh to `vsock/<cid>`).

## Tasks
- [ ] Install libvirt/QEMU on the host if they are missing; the VM goes on the default libvirt network (NAT), with no bridges to the host's physical network.
- [ ] Download the Debian testing installer image (the debian-installer build for testing; check on debian.org where it currently lives) and verify its checksum.
- [ ] Create the VM `pnv-forky`: amd64, 4 vCPUs, 8 GiB RAM, a 40 GiB qcow2 disk, BIOS firmware (SeaBIOS) — see “Risks” about snapshots and UEFI; a SPICE display for working with Plasma; a virtio vsock device (`<vsock model='virtio'><cid auto='yes'/></vsock>`, or a fixed CID — record it).
- [ ] Install Debian with the KDE Plasma task in tasksel, a user with `sudo`, and `openssh-server`.
- [ ] Before installing anything else, check whether the stock installation already has `pkexec` (`dpkg -s pkexec`, `command -v pkexec`) and which package pulled it in (`aptitude why pkexec` or `apt-cache rdepends --installed pkexec`). `pkexec` is a dependency of `plasma-nm-vpn-common` (design.md, section “Packages”); the answer tells whether it is a new dependency on users' machines. Record it in `versions.txt`.
- [ ] Install the tools for stage 0 (check the package names in forky): `build-essential cmake pkgconf git`, `libnm-dev libglib2.0-dev libjson-glib-dev`, `qt6-base-dev extra-cmake-modules libkf6coreaddons-dev libkf6widgetsaddons-dev libkf6i18n-dev libkf6networkmanagerqt-dev`, `tcpdump bind9-dnsutils dnsmasq-base python3 curl openssl nftables iproute2 hostapd`, `dpkg-dev apt-utils gnupg`.
- [ ] Make sure `plasma-nm` and NetworkManager are installed, and record the versions: `dpkg -l network-manager plasma-nm qt6-base-dev systemd apt nftables` → file `proto/vm/versions.txt` (for the prototype directory, see “Risks”).
- [ ] Check that Wi-Fi emulation is possible at all in the VM's kernel: `modprobe mac80211_hwsim radios=2` → two `wlan*` interfaces appear; then `modprobe -r mac80211_hwsim`. Setting up an access point is a task for 5.5.
- [ ] Sleep (design.md, “Testing”: a real `systemctl suspend` in s2idle mode woken by `rtcwake`): force s2idle so the result does not depend on what the virtual firmware offers — either `mem_sleep_default=s2idle` on the kernel command line or `MemorySleepMode=s2idle` in a drop-in under `/etc/systemd/sleep.conf.d/` (pick one, record it; the CI image in 1.4 uses the same); check that `/sys/power/mem_sleep` shows `[s2idle]` as the selected mode and that the VM has an emulated RTC (`/dev/rtc0`); `rtcwake -m no -s 20 && systemctl suspend` → the VM sleeps and wakes by itself, `journalctl -b` shows logind's suspend and resume. If it does not work, record the limitation (and which libvirt/QEMU settings were tried) in `versions.txt` and design.md, section “Testing”.
- [ ] DNS mode: check that the installation is in Debian's default `resolv.conf` mode (systemd-resolved is not installed by default; NM writes `/etc/resolv.conf`) and record it in `versions.txt`.
- [ ] Shut down the VM and take a snapshot: `virsh snapshot-create-as pnv-forky clean "forky+KDE, stage 0 tools"`.
- [ ] A second snapshot for the systemd-resolved variant (design.md, “Testing”: DNS is tested in both modes): from `clean`, `apt install systemd-resolved`, reboot, check that NM uses it (`resolvectl status`), shut down → snapshot `resolved`.
- [ ] Script `proto/vm/vm-reset [clean|resolved]`: `virsh snapshot-revert pnv-forky <snapshot>` (default `clean`; with a forced power-off if needed — check the flags) and start the VM.
- [ ] ssh over `AF_VSOCK` (design.md, “Testing”): in the VM, systemd-ssh-generator binds `sshd` to vsock when a vsock device is present (check that forky's systemd does this by default; otherwise enable it explicitly); on the host, `ssh vsock/<cid>` via `systemd-ssh-proxy` with the key-based login. All later work drives the VM this way, so that disconnecting or firewalling the VM's IP interfaces never cuts the control channel. Transfer prototype code via `git`/`rsync` over this ssh, with no directories shared with the host.
- [ ] Update design.md: in “Packages”, replace “whether a stock forky KDE install already has it is checked in milestone 0.2” with the result and the forky date.

## Deliverables
- VM `pnv-forky` with the snapshots `clean` (`resolv.conf` mode) and `resolved` (systemd-resolved).
- `proto/vm/vm-reset` and `proto/vm/versions.txt` (versions of NetworkManager, plasma-nm, Qt, systemd and apt in the snapshot; whether `pkexec` is in the stock installation).
- The `pkexec` finding in design.md, section “Packages”.

## Done when
- [ ] In the VM, create a file in `/etc` and remove the `nftables` package → `proto/vm/vm-reset` → the VM boots, the file is gone, `nftables` is in place.
- [ ] Log in to a Plasma session → the network applet shows a connection, “System Settings → Connections” opens.
- [ ] `vm-reset resolved` → `resolvectl status` works and `/etc/resolv.conf` points to 127.0.0.53; `vm-reset` → no systemd-resolved, `/etc/resolv.conf` is written by NM.
- [ ] `ssh vsock/<cid>` from the host into the VM works without a password, and inside the VM `ss -a --vsock` shows the session on a vsock socket, not on TCP.
- [ ] `cat /sys/power/mem_sleep` shows `[s2idle]`; `rtcwake -m no -s 20 && systemctl suspend` → the VM resumes on its own within about 30 s and the vsock `ssh` works again, or the limitation is recorded.
- [ ] `versions.txt` and design.md, section “Packages”, state whether `pkexec` is present in a stock forky KDE installation.

## Risks and notes
- Internal qcow2 snapshots in libvirt may not be supported for VMs with UEFI (pflash). Hence BIOS; if UEFI is needed, check snapshot support in the installed libvirt version before installing the system.
- forky is testing and changes every day. The snapshot pins the versions; update the VM deliberately, with a new snapshot and a new `versions.txt`. If NetworkManager in the VM is not 1.58.x, note it: the conclusions in design.md about NM behavior are based on the 1.58.1 sources.
- Stage 0 code lives in the `proto` branch in the `proto/` directory and is thrown away. Exceptions (plan.md): the 0.3 bench becomes the product test bench, and the 0.7 prototype temporarily serves as the payload for the CI test in 1.4 and is removed in 2.7.
- There is no real Wi-Fi in the VM: for 5.5 and 5.8 it is emulated with `mac80211_hwsim` and `hostapd` and, if available, checked on a separate hardware test machine (over ssh, 7.2). Here we only check that the module loads.
