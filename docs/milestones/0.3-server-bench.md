# 0.3 Server bench

**Stage:** 0 · **Duration:** 2 d · **Depends on:** 0.2 · **Needed for:** 0.4, 0.6, 0.7, 1.4

## Goal
Have our own servers for all three MVP protocols in the VM, each brought up and stopped with a single command, together with the network around them that the tests need: an “ISP” DNS server, an IPv6 server address and a local network neighbour. Without them no core can be tested, and later the same bench is used by the integration tests in CI (1.4).

## Inputs
- The VM from 0.2.
- [design.md](../design.md), section “Testing”: servers in a network namespace (hysteria2 on sing-box, VLESS XHTTP Reality on xray, AmneziaWG on amneziawg-go); a directly reachable “ISP” DNS server with A and AAAA-only records for the server name, an IPv6 address of the server and an RFC 1918 neighbour for the `allow-lan` checks; test profiles use the bench DNS inside the tunnel; the VM is driven over `AF_VSOCK`, and its management NIC stays up with never-default, no automatic DNS and no IPv6, as the one deliberate exception to the bench address rules.
- [design.md](../design.md), section “Packages”, item “Where the cores come from”: sing-box 1.14.4, xray 26.11.9 (the pinned version, `0.1.0+xray26.11.9`), amneziawg-go `v3.1.20261116`, `awg` from amneziawg-tools `v3.1.20260812`.
- [design.md](../design.md), section “Core supervision and cleanup”, item “Liveness check”: a DNS query for the root zone to the profile's first DNS server, from a socket bound to the TUN; with never-default and no `dns`, to `1.1.1.1` the same way, with no route added.
- The vsock ssh access from 0.2.

## Tasks
**Topology.** No address is from RFC 1918 (otherwise `allow-lan` in 5.1 masks leaks), except the deliberate LAN neighbour, and none is from 198.18.0.0/15 (the TUN address pool). The VM's management NIC (libvirt NAT, in CI QEMU user networking) is the one deliberate exception: it keeps its RFC 1918 address but carries no default route, no DNS and no IPv6 (see the client-side task). Documentation ranges are used wherever possible; the AmneziaWG tunnel uses 100.64.0.0/24 (RFC 6598 shared address space), and the public 1.1.1.1 exists on the bench only behind the tunnel, for the liveness check of profiles without `dns` (above all the never-default one).

| What | Where | Address |
|-----|-----|-------|
| `stand-cli` (veth, the client's “physical” interface, managed by NM) | the VM's root namespace | 192.0.2.2/24, 2001:db8:1::2/64; gateway 192.0.2.1 and 2001:db8:1::1; LAN 192.168.77.2/24 |
| `stand-srv` (peer of `stand-cli`) and the “ISP” DNS :53 | netns `stand` | 192.0.2.1/24, 2001:db8:1::1/64; LAN neighbour 192.168.77.1/24 with HTTP :80 |
| server: hysteria2 UDP 443, VLESS TCP 443, AmneziaWG UDP 51820 | netns `stand`, on `lo` | 198.51.100.1/32, 2001:db8:100::1/128 |
| “the internet behind the tunnel”: HTTP :80 and DNS :53 (name `stand.test`, root zone) | netns `stand`, dummy `inet0` | 203.0.113.1/32, 2001:db8:113::1/128; DNS also on 1.1.1.1/32 |
| AmneziaWG tunnel | server / client | 100.64.0.1/24 / 100.64.0.2 |

The server is not on the client's subnet but behind a gateway: this way the /32 route to the server and the loops in 0.6 and 0.7 are tested as in a real network. In netns `stand`, an nftables rule drops packets to 203.0.113.0/24, 1.1.1.1 and 2001:db8:113::/48 arriving from `stand-srv`: the “internet” is reachable only through the tunnel, and direct traffic to it is a sign of a leak. The “ISP” DNS and the LAN neighbour are reachable directly, as at home.

- [x] Download sing-box and xray with sha256 verification; build amneziawg-go and `awg` from tags (Go in the VM, for the bench only). Binaries go in `/opt/pnv-proto/bin/`.
- [x] `proto/stand/stand-up`: netns, veth, addresses, dummy `inet0`, routing `sysctl` in the netns, the nftables rule; an HTTP server (for example, `python3 -m http.server`) on the “internet” and LAN addresses; two `dnsmasq` instances (from `dnsmasq-base`, without the system service), one per role below.
- [x] Tunnel-side DNS at 203.0.113.1: answers `stand.test` and a query for the root zone (`dig @203.0.113.1 . SOA` → NOERROR with an answer; for example, a local authoritative `.` zone in dnsmasq — check what works). It is the DNS server of every test profile through which names are resolved, and the target of the liveness check (5.4). The same instance also listens on 1.1.1.1: a never-default proxy profile without `dns` runs the liveness check against 1.1.1.1 from a socket bound to the TUN, with no route (design.md, item “Liveness check”). It also serves `srv.stand.test` and `srv6.stand.test` with the same records as the “ISP” DNS below: while a first default-route tunnel is up, the system resolver goes through that tunnel, so a second profile resolves its server name through the first tunnel. `/etc/netns/stand/resolv.conf` points to it, so the proxy servers resolve `stand.test` too.
- [x] “ISP” DNS at 192.0.2.1: `srv.stand.test` with A 198.51.100.1 and AAAA 2001:db8:100::1, and `srv6.stand.test` with AAAA 2001:db8:100::1 only; it does not know `stand.test`, so a name from the “internet” resolves only through the tunnel. Test profiles give the server by these names (resolution and the AAAA-only case are tested in 2.4 and 2.7).
- [x] The client side under NM (design.md, “Testing”): NM does not manage veth by default (udev rule `85-nm-unmanaged.rules`, except for names `eth[0-9]*`). Enable management (`nmcli device set stand-cli managed yes` or an NM config in the VM — check that it survives an NM restart) and create a profile `stand` with the manual addresses and gateways above and `ipv4.dns 192.0.2.1`. The VM's management NIC is not disconnected (the VM is driven over vsock, 0.2, and the NIC stays available for the harness); instead its NM profile is set to `ipv4.never-default yes`, `ipv4.ignore-auto-dns yes` and `ipv6.method disabled` (check the exact properties in forky's NM), so that `stand-cli` carries the only default route, the only system DNS (192.0.2.1) and the only IPv6. `stand-up` applies this and `stand-down` restores it. Leak checks capture on `stand-cli`; record in the README that the management NIC is the deliberate exception.
- [x] Keys and secrets are generated by the script on first run in `proto/stand/secrets/`: a self-signed hysteria2 certificate (`sing-box generate tls-keypair`, valid for `srv.stand.test` and `srv6.stand.test`), Reality keys (`xray x25519`), a UUID, passwords, AWG keys (`awg genkey`, `awg pubkey`).
- [x] Servers: `stand-up <hy2|vless|awg|all>` and `stand-down` (stops the processes, removes the netns, veth and the NM profile). All servers listen on both server addresses. hysteria2 with Salamander; Reality with `target` pointing to a local TLS server in the netns (check what works: `openssl s_server` with TLS 1.3 or something else); AmneziaWG: amneziawg-go + `awg setconf` with AWG 3.1 parameters.

## Risks and notes
- The bench is an exception to the rule “prototype code is thrown away” (plan.md): it becomes the product test bench and in 1.4 moves to `tests/integration/stand/`, where it is refined rather than rewritten. So the scripts are written carefully: bash and `ip`/`nft` with no VM-specific assumptions, a non-zero exit code on error, so that they also run in CI. Every tool used here goes into the CI image package list (1.4).
- Every test profile through which names are resolved, including imported ones, sets `dns=203.0.113.1` before connecting: with the defaults, 9.9.9.9 is unreachable on the bench and slows the resolver down with timeouts, and the tests want one known DNS server. The liveness check is not the reason: with the defaults it queries the first one, 1.1.1.1, which the bench answers. Profiles without `dns` exist on purpose: the NM-level check of the defaults (2.4) and the never-default liveness check against 1.1.1.1 (5.4).
- The Reality server may require a reachable `target`; if a local TLS server does not work, write down exactly what is needed and make do with whatever works in a closed network.
- hysteria2 port hopping is not set up here (it needs DNAT of a port range on the server); the bench is extended with it in 2.5.
- IPv6 on `stand-cli` is needed for the leak checks in 2.6; IPv6 inside the tunnel is not needed.
- 5.5 and 5.8 need a second path to the server — Wi-Fi via `mac80211_hwsim` and `hostapd` (design.md, “Testing”); the topology allows for it, but it is not built here.
- Results (details in `proto/stand/README.md`, section “Bench details that matter”): the cores come from `proto/stand/fetch-cores` (sing-box and xray by the sha256 digests GitHub reports for the release assets, amneziawg-go and `awg` built from the tag commits); both DNS servers are dnsmasq with `--auth-zone` (the root zone needs an auth zone of its own); the Reality target is a threaded Python TLS 1.3 server (`openssl s_server` is single-connection and slow on the first handshake); the netns has default routes into `inet0`, and routes to the client network use the server address as source; xray's `freedom` needs `finalRules` to reach the documentation ranges behind a server inbound; `stand-up` waits for IPv6 DAD on `stand-cli`; AWG has one peer per address family; the management NIC is ssh over passt until vsock (0.2) and stays reachable because the ssh peer is on its subnet.
