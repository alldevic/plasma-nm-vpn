# 0.5 Core lifetime

**Stage:** 0 · **Duration:** 1 d · **Depends on:** 0.4 · **Needed for:** 0.7, 2.3

## Goal
Verify the mechanism that guarantees nothing outlives the daemon: on `Connect` the daemon moves itself into a transient scope, and both the core unit and a guard unit are bound to it via `BindsTo=`. When the scope empties, systemd stops the core first (the core unit is ordered `After=` the guard unit), and then the guard unit's plain `ExecStop=` runs the cleanup as root. At the same time, verify `LoadCredential=` in a transient unit (nobody but the core reads the config).

## Inputs
- The core launch script, the persistent TUN step and the working sing-box config from 0.4; the bench from 0.3.
- [design.md](../design.md), section “Architecture”: items “Core launch” (unit `plasma-nm-vpn-core-<uuid>.service`, `LoadCredential=`), “Core lifetime is bound to the daemon” and “Paths” (`/run/plasma-nm-vpn/<uuid>/`, `/usr/bin/plasma-nm-vpn-guard`).
- [design.md](../design.md), section “Core supervision and cleanup”: the items “On `Connect`, in this order” (orphan cleanup waits until the scope, the guard unit and the core unit are all inactive, failed or gone; then the run directory, the scope and the guard unit `plasma-nm-vpn-guard-<uuid>.service` with `Type=oneshot`, `RemainAfterExit=yes`, `BindsTo=`/`After=` the scope, `ExecStop=/usr/bin/plasma-nm-vpn-guard --daemon-gone <uuid>` with no `+` prefix, because the unit has no `User=` and no sandbox; `CollectMode=inactive-or-failed`; the core unit `After=` the guard unit), “Disconnect”, “Daemon crash” and “`--daemon-gone <uuid>`”.
- [design.md](../design.md), section “Leak protection”: per-UUID chains in `inet plasma_nm_vpn`, hooks `output` and `forward`; item “When the chains are installed”.

## Tasks
- [x] The “daemon” is a shell script `proto/0.5/fake-daemon <uuid>`; starting it stands in for `Connect`. All systemd calls go over D-Bus (`busctl call org.freedesktop.systemd1 /org/freedesktop/systemd1 org.freedesktop.systemd1.Manager StartTransientUnit 'ssa(sv)a(sa(sv))' …`; check the signatures against the systemd D-Bus API documentation), the way the C code will make them, not via `systemd-run`. The script, in this order:
  1. waits, up to 10 s, until `plasma-nm-vpn-daemon-<uuid>.scope`, `plasma-nm-vpn-guard-<uuid>.service` and `plasma-nm-vpn-core-<uuid>.service` are all inactive, failed or gone (the orphan cleanup in 2.3 does the same), and exits with an error otherwise;
  2. creates `/run/plasma-nm-vpn/<uuid>/` (root, 0700), moves itself into `plasma-nm-vpn-daemon-<uuid>.scope` (`PIDs au 1 $$`) and starts the guard unit `plasma-nm-vpn-guard-<uuid>.service`: `Type=oneshot`, `RemainAfterExit=yes`, `BindsTo=` and `After=` the scope, `CollectMode=inactive-or-failed`, and a plain `ExecStop` = `proto/0.5/guard-cleanup --daemon-gone <uuid>` (no `+`, no `ExecStopEx`; check whether `ExecStart` may be omitted or needs `/bin/true`);
  3. creates a test chain in `inet plasma_nm_vpn` with the UUID in its name (hooks `output` and `forward`, a harmless rule with a counter; the naming scheme is defined in 2.6);
  4. creates the persistent TUN `pnv-1a2b3c4d` as in 0.4, puts the core config into the run directory and starts `plasma-nm-vpn-core-<uuid>` as in 0.4, adding `BindsTo=` and `After=` on the scope, `After=` the guard unit, `CollectMode=inactive-or-failed` and `LoadCredential=config.json:<path>`; the core reads the config from the credentials directory (`%d` or `${CREDENTIALS_DIRECTORY}` on the command line — check which one is expanded in a transient unit, and record the path for 2.3);
  5. on `SIGTERM`, cleans up synchronously, as the real `disconnect` will: stops the core unit and waits for the job, deletes the TUN, removes the chain and the run directory, then stops the guard unit, and exits; on `SIGUSR1`, recreates only the core unit (`StopUnit`, then `StartTransientUnit` again, simulating a reconnect).
- [x] `proto/0.5/guard-cleanup --daemon-gone <uuid>`: writes its uid and effective capabilities (`CapEff` from `/proc/self/status`) to the journal, and also whether the core unit is still active at that moment; if `/run/plasma-nm-vpn/<uuid>/` still exists, stops the core unit if it is still there, deletes the TUN, removes the chains for that UUID and deletes the run directory; otherwise logs “nothing to do” and exits.
- [x] Root without `+`: `systemctl show plasma-nm-vpn-guard-<uuid> -p ExecStop` shows the command as sent; the `guard-cleanup` journal shows uid 0 and the full capability set. For comparison, record what `systemd-run -p ExecStop=…` actually sends (`busctl monitor`): the C code builds the property itself.
- [x] Stop ordering (decided in design.md, verified here): with the core unit `After=` the guard unit, `kill -9` of the “daemon” → the journal shows the core unit stopped before `guard-cleanup` started, and `guard-cleanup` logged the core as no longer active. Repeat a few times. If the order does not hold, record it and propose a fix for design.md; `guard-cleanup` stops the core unit itself in any case.
- [x] Start the “daemon” from another service, as NM does: `systemd-run --unit=pnv-fake-nm …fake-daemon <uuid>`. `systemd-cgls` → the “daemon” is in the scope, outside `pnv-fake-nm.service`.
- [x] Credentials: the file in the credentials directory cannot be read by a regular user or by `plasma-nm-vpn` outside the unit; record whether the source file can be deleted right after the unit starts.
- [x] Scenarios; in each, check `systemctl list-units --all 'plasma-nm-vpn-*'`, `ip link show pnv-1a2b3c4d`, `pgrep -u plasma-nm-vpn`, `nft list table inet plasma_nm_vpn`, the run directory and the `guard-cleanup` journal:
  - `SIGTERM` to the “daemon” → the core, guard unit and scope are gone, the TUN and the chain are gone, `guard-cleanup` logged “nothing to do”;
  - `kill -9` of the “daemon” → systemd stopped the core and then the guard unit, `guard-cleanup` ran as root and removed the TUN, the chain and the run directory; measure how long this took, until the guard unit is inactive;
  - `SIGUSR1` → the core unit is recreated and attaches to the same TUN, the guard unit stays active, the TUN, the chain and the run directory are still there;
  - `systemctl stop pnv-fake-nm.service` → the “daemon” in the scope is not killed (expected: NM manages the daemon by PID);
  - `kill -9` of the core → the scope and the guard unit are alive, the TUN and the chain are still there; record for 2.3 how the “daemon” learns about the crash;
  - right after `kill -9` of the “daemon”, start it again with the same UUID → step 1 waits until the old guard unit has gone inactive (its `ExecStop` may still be running), then all three `StartTransientUnit` calls succeed (`CollectMode=` let the old units go); record the wait; also make `guard-cleanup` exit with an error once and check that the failed unit is collected too;
  - a second “daemon” with the same UUID while the first is alive → step 1 times out; also record the error `StartTransientUnit` would return for the scope if step 1 were skipped (input for the re-activation rules in 2.3).

## Risks and notes
- `proto/0.5/guard-cleanup` is the prototype of `plasma-nm-vpn-guard --daemon-gone <uuid>` (design.md, item “`--daemon-gone <uuid>`”). It decides only by the run directory: the guard unit stops because the scope is gone, so no scope state needs to be compared.
- If `BindsTo=` on the scope does not fire on `kill -9` (for example, an emptied transient scope does not stop by itself), find the cause in the systemd documentation; if the mechanism does not work in principle, rewrite the item “Core lifetime is bound to the daemon” in design.md before 2.3.
- If the guard unit's plain `ExecStop` does not run as uid 0 with full capabilities, record the systemd version and what was seen, and correct design.md before 2.3.
- The daemon runs as root, so systemd calls over D-Bus do not require polkit. Recreating the core after a crash is the daemon's job (5.5), not systemd's.
- Results (`proto/0.5/scenarios.log`; design.md, “On `Connect`”, “Core unit failure”, “Daemon crash”): the guard unit needs no `ExecStart`; its plain `ExecStop` runs as uid 0 with full capabilities about 30 ms after the core has stopped; a `kill -9` of the daemon is cleaned up in 0.6–1.1 s; the restart right after it waits about 1.1 s; the core reads `${CREDENTIALS_DIRECTORY}/config.json`, and the credential source must exist at every start. `systemd-run` as root talks to systemd's private socket, so `busctl monitor` does not show its `StartTransientUnit`; ours is shown by `systemctl show` exactly as sent. The scenario harness starts the fake daemon as a child of a service's main process, as NM does: the main process itself would be killed with its service even from another cgroup.
