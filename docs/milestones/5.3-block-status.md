# 5.3 Block status and clearing

**Stage:** 5 · **Duration:** 1 d · **Depends on:** 5.1, 5.2 · **Needed for:** 5.4, 5.5, 5.6, 6.2

## Goal
The user can learn about a kill switch block and clear it. NM's failure signal carries only a reason code, so active blocks go to a world-readable status file, which the editor banner (6.2) reads, and `plasma-nm-vpn-guard --clear` removes leftover chains with administrator credentials via polkit.

## Inputs
- The kill switch chains, the success marker, the give-up flag and the kill switch part of `--daemon-gone` from 5.1; the inherited-block marker, the inherited path, re-activation detection, the takeover rules of the marker function, the `handing-over` entry and its first writer from 5.2; the test-build hook that holds the daemon before `Ip4Config` from 2.7.
- [design.md](../design.md), section “Leak protection”: items “Kill switch lifecycle”, “Inherited block”, `plasma-nm-vpn-guard --clear`, “How the user learns about a block”; section “Architecture”, item “Paths” (`/run/plasma-nm-vpn/guard-status`); section “Packages” (`pkexec` as a dependency of `plasma-nm-vpn-common`, versioned `guard-status` format); the 0.2 finding on whether a stock forky KDE install has `pkexec`.

## Tasks
- [ ] The `/run/plasma-nm-vpn/guard-status` format (world-readable, 0644): one entry per profile UUID, each carrying its format version, a state (`blocked`, or `handing-over` for the 5.2 hand-over), the reason of a block (e.g. gave up, daemon gone, inherited) and a timestamp; the 5.2 writer moves to this format. Profile names are not written: the file is world-readable, and the banner (6.2) gets names via NetworkManagerQt. Define the format with the banner in mind and record it in design.md, item “How the user learns about a block”. Readers accept the previous version (an upgrade does not touch running connections); writers keep entries they do not understand (a newer format version or state) unchanged, so that old and new daemon instances can share the file after an upgrade.
- [ ] Writing: several daemon instances, `--daemon-gone` and `--clear` may update the file at the same time, so every update takes a lock and replaces the file atomically (write to a temporary file, then rename).
- [ ] Entries:
  - written only if the profile's kill switch chains actually remain: the writer checks the table first, so a session whose chains were removed by `--clear <uuid>` writes nothing when it later gives up;
  - added by the daemon when it gives up with the success marker and the kill switch chains remain, and by `--daemon-gone` when the kill switch chains remain (success or inherited marker present, and no takeover marker); with a takeover marker `--daemon-gone` writes a `handing-over` entry instead (5.2);
  - ensured by the daemon when it places the inherited marker for chains left over from an earlier session, except on a takeover (the entry may be missing, for example after an upgrade or a manual removal);
  - on a takeover, only the old instance's `handing-over` entry (5.2), written by its disconnect handler on a hand-over or by `--daemon-gone` after a crash, which the new instance removes when it adopts the chains; the new instance writes a `blocked` entry only if its attempt ends without success (give-up, failure or disconnect), so a normal re-activation shows no banner;
  - kept while an attempt runs on inherited chains and when it fails or is disconnected, even explicitly;
  - removed on an explicit disconnect after success, when a successful connect replaces inherited chains, and by `--clear` (`handing-over` entries too).

  Every block is also logged to the journal with the profile UUID.
- [ ] `plasma-nm-vpn-guard --clear [<uuid>]` in `plasma-nm-vpn-common`: `--clear <uuid>` always removes that profile's kill switch chains and its `guard-status` entry, in either state. A bare `--clear` does this for every profile that has chains or an entry, except those whose VPN connection NM currently reports as activated or activating (queried via libnm by UUID, not by the daemon's scope). The daemon and `--daemon-gone` treat already removed chains as not an error.
- [ ] Elevation: run by a regular user, the tool re-executes itself via `pkexec` with the same arguments. Our polkit action (`auth_admin`, annotation `org.freedesktop.policykit.exec.path` on the tool's installed path) in `plasma-nm-vpn-common`; make sure `pkexec` is in its `Depends`. Record the action id in design.md, section “Leak protection”.
- [ ] Reboot: the table is never written to the persistent nftables config, and `/run` is tmpfs; check that nothing survives.

## Deliverables
- The `guard-status` writer in the shared library and in `--daemon-gone`; `plasma-nm-vpn-guard --clear` and the polkit action in `plasma-nm-vpn-common`.
- The `guard-status` format and the polkit action id in design.md.

## Done when
- [ ] After success, `systemctl restart NetworkManager` (a give-up) → `guard-status` has an entry for the UUID. After success, `kill -9` of the daemon → `--daemon-gone` has written the entry.
- [ ] Two blocked profiles → two entries; `nmcli connection up` that succeeds on one of them → only the other entry remains.
- [ ] An attempt on inherited chains whose entry was deleted by hand → the entry is back; the attempt fails before ACTIVATED, or is held by the 2.7 hook and ended with `nmcli connection down` → the entry is still there. Until 5.4, a failure is produced as in 5.2 (the core unit drop-in, or the hold hook followed by `kill -9` of the core), not by stopping the bench server.
- [ ] `plasma-nm-vpn-guard --clear <uuid>` run as a regular user in the VM (with `pkttyagent` as the polkit agent) → polkit asks for administrator credentials; confirmed → the profile's chains and entry are gone; refused → nothing changes, non-zero exit code.
- [ ] A bare `--clear` → all leftover blocks are removed; the chains of a connection that NM reports as activated stay. That connection is brought up before the blocks are created (or uses an IP literal in `server` or a cached server IP, since the blocks stop name resolution).
- [ ] After success, `nmcli connection up` of the same profile while it is up → no `blocked` entry at any point during the switch, and the old instance's `handing-over` entry is gone once the new instance adopts the chains; the same with the core unit drop-in from 5.1 in place, so the new attempt fails before ACTIVATED → the entry appears only when it gives up.
- [ ] A `handing-over` entry left by a hand-over whose new instance is prevented from starting (the 5.2 exit hook: the new instance exits after placing its takeover marker) → `--clear <uuid>`, and in a second run a bare `--clear`, removes it with the chains.
- [ ] After success, `--clear <uuid>` of the live session, then `systemctl restart NetworkManager` (a give-up) → no `guard-status` entry for the UUID.
- [ ] An entry with a newer format version added to `guard-status` by hand → still there, unchanged, after the daemon writes and removes its own entries.
- [ ] Rebooting the VM with leftover chains → no chains, no `guard-status` entries.

## Risks and notes
- `pkexec` requires an absolute path and strips the environment; the tool must not depend on either.
- If NM is not running, a bare `--clear` sees no active connections and clears everything: with NM gone there is no connection to protect.
- `--clear <uuid>` on a profile that is up removes the protection of a live connection; this is the user's explicit choice, and the daemon must cope with the chains being gone on disconnect.
- The banner and its “Clear” button are 6.2; the README section “No internet after a VPN failure” is 7.1.
