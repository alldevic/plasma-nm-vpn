# 3.1 AmneziaWG daemon

**Stage:** 3 · **Duration:** 2 d · **Depends on:** 2.7 · **Needed for:** 3.2, 5.4, 6.6

## Goal
The second daemon on the shared library: AmneziaWG via amneziawg-go in a unit without root, configured by the daemon through `awg setconf` from the profile fields. The milestone verifies that the stage 2 library can be reused for a core built differently from the proxy cores (config over UAPI rather than through credentials).

## Inputs
- Shared library 2.1–2.6 and test suite 2.7; findings of 0.4 (amneziawg-go as `plasma-nm-vpn`, attaching to an existing persistent TUN, `/run/amneziawg`, `awg setconf` as root).
- Package `plasma-nm-vpn-amneziawg` with amneziawg-go `v3.1.20261116`, `awg` from amneziawg-tools `v3.1.20260812` and tmpfiles.d for `/run/amneziawg` (1.2); allowlist format from 2.2.
- [design.md](../design.md), section “Architecture”: items “amneziawg-go”, “Service names follow the protocol, not the core” (`org.freedesktop.NetworkManager.pnv.amneziawg`), “Paths”, unit `plasma-nm-vpn-core-<uuid>.service`.
- [design.md](../design.md), section “Profile data schema”: AmneziaWG keys and secrets, the allowlist as data, “AmneziaWG rules in the MVP”.
- [design.md](../design.md), section “Core supervision and cleanup”: items “On `Connect`, in this order” (the guard unit from 2.3 covers this core too), “Readiness” (the core attached to the TUN within 15 s, NM sets `IFF_UP` after `Ip4Config`), “Liveness check” (for AmneziaWG the first handshake; how to trigger it reliably is checked here, the check itself and giving up without a handshake are 5.4) and “`--daemon-gone <uuid>`” (the UAPI socket is a leftover); section “Network changes and sleep” (the TUN belongs to the daemon).
- [design.md](../design.md), section “Daemon security”: `awg-quick` is not used. Parsing `.conf` belongs to the import parsers (6.6); the daemon works only with profile fields.
- AmneziaWG test bench from 0.3/1.4.

## Tasks
- [ ] `.name` (`program=/usr/lib/plasma-nm-vpn/plasma-nm-vpn-service-awg`) and D-Bus policy for `org.freedesktop.NetworkManager.pnv.amneziawg` in the `plasma-nm-vpn-amneziawg` package, following 2.1.
- [ ] Allowlist of AWG 3.1 parameters as data in `/usr/share/plasma-nm-vpn/`: `awg-<parameter>` → key in the `awg` config, type and allowed values. `HeaderProtectionKey` is not in the list: it is only the secret `awg-headerprotectionkey`. Check the exact names and syntax of the 3.0/3.1 parameters (ContentPaddingAddition, timings, MaxHandshakeAttempts, RandomTrailers, DisableCookies) and the value format of H1–H4 and I1–I5 against the amneziawg-tools sources at the pinned tag. The 6.5 editor and the 6.6 parser read the same file.
- [ ] Field validation with the 2.2 validators: `server`, `port`; `peer-public-key` and the secrets are base64 WireGuard keys; `allowed-ips` is a list of CIDRs; `keepalive` is a number within a range; an unknown `awg-*` key → `Connect` is rejected without starting the core.
- [ ] Secrets: `private-key` is required; `preshared-key` and `awg-headerprotectionkey` are requested through the shared `need_secrets` only if the profile uses them (according to the flags).
- [ ] Config generator for `awg setconf`: `[Interface]` with `PrivateKey`, the allowlisted parameters and HeaderProtectionKey from the secret; a single `[Peer]` with `PublicKey`, `PresharedKey`, `Endpoint` = the server IP chosen by 2.4 and `port`, `AllowedIPs` (IPv4 entries only), `PersistentKeepalive`. No `Address`, `DNS`, `MTU` or wg-quick hooks.
- [ ] Pass the config to `/usr/lib/plasma-nm-vpn/bin/awg setconf pnv-<…>` without writing secrets to disk (through a pipe, e.g. `/dev/stdin`; verify that `awg` accepts this).
- [ ] Unit `plasma-nm-vpn-core-<uuid>.service` via the 2.3 module: `ExecStart=/usr/lib/plasma-nm-vpn/bin/amneziawg-go -f pnv-<…>` attaching to the persistent TUN that the daemon created (2.4; the way to make amneziawg-go attach rather than create is the 0.4 finding), extension `ReadWritePaths=/run/amneziawg`; `LoadCredential=` is not needed, the config arrives over UAPI. Cleanup after a daemon crash is the guard unit with `plasma-nm-vpn-guard --daemon-gone <uuid>` (2.3, 2.6), as for the other cores; nothing protocol-specific is added to the core unit.
- [ ] Start order, after the shared 2.3/2.4/2.6 steps (orphan cleanup, run directory, daemon scope, guard unit, server name resolution, persistent TUN, guard chains): the per-core post-start step, as one function that 5.5 calls again after recreating the core: remove a stale `/run/amneziawg/pnv-<…>.sock` before starting the core unit → core unit → wait until amneziawg-go has attached to the TUN and its socket appears (15 s) → `awg setconf`. Then Config (`TUNDEV`, `gateway`, `CAN_PERSIST`) and a minimal `Ip4Config` (the first IPv4 from `address`) → NM brings the interface up and activates the connection → the first handshake is triggered.
- [ ] First handshake: verify on the test bench whether amneziawg-go initiates it on its own after `IFF_UP` with `PersistentKeepalive`, and what happens without keepalive; if needed, the daemon triggers it with a first packet. Make the trigger a library function: 5.4 also uses it to nudge an idle tunnel before each periodic check. Record the result in design.md (item “Liveness check”).
- [ ] A library function that reads the time of the last handshake: `awg show pnv-<…> latest-handshakes` or `last_handshake_time_sec` over UAPI — pick one. Here the daemon only logs the first handshake (or its absence after the allotted time) to the journal; giving up without a handshake, the success marker and the periodic check are the liveness check of 5.4.
- [ ] The UAPI socket as a leftover: amneziawg-go killed with `kill -9` does not remove `/run/amneziawg/pnv-<…>.sock`. The daemon removes it on disconnect after the core stops, orphan cleanup (2.3) removes it with the other leftovers, and `plasma-nm-vpn-guard --daemon-gone <uuid>` removes it after a daemon crash.
- [ ] Golden tests of the generator for the pinned version; unit tests: newline in an `awg-*` value, key outside the allowlist, `awg-headerprotectionkey` in `vpn.data` instead of `vpn.secrets` → rejected.

## Deliverables
- AmneziaWG daemon on `plasma-nm-vpn-common`, the AWG 3.1 allowlist in `/usr/share/plasma-nm-vpn/`, the generator with golden tests, the post-start step, the handshake trigger and handshake-reading functions, `.name` and D-Bus policy in the package; UAPI socket removal in the daemon, orphan cleanup and `--daemon-gone`.
- In design.md: how the first handshake is initiated and how it is checked.

## Done when
- [ ] In the test VM: a `.nmconnection` with fields pointing to the test bench AmneziaWG server, `nmcli connection up` → ACTIVATED, `awg show` shows a fresh handshake, ping to the server's address inside the tunnel succeeds.
- [ ] `ps -o user= -C amneziawg-go` → `plasma-nm-vpn`; `awg-quick` is not invoked on the system and is not in the package; `ip -d link show pnv-…` shows a persistent TUN owned by `plasma-nm-vpn` (the TUN was created by the daemon, not by the core).
- [ ] Wrong `peer-public-key` → the connection activates, `awg show` shows no handshake, and the daemon's journal records that no handshake happened (giving up comes with the liveness check in 5.4).
- [ ] `nmcli connection down`, and separately `kill -9` of the daemon → no unit, process, TUN, socket in `/run/amneziawg` or directory `/run/plasma-nm-vpn/<uuid>/` remains.
- [ ] A stale socket of this TUN left in `/run/amneziawg` by hand → the next `nmcli connection up` removes it and connects.

## Risks and notes
- Until the liveness check (5.4), a connection without a handshake stays formally ACTIVATED; with a default-route tunnel, traffic during this time goes into the non-working tunnel rather than around it, and the 2.6 guard is already in effect.
- A failure of the core unit: until 5.5 the library gives up on it, as in 2.7. From 5.5, a failure after success recreates the core unit through the reconnect cycle with this post-start step, and a failure before success still gives up.
- Running amneziawg-go without root, attaching to a persistent TUN and the socket directory via tmpfiles.d were verified in 0.4; that NM sets `IFF_UP` only after `Ip4Config` has already been established in design.md.
