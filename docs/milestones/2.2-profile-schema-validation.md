# 2.2 Schema and field validation

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 2.1 · **Needed for:** 2.5, 3.1, 4.1, 6.1, 6.6

## Goal
Everything in a profile is untrusted data for a daemon running as root. This milestone provides a single entry point: a profile either passes validation in full and becomes a typed structure, or it is rejected before anything is launched. This closes off a class of vulnerabilities like CVE-2018-10900.

## Inputs
- The daemon skeleton from 2.1 (protocol table, the “give up” function).
- [design.md](../design.md), section “Profile data schema”: common keys (`schema`, `server`, `port`, `dns`, `kill-switch`, `allow-lan`, `mtu`, `extra`) and protocol keys; Hysteria2 has `ports` in the link format instead of `port`.
- [design.md](../design.md), section “Daemon security”: what is validated, what is forbidden in `extra`.
- [design.md](../design.md), section “Architecture”, item “Paths”: allowlists live in `/usr/share/plasma-nm-vpn/`.
- [design.md](../design.md), section “plasma-nm user interface”: form validation calls this same library, allowlists included; parsers and validators return message codes with parameters, and the editors render them through ki18n; value lists (TLS fingerprints, XHTTP modes) are data next to the allowlists.

## Tasks
- [ ] Schema `schema=1`: a field table (key, type, required or not, default value) for the common keys and the Hysteria2 keys; a version newer than known → rejection. Lay the groundwork for migrations from older versions, but leave it empty for now.
- [ ] Validators in the library: host (DNS name per RFC 1123 or an IPv4/IPv6 literal), port 1–65535, `ports` in the Hysteria2 link format (`443` or `443,5000-6000`: a list of ports and ranges, range start not greater than range end), bounded integers (`mtu`, `hop-interval`, `up-mbps`, `down-mbps`), `yes`/`no`, enumerations (`obfs`: `salamander` or empty), base64 and hex with the expected length, a list of IPs for `dns`, a maximum length for each field.
- [ ] An IPv4 CIDR list validator (for `allowed-ips` and routes) with the normalization from design.md, “AmneziaWG rules in the MVP”: `0.0.0.0/1` + `128.0.0.0/1` → `0.0.0.0/0`. It lives here, in the shared library, so that the importer (6.6), the editor (6.5) and the daemon (3.1, 3.2) all treat these lists alike; the AmneziaWG keys themselves are added to the schema in 3.1. Unit tests: the pair in either order, with other entries, only one half (not normalized), duplicates.
- [ ] A common rule for all strings from `vpn.data` and `vpn.secrets`: control characters (including `\n`, `\r`, `\0`) are forbidden, and the string must be valid UTF-8.
- [ ] Unknown `vpn.data` keys (other than `<key>-flags`): the proposal is to reject them, naming the key, rather than silently skip them. Record the decision in design.md.
- [ ] `extra`: parse the JSON with json-glib, top-level object only; keys are checked against the allowlist; keys with file paths, `detour` and anything outside the outbound are forbidden. Limit the size and nesting depth.
- [ ] Allowlists as data: choose a file format in `/usr/share/plasma-nm-vpn/` (the file is installed by the core package), and a loader in the library. The same format and loader carry the value lists for the forms (4.1 delivers the TLS fingerprints and XHTTP modes). The Hysteria2 key list itself is filled in in 2.5. Record the format in design.md.
- [ ] Errors as message codes: every rejection returns a stable code plus parameters (the key, the offending value's position, the limit), never a ready English sentence; the daemon turns them into a journal message, the editors into ki18n strings (6.1 renders the validator codes). The codes form one shared C list; 6.6 adds the parser codes to it, and 6.7 their ki18n rendering. The library has no ki18n dependency.
- [ ] The validation result is a structure with typed fields; the config generators (2.5, 3.1, 4.1) work only with it, not with `vpn.data`.
- [ ] Unit tests: an “input → accepted/rejected” table for each validator; known vectors: a newline in `server`, `tls-sni` and the password; a file path and `detour` in `extra`; a key outside the allowlist; port 0 and 65536; `ports` like `6000-5000` and `443,,80`; overly long strings.
- [ ] Fuzzing: a target for the function “`vpn.data` + `vpn.secrets` dictionary → structure or error” and a separate one for `extra`; choose an engine (for example, libFuzzer under clang), a seed corpus from the unit tests, a scheduled CI job.

## Deliverables
- A validation module in `plasma-nm-vpn-common`: schema, validators, allowlist loader.
- Unit tests, fuzz targets and corpus, a scheduled CI job.
- The allowlist format and the rule for unknown keys in design.md.

## Done when
- [ ] `ctest` → all attack-vector tests pass: every such profile is rejected with the expected message code and parameters.
- [ ] In the VM: `nmcli connection up` of a profile with a newline in `tls-sni` → `Connect` is rejected, no core unit was created (automated in 2.7).
- [ ] The fuzzing job is scheduled in CI and has run at least once without crashes.

## Risks and notes
- Strict rejection of unknown keys simplifies auditing but breaks old daemons on new profiles; this is deliberately covered by the `schema` field.
- The values of `tls-alpn`, `tls-pin-sha256` and `ports` have their own format on the sing-box side (see 2.5): the validator and the generator must agree, and shared test profiles check this.
- The import parsers (6.6) and the editor widgets (6.1) reuse these same validators, so they must not depend on daemon code: only on GLib and json-glib.
