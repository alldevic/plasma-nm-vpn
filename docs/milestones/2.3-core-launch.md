# 2.3 Core launch

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 2.1, 0.4, 0.5 · **Needed for:** 2.4, 3.1, 4.2

## Goal
Move the mechanisms verified on the 0.4 and 0.5 prototypes into the library: the core is launched in a transient unit without root, receives its config via credentials and is guaranteed to die together with the daemon, and a guard unit cleans up after a daemon crash. Re-activating a profile must never harm its live previous instance. This is shared code for all three cores.

## Inputs
- The daemon skeleton from 2.1 (synchronous `disconnect`, the test build); the findings and working unit properties from 0.4 (user, capabilities, sandbox, the readiness signal on a persistent TUN) and 0.5 (the `StartTransientUnit` calls, scope, guard unit with a plain `ExecStop` as root, the core unit `After=` the guard unit, `BindsTo=`, `LoadCredential=` and the credentials path, `CollectMode=`, the wait after a crash).
- [design.md](../design.md), section “Architecture”: items “Core launch”, “Core lifetime is bound to the daemon”, “Paths” (`/usr/bin/plasma-nm-vpn-guard`, `/run/plasma-nm-vpn/<uuid>/`); the TUN name `pnv-` + 8 characters of the UUID.
- [design.md](../design.md), section “Core supervision and cleanup”: items “On `Connect`, in this order”, “Readiness”, “Core unit failure”, “Disconnect”, “Daemon crash”, “`--daemon-gone <uuid>`”; section “Leak protection”, item “Re-activation” (the takeover marker).

## Tasks
- [x] A systemd D-Bus client (GDBus, `org.freedesktop.systemd1.Manager`): `StartTransientUnit`, `StopUnit`, `ResetFailedUnit`, unit lookup and `ActiveState`, subscription to `JobRemoved` and `PropertiesChanged`; blocking variants for the synchronous `disconnect`.
- [x] Orphan cleanup on `Connect` (step 1 of design.md), as soon as the UUID is known and before creating our own run directory and scope:
  - if the previous daemon instance of this profile is still active (its scope is active: NM is re-activating the profile), place the “takeover” marker in its run directory (the marker gets its meaning for the kill switch chains in 5.2);
  - wait, up to 10 s, until `plasma-nm-vpn-daemon-<uuid>.scope`, `plasma-nm-vpn-guard-<uuid>.service` and `plasma-nm-vpn-core-<uuid>.service` are all inactive, failed or gone; waiting for the scope alone is not enough, because the guard unit may still be running `--daemon-gone`. On timeout, remove the takeover marker placed above and fail `Connect` without touching anything else (record this marker rule in design.md);
  - then the leftovers are removed: failed units are reset, a leftover `/run/plasma-nm-vpn/<uuid>/` is first processed by the same code as `--daemon-gone` (so that the marker logic added in 5.1 and 5.2 applies to it), then deleted; the leftover TUN goes with it. The list of leftovers is extensible: 3.1 adds the AmneziaWG UAPI socket.
- [x] TUN name collision: before deleting or creating `pnv-<8 characters>`, check whether the name belongs to a live unit of another profile (a UUID prefix collision, possibly deliberate); if so, fail `Connect` with a clear reason in the journal.
- [x] Step 2 of design.md: create `/run/plasma-nm-vpn/<uuid>/` (root, 0700), move the daemon into its scope `plasma-nm-vpn-daemon-<uuid>.scope`, then start the guard unit `plasma-nm-vpn-guard-<uuid>.service` exactly as in 0.5: `Type=oneshot`, `RemainAfterExit=yes`, `BindsTo=` and `After=` the scope, a plain `ExecStop=/usr/bin/plasma-nm-vpn-guard --daemon-gone <uuid>` (no `+` and no `ExecStopEx`: the unit has no `User=` and no sandbox, so it runs as root), `CollectMode=inactive-or-failed`. The parent `/run/plasma-nm-vpn` comes from a tmpfiles.d line in `plasma-nm-vpn-common`: `d /run/plasma-nm-vpn 0755 root root -` (0755, because `guard-status` in it is world-readable; each `<uuid>/` stays 0700).
- [x] `plasma-nm-vpn-guard` at `/usr/bin/plasma-nm-vpn-guard` in `plasma-nm-vpn-common` (users also run it for `--clear` in 5.3), command `--daemon-gone <uuid>`: acts only if `/run/plasma-nm-vpn/<uuid>/` exists; stops the core unit if it is still there, deletes the TUN, deletes the run directory. Chain removal is added in 2.6, kill switch chains and the success marker in 5.1, the inherited-block and takeover markers in 5.2, `guard-status` in 5.3, the AmneziaWG UAPI socket in 3.1.
- [x] The run directory holds the core config, passed via `LoadCredential=`. Until the generator exists (2.5), a temporary config from the 0.7 prototype is used (2.4 fills in the network values).
- [x] The core unit description as a single structure shared by all cores: `ExecStart` (a binary from `/usr/lib/plasma-nm-vpn/bin/`, the config path in the credentials directory as found in 0.5), `User=plasma-nm-vpn`, `AmbientCapabilities=` and `CapabilityBoundingSet=` per core (`CAP_NET_ADMIN` for sing-box and amneziawg-go, none for xray), `KillSignal=SIGKILL`, the sandbox, `BindsTo=` and `After=` on the scope, `After=` the guard unit (decided in design.md, verified in 0.5: on a crash systemd stops the core first and only then runs the guard unit's `ExecStop`), `LoadCredential=`, `CollectMode=inactive-or-failed`. Provide for extensions: `ReadWritePaths=` for AmneziaWG (3.1), and for xray an `ExecStart` through the helper that hands over the TUN as fd 3 (`XRAY_TUN_FD`, design.md, “Network changes and sleep”). Step 3 of design.md orders what follows: resolution (2.4), the persistent TUN (2.4), the chains (2.6), then the core unit.
- [x] Readiness: poll `IFLA_CARRIER` of `pnv-…` via `RTM_GETLINK` every 100 ms until it turns 1 (0.4: no `RTM_NEWLINK` arrives for it while the interface is down); timeout 15 s (configurable). Until 2.4 creates the persistent TUN before the core, the temporary config lets the core create the TUN itself, and readiness is its appearance. There is no need to bring the interface up (`IFF_UP`): NM does that after `Ip4Config`. Budget against libnm's 60 s connect timer: up to 10 s orphan wait, 5 s resolution (2.4), 15 s readiness.
- [x] Core unit failure: before success the daemon gives up (the function from 2.1), with the reason and the unit name for `journalctl -u` in the journal; after success it recreates the core via the reconnect cycle (5.5). Until 5.5 the daemon gives up in both cases.
- [x] Synchronous stop in `disconnect` (explicit or give-up), in the order of design.md, item “Disconnect”: `StopUnit` on the core and wait for the job, delete the TUN, remove the chains (2.6, 5.1), update `guard-status` (5.3), delete `/run/plasma-nm-vpn/<uuid>/`, and as the last step stop the guard unit (its command then finds no run directory and does nothing). All of it finishes before the handler returns.
- [x] Verification in the VM: the scenarios from “Done when” as scripts suitable for moving into 2.7.

## Deliverables
- A core launch module in `plasma-nm-vpn-common`: orphan cleanup with the takeover marker, run directory, scope, guard unit, transient core unit, readiness, supervision, synchronous stop; `/usr/bin/plasma-nm-vpn-guard --daemon-gone`; the tmpfiles.d line for `/run/plasma-nm-vpn`.

## Done when
- [x] `nmcli connection up` → the core unit is active, the process runs as `plasma-nm-vpn`, the guard unit is active, `pnv-…` exists. `nmcli connection down` → once the daemon has exited, no core unit, no guard unit, no scope, no process, no TUN and no `/run/plasma-nm-vpn/<uuid>/`.
- [x] Synchronous cleanup: in the test build, a test hook makes the daemon own a dummy per-UUID chain in `inet plasma_nm_vpn` (as kill switch chains will be), removed just before the run directory is deleted → after `nmcli connection down`, and after a give-up, no chain for this UUID remains.
- [x] `kill -9` of the daemon → within a few seconds no core unit, no sing-box process, no TUN, no scope and no guard unit; `--daemon-gone` ran as root (after the core unit had stopped) and removed the run directory.
- [x] A core with a deliberately broken config → the connection fails before the timeout, and the daemon's journal contains the unit name.
- [x] Inactive units, a TUN and a run directory left over by hand → the next `Connect` removes them and connects. Right after `kill -9` of the daemon, `nmcli connection up` → the new instance waits until the old guard unit has gone inactive, then connects (no name clash).
- [x] Re-activation: `SIGSTOP` the live daemon of a profile and `nmcli connection up` the same profile → the new instance places the takeover marker, waits about 10 s, removes the marker and fails `Connect`; the old scope, core and TUN are untouched (resume it with `SIGCONT`). A normal `nmcli connection up` while the profile is active → the old instance cleans up, the new one connects.
- [x] Two test profiles whose UUIDs share the first 8 characters → the second `Connect` fails while the first is up, and the first keeps passing traffic.
- [x] `stat /run/plasma-nm-vpn` → `0755 root root` after installing the package; `/run/plasma-nm-vpn/<uuid>/` is `0700 root`.

## Risks and notes
- How `BindsTo=` on the scope, the root `ExecStop` of the guard unit, the stop order, `LoadCredential=` and `CollectMode=` work in transient units was verified in 0.5; moving the daemon out of the NetworkManager cgroup was verified in 0.7. Do not investigate this again, just carry over the findings.
- The config with secrets stays in `/run/plasma-nm-vpn/<uuid>/` until the session ends. After a `kill -9` of the daemon, `--daemon-gone` deletes it; the orphan cleanup on `Connect` and a reboot (`/run` is tmpfs) are only fallbacks.
- If sing-box has to be run as root (a risk in design.md), only the core unit description changes.
- If 0.4 or 0.6 found that a core cannot attach to a persistent TUN, the core unit description for that core keeps the TUN creation in the core, and 5.5 adds the temporary block chain fallback for its restarts.
- Results:
  - Code: `common/daemon/units.c` (systemd over D-Bus), `tun.c`, `rundir.c` (also used by `plasma-nm-vpn-guard`, `common/guard`), `core.c` (orphan cleanup, scope, guard unit, core unit, readiness, supervision). The sing-box daemon describes its core in a `PnvCore` and builds a temporary config with json-glib.
  - The cases are `tests/integration/cases/test_31_core.py`, 8 cases in the test build, all green in the VM together with the 2.1 cases (13 in about 40 s).
  - The persistent TUN came forward from 2.4: the daemon creates it (owner `plasma-nm-vpn`, the profile's MTU or 1400) before the core, so readiness is already `IFLA_CARRIER` on the real thing. Until 2.4: the TUN address is fixed at 198.18.0.1/30, the server name resolves without a timeout, DNS servers come from the profile only, and `Config` has only the IPv4 gateway.

After `SIGCONT` the old instance gets its `Disconnect` and cleans up. Recorded in design.md (“Takeover marker on timeout”).
  - Traffic through the first of two clashing profiles is not checked: the local VM case has no bench. Instead, its core is active and the TUN carrier is 1. 2.7 runs it with the bench.
  - Test hooks added: `broken-config` (an invalid config, so the core unit fails) and the per-UUID chain `test-<8>` in `inet plasma_nm_vpn`.
