# 4.1 xray config

**Stage:** 4 · **Duration:** 2 d · **Depends on:** 2.2, 0.6, 3.2 · **Needed for:** 4.2, 6.4, 6.6

## Goal
A config generator for xray for VLESS XHTTP Reality from the typed profile fields: VLESS with `encryption`, the XHTTP transport, Reality, the built-in TUN inbound and an explicit `sockopt.interface`. The milestone carries the findings of prototype 0.6 into the product and locks down the config format with golden tests for the pinned xray version. Next to the allowlists it ships the value lists (TLS fingerprints, XHTTP modes) that the daemon (4.2), the editor (6.4) and the parser (6.6) all read.

## Inputs
- Findings of milestone 0.6: a working xray ≥ v26.10.21 config with the TUN inbound and `sockopt.interface`, without a loop, with UDP (DNS) over VLESS XHTTP, and whether xray attaches to an existing persistent TUN.
- Validators, the `schema=1` schema and the allowlists-as-data mechanism from 2.2; the reference generator and golden tests are 2.5 (sing-box).
- [design.md](../design.md), sections “Profile data schema” (VLESS XHTTP Reality keys), “Daemon security”, “Architecture” (item “Paths”), “Route to the server”, “Routing, DNS and IPv6”, “plasma-nm user interface” (value lists for the forms are data shipped with the core package next to the allowlists).

## Tasks
- [x] Pin the xray version in the data of the `plasma-nm-vpn-xray` package (per design.md currently 26.11.9, package version `0.1.0+xray26.11.9`; no lower than v26.10.21). The config template, allowlists and value lists for this version live in `/usr/share/plasma-nm-vpn/`.
- [x] The generator (C, json-glib) takes as input the validated profile fields, the `uuid` secret and runtime parameters: the server IP (from 2.4), the TUN name `pnv-<8 characters of the UUID>`, the name of the VPN's parent device in NM, the MTU. The result is written to `/run/plasma-nm-vpn/<uuid>/` (the source for `LoadCredential=`).
- [x] Inbound: xray's built-in TUN named `pnv-…`, attaching to the persistent TUN that the daemon created (2.4) as found in 0.6, and without routes (NM sets the routes). Take the exact TUN inbound key names from the 0.6 config and the TUN module README of the pinned version.
- [x] `vless` outbound: the address is the server IP chosen by 2.4, not the name; `port`; `id` = `uuid`; `encryption` = `none` or the VLESS Encryption ML-KEM key from the profile. Check the format of the `settings` block (with `vnext` or flat) against the pinned version.
- [x] `streamSettings`: `network: "xhttp"`, `xhttpSettings` from `xhttp-mode`, `xhttp-path`, `xhttp-host` (defaults to the server name) and `xhttp-extra`; `security: "reality"`, `realitySettings` from `tls-sni`, `tls-fingerprint`, `reality-pbk`, `reality-sid`, `reality-spx`. SNI and Host remain the name.
- [x] `sockopt.interface` = the VPN's parent device in NM, always set explicitly; autodetection is not used.
- [x] UDP pass-through: configure it the same way as in 0.6 (e.g. VLESS UDP encapsulation parameters; check against the documentation for the version).
- [x] Value lists as data next to the allowlists, in the 2.2 format: the allowed `tls-fingerprint` values (Reality fingerprints) and `xhttp-mode` values for the pinned xray version, taken from its documentation and sources. The 2.2 validator library checks these fields against the lists, so the daemon (4.2) and the form (6.4) reject the same values; nothing duplicates the lists in code.
- [x] `extra` is merged only into the outbound object, `xhttp-extra` only into `xhttpSettings.extra`; both according to key allowlists for the xray version. Forbidden: file paths, keys that divert traffic to another outbound (analogues of `detour`, e.g. `dialerProxy`; to be checked), overriding `sockopt.interface` and the server address, anything outside the outbound.
- [x] xray logs to stdout/stderr (they end up in the unit's journal), without an access log.
- [x] Golden tests: minimal profile, `encryption` with an ML-KEM key, each `xhttp-mode` from the value list, a non-default fingerprint, `xhttp-extra`, `extra`, empty optional fields. Negative tests: forbidden `extra`/`xhttp-extra` keys, paths, newlines.
- [x] Test step: every golden config is checked with `xray run -test` using the binary of the pinned version (check the flag for passing the config file against `xray help run`).

## Deliverables
- The xray config generator in the `plasma-nm-vpn-xray` code, the template, the `extra` and `xhttp-extra` allowlists and the value lists (TLS fingerprints, XHTTP modes) for the pinned version, installed by the package.
- Golden files and unit tests enabled in CI; the fuzzing harness from 2.2 covers parsing of `extra` and `xhttp-extra`.

## Done when
- [x] Unit tests in CI → the xray golden tests are green.
- [x] Every golden config → `xray run -test` of the pinned version completes successfully.
- [x] `extra` with a file path, with a key outside the outbound or with an override of `sockopt.interface` → the generator rejects the profile with a clear error.
- [x] A `tls-fingerprint` or `xhttp-mode` value outside the value list → rejected by the 2.2 validator; a value added to the list file is accepted without rebuilding.
- [x] In the generated config the outbound address is an IP, `sockopt.interface` is set, `serverName` and Host are names.

## Risks and notes
- The xray config format changes quickly; the template, allowlists and value lists are tied to the version in the package, and divergence is caught by the golden tests and job 1.5.
- According to its README, the TUN module is still for advanced users; its behavior was verified in 0.6 and is not re-investigated. If 0.6 found that xray cannot attach to a persistent TUN, the inbound creates the TUN itself and the fallback from design.md (“Network changes and sleep”: a temporary block chain during each core restart) applies; that is 5.5, not a generator change.
- The interface autodetection bug (issue 6412) is fixed in v26.10.21, but an explicit `sockopt.interface` is needed in any case: the core's binding must match the VPN's parent device in NM. This is decided in design.md and is not re-verified.
- The schema has no `flow` key. If links from the test bench require it, that is a change to the schema in design.md, not a silent addition to the generator.
- Results:
  - Code:
    - `backends/xray/daemon/config.c`: the generator, which fills the template `backends/xray/data/vless.json`;
    - `backends/xray/data`: the lists, all installed by `plasma-nm-vpn-xray` to `/usr/share/plasma-nm-vpn/xray/`:
      - `tls-fingerprint.list` and `xhttp-mode.list`, the value lists;
      - `vless-extra.list` and `xhttp-extra.list`, the allowlists.
    - The VLESS schema, in `common/profile/schema.c`:
      - `port`; `encryption`, `none` or `mlkem768x25519plus.…`, up to 4096 bytes (a real ML-KEM-768 client string from `xray vlessenc` is 1611);
      - `reality-pbk` (base64url, 32 bytes), `reality-sid` (hex, up to 16), `reality-spx` and `xhttp-path` (HTTP paths);
      - `tls-sni`, `xhttp-host`, and `tls-fingerprint` and `xhttp-mode` checked against the lists;
      - `xhttp-extra`, and the secret `uuid`.
      - Defaults: `encryption=none`, fingerprint `chrome`, mode `auto`, path `/`.
  - Lists: a protocol's list files are merged under prefixes (`pnv_list_merge_file`), and an allowlist entry may end in `.*` (design.md, “Validation”). Hysteria2 and AmneziaWG moved to the same scheme (`extra/`, `awg/`).
  - xray 26.11.9, from its sources:
    - fingerprints: the presets except `unsafe` (no uTLS, which Reality needs), plus the “modern” set;
    - modes: `auto`, `packet-up`, `stream-up`, `stream-one`;
    - the outbound uses the `vnext` format as in 0.6;
    - Reality's public key is `password`;
    - UDP needs no extra setting (0.6).
  - Refused in `extra` because not on the list: `proxySettings`, `sockopt.dialerProxy`, `sockopt.mark`, `sockopt.interface`, `settings`, `sendThrough`, any other top-level key. Refused in `xhttp-extra`: `downloadSettings`; `host`, `path` and `mode`.
  - Golden tests: `tests/golden/xray-26.11.9/`, 11 configs:
    - minimal; ML-KEM; each of the four modes; the `firefox` fingerprint; `xhttp-extra`; `extra`; empty optional fields; names (server by name with the IP from the session, `spiderX`, `xhttp-host`).
    - The ctest `xray-config` also has 19 rejection cases and checks that a value added to a list file is accepted.
    - `scripts/check-golden xray` runs `xray run -test -c` on each; all pass with 26.11.9. The `packages` job now checks both sing-box and xray goldens.
  - In the generated config the address is the IP, `sockopt.interface` is always set (a missing parent device is an error), and `serverName` and Host stay names. The daemon itself, the TUN handed over as fd 3 and the `.name` file are 4.2.
