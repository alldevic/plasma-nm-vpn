# 0.9 Flat repository

**Stage:** 0 · **Duration:** 1 d · **Depends on:** 0.2 · **Needed for:** 1.3

## Goal
Test the distribution scheme from design.md on real GitHub: a flat apt repository in the release assets of the latest release. We need to make sure that apt on forky installs packages from it, and pin down how GitHub renames assets, before building the release pipeline (1.3) on top of this. At the same time, set up the test repository and the test key on which all release rehearsals will later run.

## Inputs
- The VM from 0.2 (snapshot `clean`).
- [design.md](../design.md), section “Distribution and supply chain”, item “Repository”: `URIs: https://github.com/alldevic/plasma-nm-vpn/releases/latest/download/`, `Suites: ./`, no `Components`; the release is created as a draft; unchanged packages are taken from the previous release with a sha256 check; rehearsals happen in a separate test repository with a test key, and the URI in `.sources` is derived from the repository name; `Filename:` matches the final asset names; no `Acquire-By-Hash`.
- [design.md](../design.md), section “Packages”: core package versions `0.1.0+sb1.14.4`, `0.1.0+xray26.11.9`, `0.1.0+awg3.1.20261116`; the rest just use the project version.
- On the host: `gh` with access to the project account, `dpkg-dev`, `apt-utils` (for `apt-ftparchive`), `gnupg`.

## Tasks
- [ ] Create a public test repository, for example `alldevic/plasma-nm-vpn-test` (not the main one: any release published there immediately becomes `latest`). It is kept for release rehearsals in 1.3.
- [ ] A test signing key in a separate `GNUPGHOME` (not the project key); the public part goes into a binary keyring `plasma-nm-vpn-test.gpg`. Keep the private part for 1.3, marked as a test key.
- [ ] `proto/0.9/make-repo <owner/repo>`: builds with `dpkg-deb --build` empty packages `pnv-apt-test` version `0.1.0+sb1.14.4` and `pnv-apt-test-common` version `0.1.0`, as well as `pnv-apt-test-rc` version `0.1.0~rc1`; generates `.sources` with the URI derived from the repository name.
- [ ] Naming experiment: upload .deb files with their original names to a draft release and look at the resulting names (`gh release view <tag> --json assets`). Record what GitHub does with `+` and `~`. Delete the draft.
- [ ] Choose a rule for renaming files without `+` and `~` (for example, replacing them with `-`) and build it into `make-repo`.
- [ ] Index: `apt-ftparchive packages . > Packages`, `xz -k Packages` (→ `Packages.xz`), `apt-ftparchive release . > Release` (both files listed with their hashes), `gpg --clearsign -o InRelease Release`. Make sure `Filename:` matches the names of the future assets.
- [ ] Index compression (decided here, used by 1.3): the proposal is to ship `Packages` uncompressed plus `Packages.xz`. The uncompressed file stays because the release pipeline reads and checks the previous release's `Packages` against its signed `InRelease`; `Packages.xz` keeps `apt update` small as the package list grows. Check with `apt -o Debug::Acquire::http=true update` (or the apt log) which file apt fetches, and that it works when only one of the two is present; record the decision in design.md.
- [ ] Release `v0.0.1`: `gh release create v0.0.1 --draft …` with all files (.deb, `Packages`, `InRelease`), check the list of assets, then `gh release edit v0.0.1 --draft=false`.
- [ ] In the VM: the keyring in `/usr/share/keyrings/plasma-nm-vpn-test.gpg`; the generated `/etc/apt/sources.list.d/plasma-nm-vpn-test.sources` (deb822: `Types: deb`, `URIs: https://github.com/alldevic/plasma-nm-vpn-test/releases/latest/download/`, `Suites: ./`, `Signed-By:`); `apt update`, `apt install pnv-apt-test pnv-apt-test-common pnv-apt-test-rc`.
- [ ] Update `v0.0.2`: all three packages are built again, but only `pnv-apt-test` has a new version (`0.1.1+sb1.14.4`). The rule of 1.3 is rehearsed by hand: any package whose name and version already appear in the previous `Packages` has its fresh build discarded, and the previous asset is downloaded from `v0.0.1` (`gh release download`) and its sha256 checked against the previous `Packages`, whose own hash is checked against the previous signed `InRelease`; then a new index → in the VM, `apt update && apt upgrade` installs the new version and apt leaves the other packages alone.
- [ ] A draft `v0.0.3` with only some of the files, not published → `apt update` in the VM still sees `v0.0.2` without errors.
- [ ] Signature: publish a release with an `InRelease` signed by a different key → `apt update` refuses with a signature error; then fix it.
- [ ] Update design.md: close the “Verify on a prototype (stage 0)” item “A flat repository in release assets on the project's test repository” (the sixth in the list) in “Open questions and risks”; in “Distribution and supply chain”, record GitHub's behavior with `+` and `~`, the renaming rule, the index generation commands, the index compression decision and the name of the test repository.

## Deliverables
- `proto/0.9/make-repo` and a note with the results (1.3 builds the pipeline based on it).
- A test repository with releases `v0.0.1`–`v0.0.2` and a test key for 1.3.
- An entry in design.md.

## Done when
- [ ] In a clean VM with the keyring and `.sources` → `apt update` with no warnings, `apt install pnv-apt-test` installs `0.1.0+sb1.14.4`.
- [ ] Publishing `v0.0.2` → `apt upgrade` in the VM installs `0.1.1+sb1.14.4`; the sha256 of the carried-over packages matches `v0.0.1`.
- [ ] An unpublished draft is not visible to clients; an `InRelease` with a foreign signature is rejected.
- [ ] The asset naming rule and the index compression decision are recorded in design.md; with both `Packages` and `Packages.xz` published, `apt update` in the VM succeeds and the apt log shows which one it fetched.

## Risks and notes
- apt on forky working with the redirect chain to `release-assets.githubusercontent.com` has already been verified (design.md); if `apt update` still fails on a redirect, record the exact error and the apt version — this breaks the whole distribution scheme and requires a design review.
- A package with the same version but different contents breaks apt clients; that is why unchanged packages are not rebuilt (design.md). If the sha256 does not match, the release is not published.
- If apt misbehaves with `Packages.xz` in a flat repository, ship only the uncompressed `Packages` and record why; the decision is made here, 1.3 only implements it.
- Rolling back via apt is impossible by design (old versions are only on the pages of past releases); this is not tested here.
