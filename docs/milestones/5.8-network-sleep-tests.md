# 5.8 Network change and sleep tests

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.7 · **Needed for:** 6.3

## Goal
Lock down reconnection in CI on a bench with two parent devices: a parent device change, a real suspend and a core crash after success all end in a recovered tunnel without leaks, with or without the kill switch. Fix the acceptable recovery time, which the MVP acceptance criteria leave to the results of this milestone.

## Inputs
- The reconnect cycle, its timeout, the core recreation on the persistent TUN (or the fallback block chain) and the test-build switches (skip step 1, change the DNS list in the cycle), from 5.5; the suites and shared helpers from 5.6 and 5.7; the test image with `mac80211_hwsim`, `hostapd` and S3 suspend woken by `rtcwake` from 0.2 and 1.4; the bench from 0.3 with the bench DNS 203.0.113.1.
- [design.md](../design.md), sections “Network changes and sleep”, “Core supervision and cleanup” (item “Core unit failure”), “Leak protection”, “Testing” (VM over `AF_VSOCK`; sleep and Wi-Fi tests only under KVM), “MVP acceptance criteria”.

## Tasks
- [x] Bench: the client VM gets two parent devices towards the server bench: emulated Wi-Fi (`mac80211_hwsim`, with the access point via `hostapd` on the bench side) and wired (the veth from 0.3, explicitly put under NM management, otherwise it will not become the VPN's parent device). Both have a route to the server; `tcpdump` on both for the duration of each test. The management NIC is never disconnected; with never-default it never becomes the VPN's parent device, and the VM is driven over `AF_VSOCK`.
- [x] The sleep and Wi-Fi tests run only in the KVM variant of the bench and are skipped, with a visible reason, in the container fallback (they depend on the VM's own kernel).
- [x] Test profiles set `dns=203.0.113.1` before connecting (the 0.3 rule: 9.9.9.9 is unreachable on the bench, 1.1.1.1 is reserved for the never-default check); secrets via `nmcli connection up … passwd-file`; DNS in both modes (default `resolv.conf` and systemd-resolved). The tests below run with `kill-switch=yes` unless stated otherwise.
- [x] “Parent device change”: tunnel up on veth → `nmcli device disconnect` of it → the connection goes ACTIVATING → ACTIVATED, the route to the external gateway is on Wi-Fi, the liveness check passes, traffic and DNS go through the tunnel; then back. The captures have no DNS or IPv6 bypassing the tunnel and no traffic bypassing it except the kill switch exemptions.
- [x] “No leak without the kill switch”: the same device change and a `kill -9` of the core with `kill-switch=no` on a default-route tunnel, under a continuous `curl` to the bench and a `dig` loop → no IPv4 leaves directly during the cycle (only the core's traffic to the server, DHCP and local networks), because the persistent TUN keeps NM's routes, or, for a core using the fallback, because the temporary block chain is in place during the restart.
- [x] “Device comes back later”: both devices disconnected, one reconnected well within the cycle timeout → the connection recovers; none reconnected → give-up after the timeout, the kill switch chains and the `guard-status` entry remain.
- [x] “Sleep”: `rtcwake -m no -s <N> && systemctl suspend` (S3) with the tunnel up, so that logind itself emits `PrepareForSleep`; NM takes the devices down on suspend and brings them back after resume → the tunnel is restored without user involvement and without leaks. The test waits for the VM to resume over vsock rather than treating it as dead. Suspend on real hardware is checked on the hardware test machine in 7.2, if it is available.
- [x] “Core crash after success”: `kill -9` of the core under load (e.g. a continuous `curl` to the bench) → no direct traffic in the captures, the connection is ACTIVATED again with the liveness check passed, no `guard-status` entry; for AmneziaWG the stale socket was removed, `awg setconf` has run again and the handshake is fresh. Repeated kills → the increasing backoff is visible in the journal.
- [x] Tests are parameterized by protocol (Hysteria2, AmneziaWG, VLESS XHTTP Reality) where this does not require separate code.
- [x] Recovery time: measure it in the device change, sleep and core crash tests over several runs each, choose an acceptable value with a margin, check it in the tests and record it in design.md, section “MVP acceptance criteria”.

## Risks and notes
- Timing-based tests are flaky on shared runners: take the threshold with a margin rather than from the median, and log the actual time.
- If S3 suspend does not work under the CI runner's KVM even though it did in 0.2, the sleep test is skipped there with the reason logged and runs in the local VM and on the hardware test machine in 7.2; no emulated sleep path is added to the daemon.
- Wi-Fi emulation tests the device change, not the behaviour of a real radio; real Wi-Fi is tested on the hardware test machine in 7.2, if it is available.
- Results:
  - The suite: `tests/integration/cases/test_92_network.py`, 16 cases on the 5.6 helpers, kill switch on unless stated otherwise; the sleep and Wi-Fi cases are marked `kvm`. The bench (`stand-up`, `wifi()`): two `mac80211_hwsim` radios, one moved into netns `stand` as the access point `wlan-srv` (hostapd, WPA2, 192.0.4.1), the other the client `wlan0` under NM (profile `stand-wifi`, static 192.0.4.2/24, metric 600, IPv4 only), next to the veth `stand-cli`. A fixture brings both parents up before and after each case and fails if one does not come up. `tcpdump -Q out` on both parents for every case. Cases:
    - **Parent device change** (three protocols): `stand-cli` down → the route to the server moves to `wlan0`, traffic and DNS work; `stand-cli` back and `wlan0` down → back on `stand-cli`. Nothing leaves directly on either parent.
    - **DNS after a device change**: a test hook sends 203.0.113.53 in the cycle's `Ip4Config`; the tunnel's IP4.DNS shows it, and the connection state, polled every 0.1 s, went activated → activating → activated.
    - **No leak without the kill switch** (three protocols): a device change and a `kill -9` of the core under load (a curl and dig loop, and a 50/s ping, whose every packet takes the routes of that moment) → nothing leaves directly, the TUN keeps its ifindex.
    - **Device comes back later**: both parents down, Wi-Fi back after 10 s → reconnected. **No device comes back**: give-up after the cycle timeout; the chains and the `guard-status` entry stay.
    - **Sleep** (three protocols): `rtcwake` and `systemctl suspend` → “reconnected (trigger: resume)”, traffic and DNS back, nothing leaves directly.
    - **Core crash under load** (three protocols): reconnected, no `guard-status` entry; for AmneziaWG a fresh handshake. **Repeated failures back off**: the server dropped in netns `stand`, the journal shows 1, 2, 4 s.
  - Recovery times on the bench (several local runs): a parent change 2.6–3.6 s, a resume 0.3–2.0 s, a core crash 0.3–2.0 s; AmneziaWG is the slowest. The criterion is 20 s (design.md, “MVP acceptance criteria”), checked by the tests. CI keeps the test output in the junit report: over two runs in both DNS modes, a parent change 2.4–3.8 s, a resume 0.3–1.9 s, a core crash 0.3–1.9 s.
  - Found and fixed:
    - **Daemon:** with both parents down, a device-change event without a device while the daemon was stepping aside restarted the wait and stopped the poll, and a device that NM had assigned by the end of the 2 s wait was ignored. Now the wait is not restarted, and a device found then starts the regular cycle.
    - **Bench:** the hwsim access point shares the client's kernel and did not come back from a suspend (the client was stuck in association); a `system-sleep` hook restarts hostapd on resume, as its own unit. The 0.3 bench case that unloaded `mac80211_hwsim` now checks the Wi-Fi bench instead.
    - **Tests:** the 5.5 resume case suspended before the first liveness check had passed, and a resume before success is no trigger by design; it now waits for the success.
  - The QEMU RTC: after the first suspend of a boot, later ones wake within a second (“Could not disable RealTimeClock events”). The kernel still goes through S3 and NM through sleep and wake, which is what the cases check.
  - Deliberate breakages:
    - **Hooks `cycle-dns,skip-starting`:** the DNS case fails in both DNS modes, on the state (no `activating`). With `cycle-dns` alone it passes. Contrary to the milestone's assumption, the new DNS list does reach NM without step 1: NM 1.58.1 applies Config and `Ip4Config` while `STARTED` (as recorded in 0.7; a contradicting line in design.md is fixed). So the case checks the state, which is what step 1 is for, and keeps the DNS list as the proof that the cycle's `Ip4Config` applied. The resolved mode was checked in CI from a throwaway branch, deleted afterwards.
    - **A local patch deleting the TUN before the core restarts** (so the core creates its own): the no-leak case fails, with ICMP leaving directly on `wlan0`. It failed only after the ping was added to the load; the curl and dig loop alone missed the gap.
  - CI: two runs, both DNS modes green, 134 passed and 1 skipped each (a bench case for the other DNS mode), about 21.5 minutes of cases per job.
