# 7.2 Acceptance

**Stage:** 7 · **Duration:** 2 d · **Depends on:** 7.1, 1.3 · **Needed for:** 7.3

## Goal
Verify every item of the “MVP acceptance criteria” on a clean VM and fix what is found, so that 7.3 publishes a verified release. Installation from the public repository is verified in 7.3; here it is from the test repository.

## Inputs
- The 0.1.0 release candidate in the test repository (pipeline 1.3) under the package names from design.md, the README from 7.1, green CI suites (2.7, 3.2, 4.2, 5.6–5.8), the manual UI checklist from 6.9, the acceptable recovery time from 5.8.
- A clean VM snapshot from 0.2 with its recorded findings (whether `pkexec` is in a stock forky KDE installation; the VM sleeps in S3 because QEMU does not wake an s2idle guest on the RTC alarm) and the bench from 1.4 (driven over `AF_VSOCK`, bench DNS 203.0.113.1, the RFC 1918 neighbour for the `allow-lan` checks); the hardware test machine with real Wi-Fi (accessed over ssh), if available.
- [design.md](../design.md), sections “MVP acceptance criteria”, “Testing”, “Daemon security”, “Leak protection”, “Network changes and sleep”, “Core supervision and cleanup”.

## Tasks
The acceptance record is a table “criterion → how it was verified → result → link to test or issue”. The items below correspond to the “MVP acceptance criteria”, in the same order.

- [ ] **Installation.** The VM is rolled back to the clean snapshot; installation strictly follows the README, from the test repository. `apt-get install -s plasma-nm-vpn` → the `Inst` lines contain only `plasma-nm-vpn*` packages, plus `pkexec` if 0.2 found it absent from a stock forky KDE installation (the known exception recorded in design.md, “Packages”; the record names it). The “from the public repository” part is marked in the record as handed over to 7.3.
- [ ] **Documents and translation.** The repository contains the README (English and Russian), LICENSE, `SECURITY.md`, and core license information. In the `ru_RU.UTF-8` locale, the forms, validation and import messages, the block banner and the entry names in the “Add VPN” list are in Russian.
- [ ] **Profiles.** For Hysteria2, AmneziaWG and VLESS XHTTP Reality: a profile is created in plasma-nm manually and, separately, by import (a link or `.conf` from the bench); each one connects and disconnects from the applet. Hysteria2 and VLESS profiles, including imported ones, set DNS 203.0.113.1 in the “Protection” block before connecting (with the defaults, 9.9.9.9 is unreachable on the bench and slows the resolver down, and the checks want one known DNS server; the liveness check itself would pass, since it queries 1.1.1.1, which the bench answers). The 6.9 checklist is used.
- [ ] **Secrets and the unprivileged user.** The `.nmconnection` of each profile has no secrets in `[vpn]`; with “Store password for this user only (encrypted)” there are none in `[vpn-secrets]` either. As an unprivileged user: a `.conf` with wg-quick hooks is imported → the hooks are dropped with a warning and never executed; profiles with bad `vpn.data` values (paths in `extra` and `xhttp-extra`, newlines, control characters) → the connection is rejected. In both cases no new root-owned files or processes appear. Scheduled fuzzing runs with no open findings.
- [ ] **Leaks and kill switch.** The VM is driven over `AF_VSOCK` (ssh via systemd-ssh-generator), so the `allow-lan=no` checks do not cut the control channel; the management NIC stays up (never-default, no automatic DNS, no IPv6) and is never disconnected; captures are taken on the bench parent device.
  - A default-route tunnel for each protocol: the capture shows no DNS or IPv6 bypassing the tunnel.
  - With `kill-switch=yes`, the exemptions match design.md, “Leak protection”: DHCP, DHCPv6, ND and MLD pass; the RFC 1918 neighbour is reachable with `allow-lan=yes` and rejected with `allow-lan=no`; DNS (ports 53 and 853) to it is rejected in both cases.
  - After success: `kill -9` of the daemon → the block stays, no direct traffic, `guard-status` lists it; the bench server stopped and the cycle timeout reached → the same.
  - `kill -9` of the core after success, with `kill-switch=yes` and with `kill-switch=no` → the reconnect cycle restores the connection on the persistent TUN, and no IPv4 leaves directly via the parent device meanwhile (where 0.4/0.6 found that a core cannot attach to a persistent TUN, the temporary block chain from design.md, “Network changes and sleep”, gives the same result).
  - A profile with kill switch and an error (wrong key) → the connection fails, the network is not blocked.
- [ ] **Network changes and sleep.** In the VM: switching Wi-Fi ↔ Ethernet (Wi-Fi emulated with `mac80211_hwsim` and `hostapd`), and sleep as a real `systemctl suspend` (S3) woken by `rtcwake`, as set up in 0.2 and 1.4 (logind itself emits `PrepareForSleep`; no emulated signal is used) → the connection recovers within the time from 5.8. On the hardware test machine, if available (over ssh): switching between real Wi-Fi and Ethernet and a real suspend with wake-up, with the same limit. Without the machine, the record states that Wi-Fi was verified by emulation and sleep only in the VM (or not at all, under the 0.2 limitation).
- [ ] **No leftovers.** `ip link` (including the persistent `pnv-*` TUN), `ip route`, `ip -6 route`, `nft list table inet plasma_nm_vpn`, `systemctl list-units 'plasma-nm-vpn-*'`, processes of the `plasma-nm-vpn` user, `/run/plasma-nm-vpn/` and the AmneziaWG UAPI sockets in `/run/amneziawg/` are checked:
  - after `nmcli connection down` → nothing of ours remains;
  - after `kill -9` of the daemon → nothing remains except the kill switch chains and the `guard-status` entry in the cases described in “Leak protection”; `/run/plasma-nm-vpn/<uuid>/` is removed by `plasma-nm-vpn-guard --daemon-gone <uuid>` from the guard unit;
  - after `kill -9` of the core after success → the connection recovers; after the following `nmcli connection down` → nothing remains.
- [ ] Every discrepancy is an issue; a fix, a new candidate build and a rerun of the affected items. If a fix does not fit into the duration, it is moved to a separate milestone rather than stretching this one.

## Deliverables
- The acceptance record (for example, `docs/acceptance-0.1.0.md` or an issue with a checklist) with links to CI runs.
- The fixes included in the 0.1.0 candidate.

## Done when
- [ ] Each of the seven “MVP acceptance criteria” → marked as met in the record, with the verification method stated; installation from the public repository is marked as handed over to 7.3.
- [ ] Wi-Fi ↔ Ethernet and sleep → recovered within the 5.8 time in the VM (emulated Wi-Fi, real S3 suspend woken by `rtcwake`) and, if the hardware test machine is available, on it with real Wi-Fi and real suspend; the record names the method for each.
- [ ] The final candidate on a clean VM snapshot → all record items pass again without changes.
- [ ] CI on the final candidate → all suites green.

## Risks and notes
- Network experiments are done only in the VM, in CI or on the hardware test machine, not on a work machine.
- Detection of a stopped server takes about three minutes for the proxy cores and up to about five for AmneziaWG, plus the cycle timeout: allow for it when scheduling the block checks.
- If a fix affects the architecture, the decision is first recorded in design.md and then implemented in the code.
