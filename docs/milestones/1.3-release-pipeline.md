# 1.3 Release pipeline

**Stage:** 1 · **Duration:** 2 d · **Depends on:** 1.2, 0.9 · **Needed for:** 7.1, 7.2, 7.3

## Goal
Build the path from a tag to a signed apt repository in the release assets so that the signing key is available to only one job, after manual approval. Releasing 0.1.0 in 7.3 then comes down to running a ready pipeline.

## Inputs
- .deb files from the `packages` job (1.2); findings of 0.9 on the flat repository: the asset renaming rule, the commands for generating `Packages` and `InRelease` and the index compression decision, verified in the VM. 7.1 and 7.2 install from the test repository this pipeline publishes to.
- [design.md](../design.md), section “Distribution and supply chain”: repository rules (draft, unchanged packages from the previous release with sha256 verification, rehearsals in a test repository, the URI in `.sources` from the repository name, `Filename:` from the final names, no `Acquire-By-Hash`), CI, core licenses (sources of GPL cores with `go mod vendor`).
- [design.md](../design.md), section “Packages”: installation order via `plasma-nm-vpn-archive-keyring`; paragraph “Removal and upgrades”: a core-only release (for example `0.1.0+sb1.14.5`) is built from the release branch of the current project version, not from `main`.

## Tasks
- [x] Test repository: mirror the project code and workflows into `alldevic/plasma-nm-vpn-test` from 0.9 (a script that pushes the current branch and tags there, so the rehearsal runs exactly the workflows under review), and set up its Environment `release` with mandatory manual approval and the test key from 0.9 as its secret. The URI in `plasma-nm-vpn-archive-keyring` comes from `GITHUB_REPOSITORY` (1.2), so packages built there point at the test repository.
- [x] Signing key: create it outside CI; only the public part goes into the project repository (in `plasma-nm-vpn-archive-keyring`), the private part is a secret of the GitHub Environment `release` with mandatory manual approval. For this milestone's test, a separate test key and the test repository from 0.9.
- [x] The `release.yml` workflow on a `v*` tag, jobs run in sequence, each with its own minimal `permissions`:
  1. `build` — packages as in 1.2, no secrets;
  2. `attest` — provenance attestations for each .deb (`actions/attest-build-provenance`, pinned by SHA; permissions `id-token: write`, `attestations: write`);
  3. `sign` — `environment: release`; builds the index and signs it, and does nothing else;
  4. `publish` — `contents: write`, no access to the key.
- [x] Release file set: the package list is taken from `debian/control` (the sing-box package name may change in 7.1), and every package is built. Carry-over rule: any package whose name and version already appear in the previous release's `Packages` has its fresh build discarded; the previous asset is downloaded (`gh release download`) and its sha256 checked against that `Packages`, which itself is checked against the previous `InRelease` verified with the project key. A mismatch fails the pipeline. This way a package with the same version never gets different contents, which would break apt clients; only packages with a new version are taken from the fresh build. First release: when the repository has no published release at all (the API reports none, as opposed to an error fetching one), there is no previous `Packages`, nothing is carried over and every package comes from the fresh build; the log states this explicitly. Any other failure to get the previous release, its `Packages` or `InRelease` fails the pipeline rather than falling back to the first-release path.
- [x] Asset names: files are renamed in advance per the rule from 0.9 (no `~` or `+`); `Packages` is generated from the final names (`apt-ftparchive packages`), compressed per the 0.9 decision (for example, `Packages` plus `Packages.xz`), then `Release` and `InRelease` (`gpg --clearsign`). Do not enable `Acquire-By-Hash`.
- [x] Sources of GPL cores in every release: source archives of sing-box (from the pinned tag, with the `vendor/` directory after `go mod vendor`) and amneziawg-tools of the same versions as in the packages; names without `+`. If vendoring changes from run to run, the archive is made once per core version and carried over into subsequent releases the same way as unchanged .deb files.
- [x] Publication: `gh release create --draft`, upload all files, compare asset names from `gh release view --json assets` with `Filename:` in `Packages`, and verify the uploaded `InRelease` with `gpgv` against the keyring shipped in `plasma-nm-vpn-archive-keyring` (0.9: a client that once fetched a wrongly signed `InRelease` can stay stuck even after a fixed release); only if both pass, `gh release edit --draft=false`. On a mismatch the draft stays and the job fails.
- [x] README: after a release, `apt update` may fail once with “Hash Sum mismatch” for about two minutes (0.9, GitHub's redirect cache) — retry; and the recovery command for a stuck signature error, `sudo rm /var/lib/apt/lists/partial/*plasma-nm-vpn*`.
- [x] Core-only releases: each project version has a release branch (for example `release/0.1`); a core-only release is tagged on it, so the rebuilt core package is built against the same sources as the published `plasma-nm-vpn-common`, and the unchanged packages are carried over from the previous release with the sha256 check. `release.yml` refuses a tag that is not on `main` or a release branch; choose the tag naming for core-only releases and record it in design.md.
- [x] `plasma-nm-vpn-archive-keyring` is also attached to the release as a separate file — it is downloaded manually following the instructions.

## Deliverables
- `release.yml`, scripts for building the index and checking assets, the script that mirrors the project into the test repository.
- The Environment `release` with an approval rule in the test repository (test key) and in the main repository (project key, used first in 7.3).
- A test release in the test repository.

## Done when
- [x] A tag in the test repository → the pipeline stops at `sign` until manual approval; after approval a published release appears.
- [x] In a clean VM from 0.2: download `plasma-nm-vpn-archive-keyring` from the release page, `apt install ./…deb`, `apt update` without signature warnings, `apt install plasma-nm-vpn` installs all core packages.
- [x] `gh attestation verify <file>.deb --repo alldevic/<repo>` → verification passes for each .deb.
- [x] First release: the test repository emptied of all releases (and their tags) → a tag → the pipeline log states that there is no previous release and nothing is carried over, the release contains every package from the fresh build, and it installs in a clean VM as above. The later checks build on this release.
- [x] A second test release with one package changed → it again contains all current packages, and `apt upgrade` in the VM updates only the changed one.
- [x] A core-only rehearsal: a tag on the release branch with a changed core pin → the pipeline log shows the fresh builds of every package whose name and version are already in the previous `Packages` (including `plasma-nm-vpn-common`) discarded and the previous assets carried over; their sha256 matches the previous `Packages`; the release contains the new core package; `apt upgrade` in the VM updates only the core package.
- [x] Tamper with a carried-over asset in the previous test release (re-upload a different file under the same name) → the next release run fails at the sha256 check and nothing is published.
- [x] A PR to the test repository cannot see the key secret (it is absent from the PR build job's log, and `sign` does not run from a PR).

## Risks and notes
- A release in the main repository immediately becomes `releases/latest`, so test releases are made only in the test repository; the first publication in the main one is milestone 7.3.
- A compromise of CI or the key gives root on users' machines: no third-party actions in the `sign` job beyond what is necessary; key rotation via a new version of `plasma-nm-vpn-archive-keyring`.
- How apt handles GitHub redirects on forky and the asset limits have already been established in design.md and 0.9; no need to recheck.
- Emptying the test repository for the first-release check deletes the 0.9 rehearsal releases (`v0.0.1`–`v0.0.2`); their results are already recorded in design.md and the 0.9 note, so nothing is lost. 7.3 relies on the first-release path: 0.1.0 is the first release of the main repository.
- Results (rehearsed in `alldevic/plasma-nm-vpn-test`): `v0.1.0` from an emptied repository — the `sign` log says “no previous release … first release, nothing is carried over”, the run waited at `sign` until approved, all six packages verify with `gh attestation verify`, and a clean VM installs the keyring from the release page, then `plasma-nm-vpn` without warnings. With our versions only a core pin changes one package alone (a new project version changes every package), so the second release was the core-only `v0.1.0-sb1.14.5` from `release/0.1` (sing-box 1.14.5): five packages and the amneziawg-tools source carried over with digests equal to `v0.1.0`, only `plasma-nm-vpn-sb` and the sing-box source fresh, `apt upgrade` in the VM updated only `plasma-nm-vpn-sb`. A re-uploaded `plasma-nm-vpn-common` in `v0.1.0` failed the next run at “sha256 differs from its Packages” with nothing published. A PR ran only `build` and `packages`, with no trace of the key. Found on the way: a tag pushed together with the commit that first brings the workflows into a repository does not start `release`; pushing the tag again does. The GPL sources stay in the release (sing-box ~180 MB with `vendor/`, carried over per core version).
