# 1.4 Integration test bench in CI

**Stage:** 1 · **Duration:** 2 d · **Depends on:** 1.1, 1.2, 0.3, 0.7 · **Needed for:** 2.5, 2.7, 3.2, 4.2, 5.6, 5.7, 5.8

## Goal
Get a reproducible forky environment in GitHub Actions with systemd, NetworkManager and the server bench, where integration tests run on every PR. Without it, the tests of stages 2–5 would have to be run by hand in a VM.

## Inputs
- The server bench scripts from 0.3 (network namespace, veth, hysteria2 on sing-box, VLESS XHTTP Reality on xray, AmneziaWG on amneziawg-go, the “ISP” DNS at 192.0.2.1 with `srv.stand.test` and the AAAA-only `srv6.stand.test`, the server's IPv6 address 2001:db8:100::1, the RFC 1918 neighbour 192.168.77.1, the tunnel-side DNS 203.0.113.1, which also serves the server names) and the plugin prototype from 0.7.
- The repository skeleton and `build.yml` from 1.1.
- [design.md](../design.md), section “Testing”: a forky VM under KVM on a standard Linux runner after a udev rule for `/dev/kvm`; the fallback is a privileged container with systemd (`--privileged --cgroupns=host`); the test VM driven over `AF_VSOCK` (ssh via systemd-ssh-generator), with its management NIC up but never-default, without automatic DNS and without IPv6, as the one deliberate exception to the bench address rules; the bench's client veth explicitly managed by NM; Wi-Fi emulated via `mac80211_hwsim` and `hostapd`; DNS tested both in Debian's default `resolv.conf` mode (systemd-resolved is not installed by default) and with systemd-resolved; sleep tested with a real `systemctl suspend` in s2idle mode woken by `rtcwake`; the sleep and Wi-Fi tests run only in the KVM variant; test hooks only in a never-packaged test build.
- The vsock ssh setup and the s2idle setting from 0.2.
- [plan.md](../plan.md), stage 0: the 0.3 bench is product code, the 0.7 prototype is a temporary CI payload, removed in 2.7.

## Tasks
- [ ] Enable KVM on the runner: a udev rule for `/dev/kvm` (`KERNEL=="kvm", GROUP="kvm", MODE="0666"`), `udevadm control --reload-rules`, `udevadm trigger --name-match=kvm`.
- [ ] VM image: a Debian forky cloud image (check availability and path on cloud.debian.org) or a `mmdebstrap` build; in the image — everything the system under test and the 0.3 bench use: `network-manager`, `nftables`, `iproute2`, `tcpdump`, `bind9-dnsutils` (`dig`), `dnsmasq-base`, `python3` (HTTP server), `curl`, `openssl` (Reality `target`), `hostapd`, `iw`, `pkexec`, `openssh-server` (compare against the commands in the bench scripts; a missing tool is a red run, not a skip); check that the image's kernel has the `mac80211_hwsim` module (`modprobe mac80211_hwsim radios=2`): cloud images have a trimmed kernel; if the module is missing, install `linux-image-amd64`. The image stays in the default `resolv.conf` mode (no systemd-resolved); a second variant differs only by the installed `systemd-resolved`. Cache both images (`actions/cache`, key — the hash of the image build script).
- [ ] Startup: `qemu-system-x86_64 -enable-kvm -nographic`, a disk overlay on top of the cached image, a vsock device (`-device vhost-vsock-pci,guest-cid=<N>`; the runner needs `/dev/vhost-vsock`, so add it to the udev rule above and load `vhost_vsock` if needed), cloud-init (or equivalent) for the SSH key. The harness reaches the VM only over vsock (`ssh vsock/<N>` via `systemd-ssh-proxy`, or `socat VSOCK-CONNECT` as a ProxyCommand if the runner's systemd is too old), never over IP, so that kill switch tests with `allow-lan=no` cannot cut it. The VM keeps a management NIC (QEMU user networking); the image configures it with `ipv4.never-default yes`, `ipv4.ignore-auto-dns yes`, `ipv6.method disabled`, the same as in 0.3, and the bench never disconnects it. A wrapper `tests/integration/vm.sh` with the commands `up`, `ssh`, `copy`, `down`.
- [ ] Bench in the VM: the 0.3 scripts move to `tests/integration/stand/` and are brought to the form “start/stop with one command, non-zero exit code on error”. This is not a prototype but part of the tests: the code is improved, not rewritten. The bench DNS at 203.0.113.1 (and on 1.1.1.1, for the never-default liveness check) answers queries for `stand.test`, for the root zone and for `srv.stand.test`/`srv6.stand.test` with the “ISP” records, so that a second profile resolves its server through a first tunnel (0.3): it is the DNS server of the test profiles and the target of the liveness check from 5.4. The `stand` profile sets the “ISP” DNS 192.0.2.1, so the system resolver finds `srv.stand.test` before a tunnel is up. Every test profile through which names are resolved uses `dns=203.0.113.1`; profiles without `dns` exist on purpose (2.4, 5.4). The client veth is explicitly put under NM management (`nmcli device set <veth> managed yes` or a file in `/etc/NetworkManager/conf.d/`), otherwise it will not become the VPN's parent device; check with `nmcli -g GENERAL.STATE device show <veth>`.
- [ ] Cores for the bench come from the same place as for the packages (`cores/` from 1.2, sha256 check), not downloaded separately.
- [ ] Test format: a `tests/integration/cases/` directory, one executable script per test, exit code 0 means success; the runner `tests/integration/run.sh` brings up the VM and the bench, runs all cases and collects a report. The choice between shell and pytest follows the findings of 0.3/0.7, but it is one choice for the whole project.
- [ ] The first test, `smoke-nmcli`: the 0.7 prototype is built and installed in the VM, a `.nmconnection` to the bench's hysteria2 server, `nmcli connection up`, a check of traffic to an address behind the server. The prototype lives in `tests/integration/smoke/` marked “remove in 2.7”.
- [ ] On test failure — artifacts: `journalctl -b`, `nmcli -f all connection show`, `nft list ruleset`, `ip addr`/`ip route` from the VM.
- [ ] The `integration.yml` workflow on `pull_request`, a matrix over the DNS mode (`resolvconf`, `resolved`; `run.sh --dns-mode`), `timeout-minutes`, permissions `contents: read`, actions pinned by SHA. Sleep: the image forces s2idle (`mem_sleep_default=s2idle` on the kernel command line or `MemorySleepMode=s2idle`, whichever 0.2 chose), the VM gets an emulated RTC and must suspend and wake by `rtcwake` (as checked in 0.2); `vm.sh` treats the VM as asleep, not dead, while it waits. If KVM does not work on the runner — the same harness on a privileged container with systemd (driven with `docker exec`, no vsock needed); record the decision in design.md.
- [ ] `/dev/vhost-vsock` on the runner (design.md, “Verify on a prototype (stage 0)”, item “Is `/dev/vhost-vsock` available on standard GitHub runners”): check whether the device exists on a standard GitHub Linux runner, after `modprobe vhost_vsock` if needed, and whether QEMU starts with `-device vhost-vsock-pci` and the harness reaches the VM over it; record the runner image and date. Update design.md: close the item in “Open questions and risks”, or, if vsock is not available, record the replacement non-IP control channel chosen here (for example a virtio-serial console) and correct section “Testing”. In the container variant (no VM) the harness uses `docker exec` and the question does not arise; record that too.
- [ ] Test capabilities: each case declares what it needs (`needs: kvm` for sleep and Wi-Fi, since they depend on the VM's own kernel; `needs: test-build` for cases that use test hooks); in the container variant the runner reports `kvm` cases as skipped by name, never as passed.

## Deliverables
- `tests/integration/` (VM harness, bench, runner, the `smoke-nmcli` test), the image build script, `integration.yml`.
- In design.md: the chosen option (KVM or container) and the run time; the closed `/dev/vhost-vsock` item (or the replacement control channel).

## Done when
- [ ] PR → `integration.yml` is green in both DNS modes; the log shows the test “the 0.7 prototype brings up the tunnel via nmcli” passed.
- [ ] Break the server address in the test's `.nmconnection` → the run is red, artifacts with the journal are attached.
- [ ] In the VM, after the bench starts, `nmcli device` shows the client veth in the `connected` state (managed by NM), `ip netns exec stand dig @203.0.113.1 . SOA` gets an answer, `getent ahosts srv6.stand.test` returns only 2001:db8:100::1, `ping -6 2001:db8:100::1` and `curl http://192.168.77.1/` succeed without a tunnel; in the KVM variant only (skipped in the container fallback, where they depend on the runner's kernel), `modprobe mac80211_hwsim` succeeds, `/sys/power/mem_sleep` shows `[s2idle]`, and `rtcwake -m no -s 20 && systemctl suspend` returns the VM to a working vsock ssh session (or the limitation is recorded in design.md); the default routes and system DNS are only those of the client veth, and the management NIC is up with no IPv6 address; in the `resolved` variant `resolvectl status` works, in the default one `/etc/resolv.conf` is written by NM.
- [ ] A repeated run takes the image from the cache; the run time is recorded.
- [ ] The `/dev/vhost-vsock` item in design.md is closed with the runner image and date, or the design names the replacement non-IP control channel and the harness uses it.
- [ ] With the bench up, a temporary nftables rule in the VM that drops all IPv4 and IPv6 output except loopback leaves the harness's ssh session working (it goes over vsock); the rule is removed afterwards.

## Risks and notes
- A container runs on the runner's kernel (Ubuntu), not forky's: nftables and TUN behavior may differ, so KVM is preferable. The sleep and Wi-Fi cases are skipped there.
- If `/dev/vhost-vsock` is not available on the runner, record it and raise a design change before 5.6: the kill switch tests with `allow-lan=no` need a control channel that does not use IP.
- The network change tests (5.5, 5.8) will need a second client interface: Wi-Fi via `mac80211_hwsim` and `hostapd`. Here only the image is prepared (package and module); the scenarios themselves are stage 5. In the container option the module depends on the runner's kernel — another argument for KVM.
- The 0.7 prototype is used temporarily as a test payload and does not become part of the product.
- All network experiments happen only in CI, in the test VM from 0.2 or on a separate hardware test machine, never on a work machine.
