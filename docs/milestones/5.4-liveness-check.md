# 5.4 Liveness check

**Stage:** 5 · **Duration:** 2 d · **Depends on:** 5.1, 5.2, 5.3, 2.4, 3.1 · **Needed for:** 5.5

## Goal
The daemon checks the tunnel end to end after activation and while the connection is up. sing-box and xray create the TUN without contacting the server, and an AmneziaWG interface comes up without a handshake, so without this check a wrong password or key or a dead server goes unnoticed: the connection is ACTIVATED and, with the kill switch, would fail closed. From this milestone on, a session succeeds only when it is ACTIVATED and has passed the check.

## Inputs
- The success marker (with the cache write), the give-up flag and the kill switch rules from 5.1; the inherited-block and takeover rules from 5.2; the `guard-status` entries from 5.3; network parameters and the profile DNS servers from 2.4; the first-handshake trigger and the handshake-reading function from 3.1 (recorded in design.md).
- [design.md](../design.md), section “Core supervision and cleanup” (item “Liveness check”), sections “Goals and requirements” (the check as the one extra network destination), “Leak protection” (item “Kill switch lifecycle”), “DNS”, “Network changes and sleep”.
- The server bench (0.3, 1.4): the bench DNS 203.0.113.1 behind each server answers a root zone query through the tunnel, and the same instance answers on 1.1.1.1, which is reachable only through the tunnel; 9.9.9.9 does not exist on the bench.

## Tasks
- [ ] sing-box and xray: a DNS query for the root zone to the profile's first DNS server, from a UDP socket bound to the TUN (`SO_BINDTODEVICE` on `pnv-…`). Any well-formed answer with the matching ID counts. The query goes into the tunnel, so the DNS and IPv6 guard and the kill switch let it through.
- [ ] Never-default without `dns`: the check queries `1.1.1.1` the same way. No route to it is added and it is not passed as a DNS server: a route would hijack `1.1.1.1` for another connection that uses it as DNS. This is the one extra destination allowed by design.md. Default-route tunnels with empty `dns` use the first default, `1.1.1.1`, as usual.
- [ ] Verify in the VM that a socket bound with `SO_BINDTODEVICE` reaches a target that has no route via the TUN (never-default, `1.1.1.1`): the kernel sends the query out of `pnv-…`, `ip route get 1.1.1.1` still points at the parent device, and nothing goes to 1.1.1.1 on the physical interface. If the kernel refuses or misroutes it, stop and raise it against design.md rather than add a route.
- [ ] Reverse path filter: the reply arrives on `pnv-…` while the route back to 1.1.1.1 points at the parent device, so strict `rp_filter=1` would drop it. Verify the reply with `net.ipv4.conf.all.rp_filter` and `default` set to 1 (strict) and to 2 (loose). If strict mode drops it, the daemon sets `rp_filter=2` on our TUN when it creates it (the kernel uses the higher of the `all` and per-interface values), and the TUN only. Record the result in design.md, item “Liveness check”.
- [ ] AmneziaWG: the first handshake, using the 3.1 trigger and handshake-reading function. No handshake within the check timeout → give-up; this replaces the journal-only behaviour of 3.1.
- [ ] The check runs right after ACTIVATED, with retries within its own timeout. Passed → the success call from 5.1 (success marker, cache) moves here. Not passed → give-up; without the marker, the kill switch chains of this attempt are removed and no `guard-status` entry is written (5.1, 5.3); an attempt on inherited chains keeps them (5.2).
- [ ] The check timeout is a compiled-in value in the packaged daemon. Only the test build (`-DPNV_TEST_HOOKS=ON`, 2.1) has a test hook that overrides it (for example, a value read from a file the harness writes); 6.2 uses it to raise the timeout to 120 s and hold an attempt open. The packaged daemon contains no such hook (the 2.1 check).
- [ ] Periodic check every 60 s while the connection is up. For AmneziaWG, the daemon first nudges the tunnel with the 3.1 trigger (WireGuard renews handshakes only when there is traffic, so an idle tunnel would otherwise look dead), then compares the age of the last handshake against a threshold derived from the profile's rekey and keepalive parameters (`keepalive` and the AWG 3.0 timing keys); without them the default is above WireGuard's 2-minute rekey interval with a margin.
- [ ] Choose the check timeout and the derivation of the handshake-age threshold so that a stopped server is detected in about three minutes for the proxy cores and in about five to six minutes for AmneziaWG; derive the exact AmneziaWG bound from the threshold and record the timeout, the threshold rule and the bound in design.md, section “Core supervision and cleanup”.
- [ ] Three failures in a row → the reconnect cycle (5.5). Until 5.5 exists: give-up; the success marker is present, so the kill switch chains remain and `guard-status` gets the entry.
- [ ] Every failed check goes to the journal with the reason (timeout, no answer, handshake age and threshold) and the target address.
- [ ] Unit tests of the scheduler (counter reset after a success, three failures in a row, the AmneziaWG threshold from different rekey and keepalive values, the nudge before each check) with a fake clock; manual check in the VM for all three protocols.

## Deliverables
- The liveness check and its scheduler in `plasma-nm-vpn-common`, with the per-core part (DNS query, or nudge and handshake age) chosen by the daemon.
- The check timeout, the handshake-age threshold rule and the AmneziaWG detection bound in design.md; the `SO_BINDTODEVICE` and `rp_filter` findings in design.md, item “Liveness check”; the timeout override hook in the test build.

## Done when
- [ ] Hysteria2 with a wrong password, VLESS with a wrong `uuid`, AmneziaWG with a wrong key, and all three protocols with the bench server stopped before connecting, each with `kill-switch=yes` → ACTIVATED, then give-up within the check timeout; no kill switch chains, no `guard-status` entry, no cache written, the network works directly.
- [ ] A working connection, then the bench server is stopped → detected within about three minutes (proxy cores) or within the recorded bound of about five to six minutes (AmneziaWG), give-up; with the kill switch the chains remain and `guard-status` shows the block.
- [ ] A never-default proxy-core profile without `dns` → no route to 1.1.1.1 via `pnv-…`, 1.1.1.1 is not in the system DNS configuration, the check passes, and its query appears on `pnv-…` but not on the physical interface; it passes with `rp_filter` 1 and with 2 in `all` and `default`.
- [ ] In the test build, the override raises the check timeout to 120 s: with the server port dropped in netns `stand` (no answer, not even an ICMP error), an attempt stays ACTIVATED without success for about 120 s, then gives up; the packaged daemon uses its compiled-in timeout.
- [ ] A working tunnel left idle for 10 minutes (AmneziaWG also without `keepalive`, and with non-default AWG timings) → no failed checks in the journal.

## Risks and notes
- On the bench, test profiles set `dns=203.0.113.1` (the 0.3 rule). 9.9.9.9 is unreachable there; 1.1.1.1 answers through the tunnel and is kept for the never-default check and the two-connection case of 5.7 (a never-default profile without `dns` next to a default-route profile with empty `dns`, whose DNS on 1.1.1.1 must not be taken over).
- The never-default check sends one query to 1.1.1.1 per minute through the tunnel; it is an accepted extra destination, listed in design.md, “Goals and requirements”.
- If the profile's first DNS server does not answer through the tunnel while traffic flows, the check gives a false failure. Not changed in the MVP; the journal names the server.
