# 2.7 Hysteria2 integration tests

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 2.4, 2.5, 2.6, 1.4 · **Needed for:** 3.1

## Goal
Lock in the outcome of the stage — “Hysteria2 works via `.nmconnection` and `nmcli`” — with a test suite that runs in CI on every pull request. The suite becomes the model for AmneziaWG (3.2) and xray (4.2), and in stage 5 it is extended with resilience tests.

## Inputs
- The integration test bench in CI from 1.4 (a forky VM under KVM or a privileged container with systemd, the 0.3 bench: servers on 198.51.100.1 and 2001:db8:100::1, the “ISP” DNS 192.0.2.1 with `srv.stand.test` and the AAAA-only `srv6.stand.test`, the tunnel DNS 203.0.113.1, the LAN neighbour 192.168.77.1) and its harness with the temporary test on the 0.7 prototype.
- The sing-box daemon with all its parts: 2.3 (launch, guard unit, re-activation rules), 2.4 (network parameters), 2.5 (config), 2.6 (DNS and IPv6 guard); the verification scripts from those milestones; the `prerm` scripts from 1.2.
- [design.md](../design.md), section “Testing”: the list of integration checks; all network experiments only in a VM, CI or on a hardware test machine.
- [design.md](../design.md), subsections “Route to the server” and “DNS”; section “MVP acceptance criteria”: what “no traces left” means.

## Tasks
- [x] Test `.nmconnection` profiles (0600, in `/etc/NetworkManager/system-connections/`, followed by `nmcli connection reload`): `service-type=org.freedesktop.NetworkManager.pnv.hysteria2`, `vpn.persistent=yes`, `server=srv.stand.test`, secrets in `[vpn-secrets]`; default-route tunnel and never-default. `ipv4.dns-priority` is not set. The suite installs the daemon from the `packages` job's .deb files (1.2).
- [x] Test build: the few cases that need test hooks (the 2.3 dummy chain, the 2.1 slow cleanup step, holding the daemon before `Ip4Config`) declare `needs: test-build` (1.4); the harness builds the daemons with `-DPNV_TEST_HOOKS=ON` (2.1) and puts them in place over the packaged binaries only for those cases (for example, a bind mount over the daemon path, removed afterwards), never through a .deb. All other cases, including package removal, run against the packaged daemons.
- [x] DNS in tests: the test bench has no internet, so every test profile through which names are resolved sets `dns=203.0.113.1` before connecting; from 5.4 on it is also the target of the liveness check. Profiles without `dns` exist on purpose: the defaults (1.1.1.1, 9.9.9.9) are checked only at the NM level (2.4), and the never-default case without `dns` is covered below. Secrets are passed with `nmcli connection up … passwd-file` where a profile does not store them. Every DNS-related test runs in both DNS modes from 1.4.
- [x] A shared “no traces left” function: no `pnv-*` interfaces, no routes via them and no /32 or /128 to the server; no chains for this UUID in `inet plasma_nm_vpn`; no `plasma-nm-vpn-core-*` and `plasma-nm-vpn-guard-*` units and no `plasma-nm-vpn-daemon-*` scopes (`systemctl list-units --all`); no processes of the `plasma-nm-vpn` user and no daemon process; no `/run/plasma-nm-vpn/<uuid>/` and no /30 reservation for this UUID. It waits for the daemon process to exit before checking.
- [x] Test “connection and traffic”: `nmcli connection up` → ACTIVATED; an HTTP request to `http://stand.test/` (reachable only through the bench server) succeeds; names resolve through the tunnel; the core process runs as `plasma-nm-vpn`. Separately, a profile with port hopping.
- [x] Test “name resolution”: `srv.stand.test` (A and AAAA) → `gateway`, the core config and the route all use 198.51.100.1; after the session `/var/lib/plasma-nm-vpn/<uuid>` holds it.
- [x] Test “cached-IP fallback”: after a successful session, stop the “ISP” DNS (or remove the record) and connect again → after the 5 s resolution timeout the daemon uses the cached server IP, the tunnel comes up, the journal says so. Without a cached file, or with one whose stored `server` differs from the profile's, the same attempt fails `Connect` with a clear reason before any chains, TUN or core unit are created (a `Connect` error, not a give-up). A profile with an IP literal in `server` connects without any DNS query.
- [x] Test “AAAA-only server”: `server=srv6.stand.test` → `gateway` and the IP in the core config are 2001:db8:100::1, NM sets the route to it via `stand-cli`, traffic flows, and the IPv6 guard does not reject the core's own IPv6 traffic.
- [x] Test “DNS and IPv6 leaks”: with a default-route tunnel, `tcpdump` on `stand-cli` during DNS queries and IPv6 connection attempts → no packets to 53/853 and no IPv6 other than link-local/multicast and neighbour discovery; a query to the “ISP” DNS 192.0.2.1 fails immediately; the `forward` hook test from 2.6 (test netns, masquerade, reject counter).
- [x] Test “two connections”: a default-route tunnel plus a second connection with a route to 203.0.113.1 → traffic and DNS routed into the second tunnel pass, nothing is rejected by the first one's chains.
- [x] Never-default tests: no default route via `pnv-…`, no guard chains, the route to the server via the parent device exists; with `dns=203.0.113.1` a /32 route to it via `pnv-…` and no other DNS added; with empty `dns` no DNS servers on `pnv-…`.
- [x] Test “cleanup after `Disconnect`”: `nmcli connection down` → “no traces left”, including a dummy chain owned through the synchronous `disconnect` (the 2.3 test hook).
- [x] Test “`kill -9` of the daemon”: NM tears down the connection, systemd stops the core and the guard unit, whose `plasma-nm-vpn-guard --daemon-gone` removes the DNS/IPv6 chains and `/run/plasma-nm-vpn/<uuid>/` → “no traces left”.
- [x] Test “`kill -9` of the core”, only before success: in the test build, a hook holds the daemon after the core has attached and before `Ip4Config` is sent; `kill -9` of the core then → the daemon gives up, the connection fails, the daemon's journal contains the reason and the unit name → “no traces left”. After-success behaviour (recovery via the reconnect cycle, no teardown) is not tested here: it is added from 5.6, which also updates the 3.2 and 4.2 suites.
- [x] Re-activation and collision tests from 2.3 (stalled previous instance: takeover marker placed and removed on timeout; normal re-activation; UUID prefix collision; a reconnect right after `kill -9` of the daemon waits for the old guard unit) as cases of the suite.
- [x] Test “package removal”: with a Hysteria2 connection up, `apt remove plasma-nm-vpn-sb` → the connection is deactivated, the `prerm` waits for the daemon scope to go away (its log shows the wait ending before the timeout), “no traces left”; `apt remove plasma-nm-vpn-common` with a hand-made chain in `inet plasma_nm_vpn` → no table and no `guard-status`.
- [x] A repeated `nmcli connection up` after each failure scenario succeeds.
- [x] Attack vectors via `nmcli`: a newline in `server`, `tls-sni` and the password (via `nmcli connection modify … vpn.data`/`vpn.secrets`), a file path and `detour` in `extra` → `nmcli connection up` fails, no core unit was created, and the journal contains the rejection reason.
- [x] Remove the temporary test on the 0.7 prototype and the prototype itself from CI; the Hysteria2 suite takes its place.
- [x] Enable the suite in CI on every pull request; on failure, save as artifacts the NM, daemon, core and guard unit journals, the output of `nft list ruleset` and the `tcpdump` capture.

## Deliverables
- The Hysteria2 integration test suite and test profiles in the repository, a CI step with artifacts on failure.
- Shared check functions (traces, leaks, attack vectors, name resolution) suitable for 3.2 and 4.2.
- The 0.7 prototype removed from the repository and CI.

## Done when
- [x] A pull request in CI → the Hysteria2 suite passes in full, in both DNS modes.
- [x] A deliberate breakage (for example, disabling the DNS rule in the 2.6 template, or making the daemon prefer AAAA) → the corresponding test fails.
- [x] A repeated run of the same commit → the result is stable (no flaky tests).
- [x] There are no CI steps referring to the 0.7 prototype.

## Risks and notes
- In the container variant of the test bench (without a VM), the behavior of systemd-resolved, scopes and nftables may differ from a real machine; if a test passes in only one variant, record this in the notes of 1.4.
- Without a negative `ipv4.dns-priority`, the resolver may also send queries to the parent device's DNS servers (here the “ISP” DNS 192.0.2.1); the guard rejects them and they fail fast (design.md, section “DNS”). The test checks that nothing leaves the physical interface.
- The kill switch, the liveness check, reconnect, recovery after a core crash, network changes and sleep are stage 5 (tested in 5.6–5.8) and are not tested here. Until 5.4, “success” is ACTIVATED, so the cached-IP test does not depend on the liveness check.
- Results:
  - The suite: `tests/integration/cases/test_30_daemon.py` … `test_34_hysteria2.py` and `test_80_packages.py`, with shared helpers in `cases/helpers.py`:
    - `keyfile()`: test `.nmconnection` files, 0600, `vpn.persistent=true`;
    - `no_traces()`;
    - `journal()`, which runs `journalctl --sync` first.
    - Bench profiles set `dns=203.0.113.1` unless a case is about empty `dns`. Attack vectors via `nmcli connection modify`; nmcli does not store a secret with a newline, so that vector goes in through the keyfile.
  - CI (`integration.yml`):
    - The workflow builds the .deb files and the test build (`-DPNV_TEST_HOOKS=ON`, a DESTDIR tree) in a forky container, with `check-no-test-hooks` on the .deb files.
    - `guest/prepare` installs `plasma-nm-vpn-common` and `-sb` from the .deb files. Cases marked `test_build` run with the test binaries bind-mounted over the packaged daemon and guard, unmounted lazily afterwards; cases marked `packages` need the packages installed.
    - The CI image now carries `plasma-nm` and `libjson-glib-1.0-0`, so the packages install offline once the bench owns the network. A `tcpdump` of `stand-cli` for the whole run and the journal, ruleset, addresses and routes are kept as artifacts on failure.
  - Package removal: `apt remove plasma-nm-vpn-sb` with a connection up runs the `prerm`. `deactivate-connections` now logs “brought down <uuid>, cleaned up after N s” when its wait ends, and the case checks that line and “no traces left”. `apt remove plasma-nm-vpn-common` then leaves no table and no `guard-status`.
  - `kill -9` of the core before success uses the test hook `hold-before-config` (the daemon holds `Ip4Config` for 20 s with the core supervised): the daemon gives up naming the unit, no traces, the next `up` works.
  - Found on the way to green CI:
    - `apt-get install --no-download` with local .deb files fails (“Pathname to install is not absolute”);
    - systemd-resolved served the name from its cache in the “no DNS” case (now flushed);
    - systemd-timesyncd queries the “ISP” DNS (stopped during the no-query case);
    - a journal line could lag behind the event (now `journalctl --sync`);
    - NM 1.58.1 marks the VPN link `Default Route: yes` in resolved instead of adding `~.` (design.md updated).
  - Deliberate breakages, in the VM: removing the DNS rule from `guard.nft` fails 3 guard cases; preferring AAAA fails the route case.
  - Stability: the final commit ran twice in CI, both DNS modes green each time (50 passed, 1 skipped: the bench check for the other DNS mode), about 2 minutes of cases per job.
  - The 0.7 prototype, its smoke case, `tests/integration/smoke/` and the image's build tools for it are gone; nothing in CI refers to them.
