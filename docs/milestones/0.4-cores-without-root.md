# 0.4 Cores without root

**Stage:** 0 · **Duration:** 2 d · **Depends on:** 0.2, 0.3 · **Needed for:** 0.5, 0.7, 2.3, 3.1

## Goal
Confirm that all three cores pass traffic while running as the `plasma-nm-vpn` user with `CAP_NET_ADMIN` and `CAP_NET_RAW` in our systemd sandbox, and that each of them attaches to an existing persistent TUN created beforehand by root (as the daemon will do) instead of creating its own. The security model and the nftables exemption for core traffic (`meta skuid plasma-nm-vpn`) rest on the first; keeping NM's routes across a core restart rests on the second. If either assumption does not hold, the design must change before the library is written.

## Inputs
- The VM from 0.2, the bench and core binaries from 0.3 (`/opt/pnv-proto/bin/`).
- [design.md](../design.md), section “Architecture”: items “Core launch” (user, capabilities, sandbox, unit name `plasma-nm-vpn-core-<uuid>.service`) and “amneziawg-go” (`/run/amneziawg`, tmpfiles.d, `ReadWritePaths=`, `awg setconf` as root, `-f`).
- [design.md](../design.md), subsection “Network changes and sleep”, item “The TUN belongs to the daemon, not to the core” (persistent TUN, owner `plasma-nm-vpn`; the fallback if a core cannot attach); section “Core supervision and cleanup”, item “Readiness” (the core has attached to the TUN, checked via netlink).
- [design.md](../design.md), section “Open questions and risks”: the first and the fourth “Verify on a prototype (stage 0)” items and the risk “sing-box is moving away from running without root”.

## Tasks
- [ ] Create the system user: `useradd --system --no-create-home --shell /usr/sbin/nologin plasma-nm-vpn` (in the product, the package does this, 1.2).
- [ ] `/etc/tmpfiles.d/plasma-nm-vpn.conf`: `d /run/amneziawg 0750 plasma-nm-vpn plasma-nm-vpn -`, then `systemd-tmpfiles --create`.
- [ ] Script `proto/0.4/run-core <core> <config>` on top of `systemd-run --unit=plasma-nm-vpn-core-<uuid>` with the properties: `User=plasma-nm-vpn`, `AmbientCapabilities=CAP_NET_ADMIN CAP_NET_RAW`, `CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_RAW`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`; for amneziawg-go additionally `ReadWritePaths=/run/amneziawg`. For now the config is a file readable by the user (`LoadCredential=` is milestone 0.5).
- [ ] Before each core starts, the script creates the TUN as root as a persistent device owned by the core user: `ip tuntap add dev pnv-1a2b3c4d mode tun user plasma-nm-vpn` (with `multi_queue` only if the core requests it: a `multi_queue` mismatch makes `TUNSETIFF` fail, while `vnet_hdr` is taken from the attaching side; record which flags each core needs). The cores are configured to use this existing name.
- [ ] sing-box: the client config from 0.3, but instead of SOCKS a `tun` inbound with `interface_name` = `pnv-1a2b3c4d`, `address` from 198.18.0.0/15 (/30), `auto_route: false`; a hysteria2 outbound with `bind_interface: stand-cli`. Try the `stack` values and record which one works without root.
- [ ] xray: a TUN inbound with the same name, a VLESS XHTTP Reality outbound with `sockopt.interface: stand-cli`. Take the exact TUN inbound keys from the README of the TUN module in the pinned version.
- [ ] amneziawg-go: a unit with `amneziawg-go -f pnv-1a2b3c4d` on the existing TUN; then, as root, `awg setconf pnv-1a2b3c4d <file>` (`awg` format, without awg-quick keys), address 100.64.0.2/24, `ip link set up`.
- [ ] For each core, do as root what NM will do later: an address on the TUN (if the core does not set one), `ip route add 203.0.113.0/24 dev pnv-1a2b3c4d`; `curl http://203.0.113.1/`.
- [ ] Check which user the core runs as: `ps -o user,pid,cmd`, `grep Cap /proc/<pid>/status`, `ss -tunape` (uid of the sockets to 198.51.100.1).
- [ ] Negative checks: without `AmbientCapabilities`, record what fails for each core (attaching to a TUN owned by the core user may itself work without `CAP_NET_ADMIN`; binding to an interface, setting the address or MTU may not); amneziawg-go without `ReadWritePaths=/run/amneziawg` does not create its socket. Separately, try without `CAP_NET_RAW` and record whether each core needs it.
- [ ] Persistent TUN, for each core: stop the unit and start it again with the TUN in place → the core attaches again; NM-style state set by root on the TUN (address, the route to 203.0.113.0/24) survives the restart, and `curl` works again without redoing it. Check that the core does not delete or rename the interface on stop or on `kill -9`, and whether it resets the address or MTU on attach. For amneziawg-go, record whether a stale UAPI socket `/run/amneziawg/pnv-1a2b3c4d.sock` is left after `kill -9` and whether it blocks the next start (design.md: the daemon removes it before the start).
- [ ] Readiness signal for 2.3: record how attachment is visible via rtnetlink on a persistent TUN that is not yet up (for example, `IFLA_CARRIER` or `IFLA_OPERSTATE` changing in `ip monitor link` when the core opens the device, and back on detach), and that it does not depend on `IFF_UP` (NM brings the interface up only after `Ip4Config`).
- [ ] Record whether the cores needed any other unit properties (state directory, working directory, access to `/dev/net/tun`), and what messages the cores write to the unit journal.
- [ ] Update design.md: close the first “Verify on a prototype (stage 0)” item in “Open questions and risks” (or rework the “Core launch” item if something did not work); the chosen sing-box `stack` and any additional properties found go into “Architecture”. Close the fourth item (persistent TUN) for sing-box and amneziawg-go, and for xray as far as attaching goes (0.6 adds the restart with the default route); in “Network changes and sleep”, record per core whether it attaches, the TUN flags it needs and, if a core cannot attach, that the temporary per-UUID block chain fallback applies to it. The readiness signal goes into “Core supervision and cleanup”, item “Readiness”.

## Risks and notes
- The official xray and sing-box 1.14.4 units already run without root, and the amneziawg-go code has no root check (design.md). Only our sandbox is being tested.
- Do not enable `PrivateDevices=`: it hides `/dev/net/tun`.
- If sing-box does not work without root in our sandbox, do not work around it on the spot: record the cause and the options from the risk “sing-box is moving away from running without root” in design.md.
- Routes and addresses in this milestone are set manually; in the product NM sets them (0.7).
- If a core cannot attach to a persistent TUN, do not patch the core: the design already has a fallback (a temporary per-UUID block chain during each core restart of a default-route tunnel, even with the kill switch off); record which core needs it so that 2.3, 2.4 and 5.5 plan for it.
