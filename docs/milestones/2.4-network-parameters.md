# 2.4 Network parameters

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 2.3 · **Needed for:** 2.5, 2.6, 2.7, 5.1, 5.4, 5.5

## Goal
Give NM everything it needs to set the address, routes and DNS on the TUN itself, and the route to the server via the parent device. The TUN becomes the daemon's own persistent device, so a later core restart keeps NM's routes. After this milestone a tunnel with a temporary core config is fully configured by NM, and the IP in the route to the gateway matches the IP the core connects to.

## Inputs
- The core launch module from 2.3; the findings of 0.7 on Config, `Ip4Config` and `CAN_PERSIST`; the findings of 0.4 and 0.6 on persistent TUNs (flags, readiness signal); the bench names from 0.3 (`srv.stand.test` with A and AAAA, the AAAA-only `srv6.stand.test`, the “ISP” DNS 192.0.2.1).
- [design.md](../design.md), subsection “Route to the server”: resolution before the tunnel comes up, choosing one IP (IPv4; IPv6 only if the server has no A record), the cached server IP in `/var/lib/plasma-nm-vpn/<uuid>` (the `server` value next to the IP, written only after the session succeeds, ignored when `server` changed), an IP literal used directly, the fallback to the cache when resolution fails, the first-ever connect without resolution and cache, the tmpfiles.d rule `m:90d`, no reconciliation with NM, `NM_VPN_PLUGIN_CONFIG_EXT_GATEWAY` always, binding to the parent device.
- [design.md](../design.md), subsections “TUN addressing” (/30 from 198.18.0.0/15 under a lock file in `/run/plasma-nm-vpn/` with a per-UUID reservation, the pool in `/etc/plasma-nm-vpn/plasma-nm-vpn.conf`) and “DNS” (defaults 1.1.1.1 and 9.9.9.9 only for a default-route tunnel with empty `dns`; with never-default no defaults, explicit DNS servers get /32 routes via the TUN).
- [design.md](../design.md), subsection “Network changes and sleep”: `NM_VPN_PLUGIN_CAN_PERSIST`, item “The TUN belongs to the daemon, not to the core”; section “Core supervision and cleanup”, item “On `Connect`, in this order” (step 3: resolution with a 5 s timeout, persistent TUN, chains, core unit); “Leak protection”, items “When the chains are installed” and “Kill switch lifecycle” (session, success).
- For reference: the Config and `Ip4Config` keys in `src/libnm-core-public/nm-vpn-dbus-interface.h`.

## Tasks
- [ ] Server resolution: the system resolver (`getaddrinfo` in a worker thread or `GResolver`) in `Connect`, after the guard unit is running and before the TUN, the chains and the core (2.3, 2.6), with a 5 s timeout. An IPv4 address is taken; IPv6 only if the server has no A record. An IP literal in `server` is used directly, without resolution or cache. The selection is a separate function with unit tests on a stubbed resolver (A and AAAA, AAAA only, no answer, timeout).
- [ ] Cached server IP: an atomic write to `/var/lib/plasma-nm-vpn/<uuid>` (root, 0600; the directory is installed by `plasma-nm-vpn-common`) holding the profile's `server` value and the IP, and a read function that ignores the file when the stored `server` differs from the profile's. The file is written only when the session succeeds, which also refreshes its modification time; a failed attempt never touches it. Until the liveness check exists (5.4), the success point is ACTIVATED; 5.4 moves it after the check. If resolution fails and a valid cache entry exists, it is used. If resolution fails and there is none (the very first connect of a profile), `Connect` fails with a logged reason before any chains are installed; this is a `Connect` error, not a give-up. Using the session server IP on reconnect is 5.5; using the cached server IP right away when this profile's kill switch chains remain is 5.2.
- [ ] Session server IP: the chosen IP is also written to the run directory, so that the reconnect cycle (5.5) reuses this session's IP rather than resolving again.
- [ ] Stale files: a tmpfiles.d rule in `plasma-nm-vpn-common` that ages `/var/lib/plasma-nm-vpn/` by modification time only, for example `d /var/lib/plasma-nm-vpn 0700 root root m:90d` (check the syntax in forky's `tmpfiles.d(5)`). The daemon does not reconcile the cache with NM's profile list: profiles can change while NM is down, and the age rule is simpler.
- [ ] Persistent TUN: after resolution and the collision check (2.3), the daemon creates `pnv-<8 characters of the UUID>` as a persistent TUN owned by `plasma-nm-vpn` (`TUNSETIFF` + `TUNSETPERSIST` + `TUNSETOWNER` as root, or netlink; the flags as found in 0.4), before the chains and the core unit. The core attaches to it, and readiness (2.3) becomes “the core has attached”. It is deleted on disconnect and by `--daemon-gone` (both already delete the TUN, 2.3). If 0.4 or 0.6 found that a core cannot attach, that core keeps creating its own TUN.
- [ ] TUN subnet: a free /30 from 198.18.0.0/15, not overlapping with addresses and routes on the machine (netlink), with a starting position derived from a hash of the UUID. The choice is made under a lock file in `/run/plasma-nm-vpn/` and recorded as a per-UUID reservation, so that two daemons connecting at once never pick the same /30 before NM applies either; the reservation is released on disconnect and ignored once its run directory is gone. The pool can be overridden in `/etc/plasma-nm-vpn/plasma-nm-vpn.conf` (choose the key format and record it in design.md).
- [ ] Parent device: get, via libnm, the interface name of the parent device of our own VPN connection (verify that `nm_active_connection_get_devices()` on a VPN connection returns exactly that). This is the `bind_interface` value for the 2.5 generator.
- [ ] Until the generator exists (2.5), the daemon fills the chosen /30, the server IP and the parent device into the temporary 0.7 config (TUN address, `server`, `bind_interface`), so that the tunnel already works end to end with real values.
- [ ] Config: `tundev` (`pnv-…`), `gateway` (the chosen IP), `can-persist`, `has-ip4=true`, `has-ip6=false`, `mtu` if present in the profile.
- [ ] `Ip4Config`: `address` and `prefix=30`; DNS by the rules in design.md, “DNS”: the profile's servers; with a default-route tunnel and empty `dns`, `1.1.1.1` and `9.9.9.9`; with never-default (the profile's `ipv4.never-default` from `Connect`), no defaults, and each explicit DNS server gets a /32 route via the TUN. The default route itself is decided by NM.
- [ ] Ordering: Config and `Ip4Config` are sent only after the core has attached to the TUN (2.3) and the chains are installed (2.6).
- [ ] Test `.nmconnection` files: default-route tunnel and never-default (with and without `dns`); `server=srv.stand.test`; `ipv4.dns-priority` and `ipv4.dns-search` are not set.

## Deliverables
- Modules for resolving the server and caching its IP, creating the persistent TUN, choosing and reserving the subnet, getting the parent device, and building Config and `Ip4Config` in `plasma-nm-vpn-common`; the tmpfiles.d rule.
- The pool setting format in design.md.

## Done when
- [ ] `nmcli connection up` → `ip -d link show pnv-…` shows a persistent TUN (`persist on`) owned by `plasma-nm-vpn`; `ip -4 addr show pnv-…` shows an address from 198.18.0.0/15 with /30, and the interface was brought up by NM. After `nmcli connection down` the TUN is gone.
- [ ] `ip route get <server IP>` → the route goes via the parent device, not via `pnv-…`; for `srv.stand.test` the IP is 198.51.100.1 (IPv4 preferred), and it matches the IP in the core config and, after the session succeeds, the contents of `/var/lib/plasma-nm-vpn/<uuid>` (next to `srv.stand.test`).
- [ ] A default-route profile with empty `dns` → `nmcli -f IP4.DNS device show pnv-…` shows 1.1.1.1 and 9.9.9.9; in the default `resolv.conf` mode `/etc/resolv.conf` lists them before the parent device's servers; in the systemd-resolved variant `resolvectl status pnv-…` shows them and the `~.` domain added by NM.
- [ ] A never-default profile → no default route via `pnv-…`, the route to the server exists; with empty `dns` no DNS servers on `pnv-…`; with `dns=203.0.113.1` that server is on `pnv-…` and `ip route get 203.0.113.1` goes via `pnv-…`.
- [ ] Connect once and note the /30 chosen for this UUID; disconnect, put exactly that /30 on a dummy interface, connect again → a different free /30 is chosen. Two profiles connected at the same moment get different /30s.
- [ ] A core with a deliberately broken config (2.3) → the attempt fails and `/var/lib/plasma-nm-vpn/<uuid>` is not created or changed.
- [ ] A new profile whose server name does not resolve (the “ISP” DNS stopped) and that has no cache file → `Connect` fails within about 5 s with a logged reason, and no chains, TUN or core unit were created. The same with a cache file whose stored `server` differs from the profile's. `server=198.51.100.1` → connects with no DNS query (no query in a capture on `stand-cli`).
- [ ] A file in `/var/lib/plasma-nm-vpn/` with its modification time backdated by `touch -m -d '-91 days'` (its ctime stays current) → `systemd-tmpfiles --clean` deletes it; a file with a current modification time survives.

## Risks and notes
- Without `gateway`, NM aborts activation (verified against the 1.58.1 sources): always pass it.
- The sing-box TUN inbound itself requires an address in the config; it must match the address in `Ip4Config` (checked in 2.5).
- With an IPv6 server, the core's traffic to it does not trip the IPv6 guard from 2.6 only thanks to the `skuid` exception. The end-to-end tests of name resolution, the cached-IP fallback and the AAAA-only server belong to 2.7.
- `getaddrinfo` has no timeout of its own; a blocking call must not stall the daemon's main loop or exceed the 5 s budget (2.3).
