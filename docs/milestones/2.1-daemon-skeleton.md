# 2.1 Daemon skeleton

**Stage:** 2 · **Duration:** 2 d · **Depends on:** 1.1, 0.7 · **Needed for:** 2.2–2.7

## Goal
Turn the daemon prototype from 0.7 into the shared library `plasma-nm-vpn-common` that all three daemons are built on: D-Bus, states, secrets, errors and logging are written once. After this milestone the sing-box daemon already registers with NM and handles `Connect`/`Disconnect` correctly, although it does not bring up a tunnel yet.

## Inputs
- The repository skeleton and the daemon CMake from 1.1; the working plugin prototype and the findings of 0.7.
- [design.md](../design.md), section “Architecture”: `NMVpnServicePlugin`, `--bus-name`, `supports-multiple-connections=true`, the `own_prefix` policy, matching names, service names per protocol (`org.freedesktop.NetworkManager.pnv.hysteria2`), protocol from `vpn.service-type`, several `.name` files for one binary.
- [design.md](../design.md), section “Profile data schema”, paragraph “Secrets”: `<key>-flags` flags, `need_secrets` for each protocol.
- [design.md](../design.md), section “Core supervision and cleanup”: the failure signal carries only a code, details go to the journal (item “Core unit failure”); item “Disconnect”: cleanup is synchronous, finished before the `disconnect` handler returns, because libnm quits the main loop right after `STOPPED`.
- The 0.7 findings on when libnm quits and on the deactivation reasons NM reports.
- For reference: `src/libnm-client-impl/nm-vpn-service-plugin.c` (NM 1.58.1), `src/nm-openvpn-service.c` (NetworkManager-openvpn).

## Tasks
- [x] Library: a base class derived from `NMVpnServicePlugin` overriding `connect`, `disconnect`, `need_secrets` (`connect_interactive` and `new_secrets` per the findings of 0.7). A concrete daemon registers a protocol table: service-type → handlers (list of secrets, validation, config generation — stubs for now). For the sing-box daemon the table has a single protocol for now: `org.freedesktop.NetworkManager.pnv.hysteria2`.
- [x] The daemon's `main()`: parse `--bus-name` (via `GOptionContext`, as in openvpn), create the object with `NM_VPN_SERVICE_PLUGIN_DBUS_SERVICE_NAME` and `NM_VPN_SERVICE_PLUGIN_DBUS_WATCH_PEER=TRUE` so that the process exits after `STOPPED` and when NM goes away; a `--debug` option for local debugging.
- [x] Protocol detection: `nm_setting_vpn_get_service_type()` from the `Connect` settings; a service-type not in the protocol table → `Connect` error without launching anything.
- [x] Shared `need_secrets`: based on the protocol's list of required secrets and their flags, read with `nm_setting_get_secret_flags()` on the connection's `NMSettingVpn` (the `<key>-flags` entries), return `"vpn"` if a secret is missing and its flag is not `NOT_REQUIRED`.
- [x] Errors: a single “give up” function — logs the reason to the journal (later also the core's unit name for `journalctl -u`) and calls `nm_vpn_service_plugin_failure` with the appropriate `NM_VPN_PLUGIN_FAILURE_*` code (`LOGIN_FAILED`, `CONNECT_FAILED`, `BAD_IP_CONFIG`). The signal carries only the code. After it, libnm itself moves the connection to `STOPPED` and calls the disconnect handler, so the handler must be ready for such a call. The give-up flag for the kill switch is added in 5.1. Errors before the core is launched are returned via `GError` from `connect`.
- [x] Synchronous `disconnect`: the handler runs the cleanup steps registered by later milestones (core unit 2.3, chains 2.6, guard unit 2.3) to completion before it returns, with blocking D-Bus calls (or a private main context), never by scheduling work on the main loop. Telling an explicit disconnect from a give-up by the deactivation reason is 5.1.
- [x] Test build: a CMake option (for example `-DPNV_TEST_HOOKS=ON`, off by default) that compiles in the test hooks used by this and later milestones (a deliberately slow cleanup step here, the dummy chain in 2.3); `debian/rules` never enables it, so no package ever contains them (design.md, “Testing”). How the integration harness puts the test build in place for the cases that need it is decided in 2.7.
- [x] Logging: `g_log` with the daemon's domain and the profile UUID in every message; values from `vpn.secrets` are never logged, including with `--debug`.
- [x] `.name` for `org.freedesktop.NetworkManager.pnv.hysteria2` (`program=/usr/lib/plasma-nm-vpn/plasma-nm-vpn-service-sb`, the shared sing-box daemon binary per design.md item “Paths”; `supports-multiple-connections=true`) in `/usr/lib/NetworkManager/VPN/`. D-Bus policy in `/usr/share/dbus-1/system.d/` modeled on `nm-openvpn-service.conf`: `own_prefix` and `send_destination` for root only.
- [x] A test `.nmconnection` with `service-type=org.freedesktop.NetworkManager.pnv.hysteria2` and a script for the VM: load the profile, `nmcli connection up`, check the journal. Scripts pass secrets with `nmcli connection up <name> passwd-file <file>` (`vpn.secrets.password:<value>`).

## Deliverables
- The `plasma-nm-vpn-common` library (plugin skeleton, protocols, secrets, errors, logging) and the sing-box daemon built on it.
- `.name`, the D-Bus policy, and their installation in `debian/`.

## Done when
- [x] `nmcli connection up` of a Hysteria2 profile → NM starts the daemon with `--bus-name org.freedesktop.NetworkManager.pnv.hysteria2.Connection_<N>`, and it acquires the name on the bus (visible in `busctl --system list`).
- [x] A profile without `password` with the flag “Ask for this password every time” → `need_secrets` returns `"vpn"` and NM issues `GetSecrets` to the secret agents (visible in the NM journal); `nmcli connection up <name> passwd-file <file>` gets past this step and reaches `Connect`.
- [x] A test-only `.name` (installed only by the test harness) whose `service` is not in the protocol table but whose `program` is our daemon binary, and a profile with that service-type → `Connect` fails, nothing is launched, and `journalctl` names the unknown service-type. A call to the “give up” stub → the connection fails, and `journalctl` has a clear reason without secrets.
- [x] `nmcli connection down` → the daemon receives `Disconnect`, moves to `STOPPED` and exits; in the test build, a deliberately slow cleanup step (a test hook, a few seconds) logs its completion before the process exits.
- [x] The packaged daemon binary (from the `packages` job) contains no test hooks: the option is off in `debian/rules`, and a check in the job (for example, `strings` on a marker symbol) fails the build otherwise.

## Risks and notes
- The user sees the reason text and the unit name only in the journal: this was decided in design.md and does not need rechecking.
- The base class itself sets a 60 s connect timer (`nm-vpn-service-plugin.c`); waiting for the TUN (15 s, milestone 2.3) fits within it.
- That NM checks the uniqueness of `service`, not `program`, has already been established in design.md.
- The service name ends up in `.nmconnection` and cannot be changed later without breaking profiles: do not touch it after this milestone.
- Results: `common/daemon` (`plugin.c`, `secrets.c`) and the sing-box daemon; `connect_interactive`/`new_secrets` are not overridden yet, so libnm answers `ConnectInteractive` with “not supported” and NM falls back to `Connect`. The cases are `tests/integration/cases/test_30_daemon.py` (test build, marker `test_build`; 2.7 decides how CI installs it), green in the VM. nmcli turned out to fill `passwd-file` (and `--ask`) only for the secrets it knows of: hints from the plugin, a hardwired list of in-tree plugins, or an auth dialog in external UI mode. Without one, `GetSecrets` ended with “No agents were available for this request”. So `plasma-nm-vpn-common` ships `plasma-nm-vpn-auth-dialog`, named in each `.name` under `[GNOME]` with `supports-external-ui-mode=true`. It reads the connection over stdin, prints the `[VPN Plugin UI]` keyfile with the service type's secrets from the table that `need_secrets` uses, and asks nothing itself. plasma-nm ignores it. Journal checks in the cases use cursors, not `--since`: cases started within one second saw each other's lines.
